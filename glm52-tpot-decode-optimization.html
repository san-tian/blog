核心结论

无损融合新的 fused_dsa_quant_store 用一个 kernel 替代「量化 + 写回」两步，省掉一个中间 tensor 和一次 kernel launch，且 nope / scale / rope 三区域字节级一致（0-byte diff）。
量化公式逐行一致量化必须用 y * (1.0/y_s) 而非 y / y_s——浮点舍入不同会导致非字节级无损，这是合并时被实测揪出来并修正的关键细节。

背景：DSA 的 KV cache 长什么样

GLM-5.2 走的是 DSA（DeepSeek Sparse Attention）路径。在 DSA 里，每 token 每层的 K 被拆成两部分：

  • k_nope（512 维）：不带位置编码的 latent 部分，可以做量化压缩；
  • k_rope（64 维）：已经过 RoPE 的旋转位置编码部分，位置敏感、保持 bf16 不量化。

写进 paged KV buffer 时，两种 dtype 混在同一个 buffer 里，字节布局固定为：

# 每 token 每层 656 字节
[ nope_fp8(512) | scales_fp32(16) | rope_bf16(128) ]
    0 .. 511        512 .. 527        528 .. 655   (字节偏移)

# fused_dsa_quant_store.py:15-27
_DIM_NOPE = 512          # k_nope 维度
_DIM_ROPE = 64           # k_rope 维度
_GROUP_SIZE = 128        # 量化分组大小
_NUM_NOPE_BLOCKS = 4     # 512 / 128
_SCALE_BYTES = 16        # 4 blocks × 4 字节 fp32 scale
_ROPE_BYTES = 128        # 64 × 2 字节 bf16
_TOTAL_BYTES = 656

其中 scales_fp32(16) 是 k_nope 每 128 个元素一组的量化 scale（4 组 × 4 字节），rope_bf16(128) 是 64 个 bf16 元素（64 × 2 = 128 字节）。MLA/DSA 的更完整背景见姊妹篇 《sglang 算子融合：从天花板到突破》。

改动①：融合 DSA 量化写回 kernel

这是本 commit 的核心代码。原来这条路径要分两步走：

  1. quantize_k_cache_separate() —— 先把 k_nope 量化成 fp8、拿到 scale，产出一个中间 tensor；
  2. set_mla_kv_buffer_triton() —— 再把这个中间 tensor 写进 paged KV buffer。

两步意味着：一个中间 tensor 的显存分配/释放 + 两次 kernel launch。融合后，一个 kernel 边量化边按字节偏移直接写进 paged buffer，省掉中间 tensor 和一次 launch。

三个 dtype 视图覆盖同一个 buffer

融合的关键是：同一个 paged buffer，用三个不同 dtype 的 view 分别覆盖三段字节区间——这样 triton kernel 写不同区域时能各自以「元素」为单位寻址，而不需要手动拼字节：

# fused_dsa_quant_store.py:102-109
buf_flat = kv_buffer.view(kv_buffer.shape[0], kv_buffer.shape[1], -1)
nope_buf  = buf_flat[:, :, _NOPE_OFFSET : _NOPE_OFFSET + _DIM_NOPE]          # fp8
scale_buf = buf_flat[:, :, _SCALE_OFFSET : _SCALE_OFFSET + _SCALE_BYTES].view(torch.float32) # fp32
rope_buf  = buf_flat[:, :, _ROPE_OFFSET : _ROPE_OFFSET + _ROPE_BYTES].view(torch.bfloat16)   # bf16

kernel 网格：每 token 5 个 block

kernel 用二维 program grid (num_tokens, 5)：前 4 个 block 各量化一段 128 维的 k_nope，第 5 个 block 负责拷贝 k_rope。这样 128 个元素一组恰好整除、nope 段无需 mask：

# fused_dsa_quant_store.py:50-80（节选）
token_id = tl.program_id(0)
block_id = tl.program_id(1)
cache_loc = tl.load(loc_ptr + token_id).to(tl.int64)

if block_id < NUM_NOPE_BLOCKS:
    # 量化这一段 nope，用自己的 per-block scale
    offs = block_id * GROUP_SIZE + tl.arange(0, GROUP_SIZE)
    y = tl.load(k_nope_ptr + token_id * k_nope_stride_0 + offs).to(tl.float32)
    y_s = tl.max(tl.abs(y)) / FP8_MAX
    y_s_inv = 1.0 / y_s
    y_q = tl.clamp(y * y_s_inv, -FP8_MAX, FP8_MAX).to(nope_buf_ptr.dtype.element_ty)
    tl.store(nope_buf_ptr + cache_loc * nope_buf_stride_0 + offs, y_q)
    tl.store(scale_buf_ptr + cache_loc * scale_buf_stride_0 + block_id, y_s)
else:
    # 拷贝 rope 部分，保持 bf16（位置敏感，不量化）
    rope_block = block_id - NUM_NOPE_BLOCKS
    offs = rope_block * GROUP_SIZE + tl.arange(0, GROUP_SIZE)
    mask = offs < DIM_ROPE
    data = tl.load(k_rope_ptr + token_id * k_rope_stride_0 + offs, mask=mask, other=0.0)
    tl.store(rope_buf_ptr + cache_loc * rope_buf_stride_0 + offs, data, mask=mask)

正确性细节一：量化公式必须逐行一致

per-block 量化是「按块找最大绝对值 → 除以 fp8 上限得到 scale → 乘 scale 的倒数」：

y_s = max(|y|) / 448.0
y_q = clamp(y * (1.0 / y_s), -448.0, 448.0)

这里的陷阱在 y * (1.0/y_s) vs y / y_s：两者数学上等价，但浮点舍入不同。融合 kernel 必须与未融合路径 quant_k_cache._quantize_k_cache_fast_kernel 逐行一致（用 scale 倒数相乘，不用除法），否则写出的字节与未融合路径对不上——就不是「无损」了。源码注释明确写了这一点（B300 + triton 3.6.0 上实测 y / y_s 会产出不同的 nope 字节）。✓ 源码确认

正确性细节二：fp8 e4m3fn 是对称的，max = 448

代码里 _FP8_MAX = 448.0 不是随便取的：fp8 e4m3fn 是对称格式，可表示的最大有限值是 448，且 max = -min。所以 clamp 的上下界是 ±448。✓ 源码确认

正确性细节三：测试必须用无碰撞的 loc

test_correctness() 里对 fused 与未融合两条路径做字节级对比（nope / scale / rope 三段分别 torch.equal）。一个容易踩的坑：槽位 id loc 必须用 torch.randperm（无碰撞），不能用 randint——128 token 撒进 256 个槽，randint 平均产生 ~27 个碰撞槽；碰撞槽的「最后写入者」在 torch 参考实现（串行覆盖）与 triton 融合 kernel（并行、顺序未定义）之间不一致，会让测试假失败，尽管 kernel 本身是无损的。

这个测试细节本身就是一个好例子：验证「无损」时，对照实验和被测对象必须在同样的并行语义下比较，否则测的不是正确性，而是两条路径对同一竞态的未定义行为差异。

改动②：跳过 no-op 的 slice + contiguous

第二个代码改动很小，但目标明确：在 MoE forward 里，final_hidden_states 的最后一维如果已经等于 origin_hidden_states_dim，就不再做 slice + contiguous。原来是无条件的：

# fused_moe_triton/layer.py:1291 附近（改前）
final_hidden_states = final_hidden_states[..., :origin_hidden_states_dim].contiguous()

# 改后：维度已匹配就直接跳过
if final_hidden_states.shape[-1] != origin_hidden_states_dim:
    final_hidden_states = final_hidden_states[..., :origin_hidden_states_dim].contiguous()

那个无条件的 view + contiguous 会额外起一个 copy kernel（profile 里表现为 unrolled/vectorized_elementwise），数值上完全无影响，只是白跑一次拷贝。加一个 shape 判断就能省掉每个 MoE forward 的一次 kernel launch——它计入本次 -13.1% 的累计收益里。✓ 源码确认

改动③：文档记录的两项配置层优化

真正拉开收益的两项，其实不在「写代码」而在「改配置」，它们记录在新增文档 docs/agent/glm52-tpot-decode-optimization.md 里。

AllReduce 融合（-4.6~5.5%）

GLM-5.2 的 GlmMoeDsaForCausalLM 在 SM100（Blackwell）支持列表内，去掉 --enforce-disable-flashinfer-allreduce-fusion 后，TP 的 AllReduce 能融进 mnnvl attention kernel，省掉单独的通信-计算切换。同 bs/seq_len 的 A/B 下，decode verify 中位数下降 4.6%~5.5%。

tile 对齐 BLOCK_SIZE_M=64→16（-8.8%，最大单项）

decode 日志显示 GLM-5.2（E=257, N=256, L20D）没有匹配的 MoE config 文件，走了默认 BLOCK_SIZE_M=64。参考同构 B200 实测 tune 值，为 L20D 生成 BLOCK_SIZE_M=16 的 config（含 down TMA），严格 A/B 下：

一个值得注意的细节：config 的 18 个标准 key 里，BLOCK_M=16 覆盖了 1~512 的全部 decode 实际 M 值；decode 里 46.4% 的非标准 M（40/72/88/104）fallback 到邻近 key 后 BLOCK_M 仍为 16。也就是说主导的 tile 维度被 100% 覆盖，残留的只是 N/K 的 64↔128 小差异。

诚实结论

这个 commit 最有教学价值的一点，恰恰是它如实标注了每个优化的真实贡献：

  • 融合 DSA 量化写回 kernel 在工程上是干净的——省中间 tensor、省一次 launch、字节级无损，但端到端只带来 +0.9%（噪声级）。它的价值在「消除低效、为后续优化铺路」，不在「直接提速」。
  • -13.1% 的大头来自配置层：AllReduce 融合（-4.6~5.5%）和 tile 对齐（-8.8%）。这两项不写一行算子代码，只是「去掉一个错误的启动 flag」和「补上一份匹配的 config 文件」。
  • 方法论上，文档反复强调同 bs/seq_len 的严格 A/B 才可信——grep 全日志均值会混入多次重启的不同批次，直接导致误判。

一句话：机制上「能不能融合」和性能上「融合划不划算」是两件事，这个 commit 用源码和实测把两者都讲清楚了。
