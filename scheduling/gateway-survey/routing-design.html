细粒度负载路由设计：基于「逐请求 prefill 等待」

insight 路由策略设计 队列组成盲区

核心问题：计算负载时，现有方案用的都是实例级聚合指标（inflight token 总数、活跃请求数），看不到实例队列内部每个请求各自的 prefill 等待量。本文展开这个盲区，并设计一个基于逐请求细粒度负载的路由策略。

缺陷分析：路由策略在两个层次都太粗

把现有路由策略的缺陷拆成两个独立层次——它们叠加，就是「长 prefill + 长 decode 混合负载下路由失准」的根源。

缺陷 1：负载度量太粗（聚合 → 逐请求）

  • 现状：inflight token 总数、batch size、活跃请求数——都是聚合标量。
  • 缺陷：看不到队列组成——「谁挡在前面、挡多久」。
  • 症状：1 个长 prefill 大块头 vs 100 个短请求，聚合值一样，新请求的实际等待天差地别。

缺陷 2：瓶颈表达太粗（标量 → 向量）

  • 现状：路由打分把 prefill（计算密集） 和 decode（内存带宽密集） 两个维度的饱和度压成一个标量 score。
  • 缺陷：一个标量无法同时表达「计算快满了」和「内存快满了」两种状态。
  • 修正：llm-d 的「瓶颈匹配」和 Lodestar 的「inflight prefill/decode tokens 分开」已经在度量层分开了信号——真正的缺陷是，它们在路由决策这一步又把两个信号合成了一个标量，信息在最后一步丢失。
一句话 gap：现有路由策略在「度量维度」和「瓶颈维度」上双重粗粒度——度量上要逐请求（看队列组成），瓶颈上要分维（prefill/decode 各看饱和度）。两者叠加，导致长 prefill + 长 decode 混合负载下路由失准。

两个缺陷的对应解方向

缺陷解方向本页对应
度量太粗逐请求队列 W_i(r)「细粒度负载模型」+「新路由策略」
瓶颈太粗瓶颈向量 (P_i, D_i) × 冲击向量 (c_r, m_r)「瓶颈向量路由」

你的 insight：聚合负载指标的「队列组成盲区」

现有路由策略计算负载时，看到的都是聚合值：

方案负载指标粒度
llm-d token-loadin-flight 未缓存 token 数实例聚合
LMetricbatch size实例聚合
Dynamotoken 负载（剩余 prefill + 活跃 decode）实例聚合
Lodestarinflight prefill/decode tokens、running/queued 数实例聚合

聚合值的致命盲区：同样的聚合数字，队列组成可以完全不同，新请求的实际等待时间也完全不同。

一个反例：两个实例，聚合 inflight prefill 都是 100 token，但——
  • 实例 A：1 个请求正在 prefill，剩余 100 token（一个"大块头"挡在前面）。
  • 实例 B：100 个请求，各剩余 1 token（prefill 都快完了，但 decode 队列很长、KV 满）。
聚合指标看两者"一样闲/一样忙"，但新请求路由过去：
  • 到 A：要等那个 100-token 大块头 prefill 完（且它是计算密集，占满 GPU）；
  • 到 B：prefill 瞬间就空出位置，但要挤进已经很满的 decode 批。
「总共多少」掩盖了「谁挡在前面、挡了多久」——这正是你要解决的盲区。

细粒度负载模型：把实例负载拆成「逐请求队列」

把实例的负载从"一个聚合数"升级为"一个有序的逐请求队列"：

Q_i = [ (r_1, c_1, s_1), (r_2, c_2, s_2), ..., (r_k, c_k, s_k) ]

  c_j = 请求 j 的剩余 prefill 成本（token 数，考虑 KV 命中后还需新算的）
  s_j = 请求 j 的状态（prefill 中 / 排队中 / decode 中）

三个关键字段：

  • c_j（剩余 prefill 成本）：LMetric 已经证明该用"需新算的 prefill token 数"（而非命中率）——这里把它细化到每个请求。
  • 逐请求而非聚合：这样才知道"排在新请求前面的具体是哪些请求、各剩多少"，而不是只知道"总共还剩多少"。
  • 动态更新：c_j 随 prefill 推进递减，prefill 完成后请求转入 decode（对后续 prefill 不再构成阻塞）。

新路由策略：最小化「新请求的期望 TTFT」

路由目标从"平衡聚合负载"改为"最小化新请求的期望 TTFT"——而期望 TTFT 由逐请求队列精确算出。

打分公式

TTFT(r → i) ≈ ( W_i(r) + c_r ) / prefill_throughput_i

W_i(r) = Σ c_j        # 所有「排在 r 前面」的请求的剩余 prefill 之和
  • c_r：新请求自己的 prefill 成本（输入 token − 命中 KV 的 token）。
  • W_i(r)：r 插进队列后，排在它前面的那些请求的剩余 prefill 之和——这才是"r 实际要等多久"的精确度量，也是聚合指标算不出来的部分。
  • 路由决策：选 TTFT 最小的实例。

「排在 r 前面」由队列重排策略决定——这是设计的核心自由度

重排策略W_i(r) 的计算效果
FIFO（不重排）r 排队尾，W = 队列里全部剩余 prefill 之和等价于聚合指标（退化为 llm-d 的 inflight token），无新增信息
SJF（短请求插队）r 插到所有 c_j < c_r 的请求前面，W = 所有 c_j < c_r 的请求的 prefill 之和短请求等待大幅缩短；长请求可能饿死，需 aging 兜底
分位感知（QUARTZ 式）用每个请求的 prefill 分位（而非精确值）排序对不确定性的鲁棒性更好

关键：FIFO 下逐请求信息没有新增价值（退化成聚合）；逐请求信息的价值在于支持队列重排（SJF/分位）——而这正是 QUARTZ 在"准入层"已经做了、但"路由层"还没做的事。

瓶颈向量路由：把负载从标量升级到二维（缺陷 2 的解）

缺陷 2 的解方向：实例状态和新请求冲击都用二维向量表示，而不是压成一个标量。

实例状态 = 瓶颈向量

实例 i 的状态 = (P_i, D_i)
  P_i = prefill 饱和度（计算维度）
  D_i = decode 饱和度（内存/带宽维度）

新请求冲击 = 冲击向量

请求 r 的冲击 = (c_r, m_r)
  c_r = prefill 冲击（需新算 token，瞬时计算）
  m_r = 内存冲击（KV cache 大小 ≈ 总 token 数，长期占用）

关键：不同请求对两个维度的冲击不同——长 prefill 请求 c_r 大、m_r 小；长 decode 请求 c_r 小、m_r 大。这正是标量 score 表达不了的。

路由决策（方向性示意，范数待实验）

cost(r → i) = max( P_i + c_r / C_i,   D_i + m_r / M_i )

# C_i、M_i = 实例 i 的计算 / 内存容量
# 取 max：任一维度超载都会拖垮实例（木桶原理），选 cost 最小的实例
两个缺陷的解是天然互补的：瓶颈向量 P_i 的精确值，正是逐请求队列的 Σ c_j / C_i——所以「度量细粒度」（逐请求队列）提供了精确的 P_i，而「维度细粒度」（向量化）保证 P_i 和 D_i 不被压成一个标量。两者合起来才是完整的路由模型。

算法谱系与依据：这个设计基于哪些旧指标

严格说，这个设计没有发明新指标——它是几个「已有旧指标/旧方法」的细粒度组合。逐组件追溯：

本设计的组件直接继承的旧指标/方法来源
c_j / c_r：逐请求的「剩余 prefill 成本（token 数）」 LMetric 的「需新算的 prefill token 数」（KV 指标，而非命中率） LMetric（OSDI 26）
W_i(r)：排在 r 前面的成本之和 llm-d / Lodestar 的「inflight prefill token 总和」，拆成「逐请求前缀和」 llm-d token-load；Lodestar
路由目标：最小化期望 TTFT 排队论 JSQ（join the shortest queue）的 LLM 化——把「最短队列」换成「最短剩余工作量」 经典排队论（见下）
队列重排：SJF + aging QUARTZ 的准入队列（逐请求分位成本 + SJF + λ·a_r aging） QUARTZ（ACL 26 findings）

概念来源：经典调度理论（注意：结论不能直接套用）

  • SRPT 最优性：单机、已知处理时间下，SRPT（最短剩余处理时间优先）最小化平均响应时间。来源：Schrage & Miller, "The Queue M/G/1 with the Shortest Remaining Processing Time Discipline", Operations Research 14(4):670–684, 1966。 DOI →
  • SPT（Smith 规则）：最短处理时间优先最小化平均等待时间。来源：W. E. Smith, "Various Optimizers for Single-Stage Production", Naval Research Logistics Quarterly 3(1-2):59–66, 1956。 DOI →
  • Size-based dispatching：按 job size 路由 + size-aware 排序。来源：Harchol-Balter, Schroeder, Bansal, Agrawal, "Size-Based Scheduling to Improve Web Performance", ACM TOCS 21(2), 2003。 论文 →
这些经典结论在 LLM 推理场景下假设不成立，只能当「概念来源」、不能当「理论依据」：
  • 「处理时间已知」只对 prefill 成立：SRPT/SPT 假设 job size 到达即知；LLM 里 decode 长度不可预测（用户随时停），只有 prefill 的「需新算 token」可估计。
  • 「可抢占且无成本」不成立：SRPT 依赖免费抢占；LLM 里抢占 = 丢弃/换出 KV cache，代价不小。
  • 「服务时间外生」不成立：经典模型里 job 处理时间与调度无关；LLM 里 batching 让处理时间内生（取决于和谁同批）。
  • 「size 不随服务器改变」不成立（最关键）：经典 size-based 里同一 job 到处一样；LLM 里 size = KV 命中后需新算 token，因实例缓存状态而异——这正是 KV 感知路由存在的原因，也是经典结论失效的根源。
  • 「最小化平均」目标不匹配：SRPT/SPT 优化平均响应时间；LLM 要的是尾延迟（P99 TTFT）和 SLO 达成率，SRPT 甚至会恶化长请求的尾延迟。
所以：这些文献的价值在于提供正确的概念框架 + 「短任务优先」的普适直觉；真正可直接作为依据的前身是 QUARTZ——它已经用「分位预测」处理了「处理时间未知」、用「aging」处理了「短任务优先的公平性」，这两个正是经典文献没解决、而 LLM 场景必须解决的问题。
一句话谱系：
经典调度理论（JSQ 路由目标 + SPT/SRPT + size-based dispatching，作为概念来源，结论见上限定）
→ LLM 系统的旧指标（LMetric 的需新算 prefill token、llm-d/Lodestar 的 inflight token 总和、QUARTZ 的逐请求准入队列）
→ 本设计（把这些旧指标的粒度统一推进到「逐请求」，路由层直接算 W_i(r) 而非聚合值）。
所以它不发明新指标，真正的增量只有一处：把「队列总成本」换成「排在 r 前面的成本之和」（逐请求前缀和），以及把 QUARTZ 的准入层逐请求机制提前到路由层。

和现有方案的关系：把 QUARTZ 的准入粒度提前到路由

这个设计不是凭空发明，而是把几篇论文的边界往前推一步：

方案路由层（选实例）用什么准入层（排顺序）用什么
LMetric聚合 batch size × 新请求 prefill无（交给引擎 FCFS）
llm-d聚合 inflight token / 活跃请求无（粘性 + 饱和释放）
QUARTZ聚合 Ŵ + 新请求分位（K=2 候选）逐请求分位 + aging + 公平（SJF 类）
本设计逐请求队列（精确 W_i(r)）同一套逐请求队列（路由 + 准入统一）
一句话定位：QUARTZ 已经证明「逐请求成本 + SJF + aging」在准入层能降尾延迟；本设计把它提前到路由层——路由决策直接看"插进这个实例的逐请求队列后，新请求要等多久"，而不是看聚合的 inflight 数。同时把 QUARTZ 的"分位预测"（有误差）升级为"逐请求精确队列"（无预测误差，代价是状态维护）。

打分公式的两种实现（精确 vs 分位）

实现 A：精确逐请求队列

TTFT(r → i) = ( Σ_{j: c_j < c_r} c_j  +  c_r ) / prefill_throughput_i

# 假设 SJF 重排，r 插到所有比它短的请求前面

优点：精确，无预测误差。缺点：需要实时维护每个实例的逐请求队列（成本动态递减、完成即移除），且多实例路由时这个状态的跨副本同步更难。

实现 B：分位逐请求队列（QUARTZ 的细粒度版）

用 Q̂_prefill_α(r_j) 替代精确 c_j，其余不变

优点：对成本估计误差更鲁棒。缺点：分位预测本身有误差（QUARTZ 用决策树 + pinball loss）。

挑战与代价（诚实标注）

  • 状态维护成本：路由器要实时追踪每个实例里每个请求的剩余 prefill（c_j 动态递减），这比维护一个聚合计数器重得多。但好消息是：引擎（vLLM/SGLang）已经知道每个请求的剩余 token，只需把"逐请求进度"上报给路由器（而不是只上报聚合值）。
  • 跨副本同步：多实例路由（llm-d active-active、SMG mesh）下，逐请求队列的同步比聚合值更难——这是 llm-d active-active 下"前缀缓存分区"问题的放大版。可能需要接受"最终一致的逐请求队列"（短暂分歧可接受，像 Dynamo 那样）。
  • SJF 的公平性：短请求插队会让长请求饿死，必须配 aging（QUARTZ 的 λ·a_r 项）——这个 QUARTZ 已经给了现成解法。
  • prefill 吞吐不是常数：不同请求的 prefill 吞吐受 batch 组成影响，用常数 prefill_throughput_i 是近似。可以用离线 profile 的 lookup table（Libra 的做法）修正。

待验证的开放问题

  • W_i(r) 的精确收益有多大？ 相比 llm-d 的聚合 inflight token，逐请求 W_i(r) 能再降多少 TTFT？需要实测——一个合理的预期是：在"长 prefill + 短请求混合"的负载下收益最大（因为聚合指标在这种负载下最误导）。
  • SJF 重排 vs FIFO：路由层允许重排（SJF）的收益，是否足以抵消重排的公平性代价和实现复杂度？QUARTZ 在准入层的答案是"值得"，路由层是否同样成立待验证。
  • 和 KV 命中的交互：c_r 已经扣掉了 KV 命中（= 需新算的 token），但 KV 命中还会影响"队列里其他请求的成本"（如果新请求的 prefill 会改变 KV 状态）。这个二阶效应是否需要建模？

一句话总结

完整的 gap 是「双重粗粒度」：度量层面用聚合值（看不到队列组成），决策层面用标量（丢失 prefill/decode 两个瓶颈各自的饱和度）。
对应的解是两半：① 度量细粒度——逐请求队列 W_i(r)，选等待最短的实例（SJF + aging 是钥匙，QUARTZ 已在准入做了、路由层还没做）；② 维度细粒度——瓶颈向量 (P_i, D_i) × 冲击向量 (c_r, m_r)，选在两个维度上都最有余量的实例。
