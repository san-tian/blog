QUARTZ 论文讲解

ACL 2026 Findings · Quantile-Aware Routing and Queueing for TTFT SLOs · 修改 SGLang router 实现

一句话

面向 TTFT 尾部 SLO 的分位感知路由 + 排队：用分位（而非点估计）预测 prefill 服务时间，同时覆盖「实例间路由（选 worker）」和「实例内准入（排顺序）」两层，对齐 P95/P99 SLO 并保持公平性。

来源：ACL Anthology

核心洞察：尾部 SLO 是分位目标，要用分位预测

尾部 TTFT 的相当一部分在 GPU 执行之前、在 router 队列里就被决定了——size-unaware 的准入会让长请求过早准入，堵塞后面的短请求（队头阻塞），放大尾延迟。

为什么用分位而非点估计：SLO 是分位目标（P99 TTFT < 2s）。点估计（均值）会系统性低估长请求——一个实际 5000ms 的长请求被均值估成 590ms，看起来"不算长"，被过早准入，堵塞后面所有短请求。用保守的高分位（α=0.95）预测，长请求会被正确延后。

四组件架构

组件作用
分位预测器轻量决策树 + pinball loss，预测 prefill 的 α∈{0.9, 0.95} 条件分位（默认 α=0.95）
分位感知路由实例间：K=2 候选（power-of-two）+ 三成分打分，选预测尾部完成时间最小的 worker
分位感知准入实例内：准入队列按 成本+aging+token公平 排序派发
鲁棒性监控残差、轻量校准、负载漂移下回退安全基线（FIFO + least-loaded）

分位预测器：输入特征

  • 请求侧：prompt length、max new tokens、decoding 参数、request type。
  • 局部性：prefix-locality proxy（命中多少缓存前缀）、LPM 长度（最长前缀匹配）、locality bucket（none/partial/high 三档）。
  • worker 侧：active sequences、prefill backlog、KV 压力。

输出：Q̂_prefill_α(r,w)——请求 r 在 worker w 上 prefill 成本的 α 分位。

阶段一：实例间路由（选 worker）

S_α(r,w) = Ŵ(w) + Q̂_prefill_α(r,w) + ψ(r,w)
  • Ŵ(w)：已排队请求的期望工作量（用均值，分位不能直接相加）。
  • Q̂_prefill_α(r,w)：当前请求自己的 prefill α 分位（用分位，点估计会低估长请求）。
  • ψ(r,w)：KV 压力等不健康状态的惩罚。
  • K=2 候选：先随机抽 2 个候选，再在其中用完整分数选最优（power-of-two-choices，O(2) 开销接近全局最优，且随机性避免羊群效应）。

阶段二：实例内准入（排顺序）

k(r)      = Q̂_prefill_α(r,w) + λ·a_r      # 成本 + aging
k_fair(r) = k(r) + β·u(c(r))            # 再 + token 公平
  • Q̂_prefill_α：成本小的先派（类 SJF），减少队头阻塞。
  • λ·a_r（aging）：到达越早 key 越小，防长请求饿死。
  • β·u(c)（token 公平）：已用 token 越多 key 越大，防单 client 垄断。
  • 容量可用时 pop 最小 key 派发。

这一层是 QUARTZ 独有的：Lodestar 选完 worker 就直接交给 vLLM 的 FCFS 队列了；QUARTZ 额外控制"何时派发"。

和实例间/实例内调度的关系

QUARTZ 恰好同时覆盖两层：阶段一是实例间路由（选 worker），阶段二是实例内准入（排顺序）。这正是它名字"Routing and Queueing"的含义——所以它在全景调研里归「实例间调度」（A 类），但它的准入队列部分已经是实例内调度的范畴。

默认参数

分位水平 α=0.95、候选数 K=2、aging λ=0.02、公平 β=0.10、回退阈值 δ=0.05。
