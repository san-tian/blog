维度详解：四个关注点的关键差异

① 多实例 HA / 状态同步 —— 谁真正解决了「路由状态跨实例一致」

这是四个维度里分歧最大的。核心矛盾：KV cache 状态是路由决策的输入，但多实例路由时每个实例看到的状态必须一致，否则会做出冲突的路由决策（比如两个 router 都把请求派给同一个"看起来最闲"的 worker）。各家解法分三档：

  • 最强（SMG）：SWIM gossip + CRDT 同步了包括 cache-aware routing tree 在内的全量路由状态——这是唯一把「KV 路由树」本身纳入跨实例同步的方案，3/5 节点容忍 1/2 节点故障。
  • 事件驱动收敛（Dynamo / llm-d / Ray Serve）：Dynamo 的 selection service 用 ZMQ 同步 admission/prefill-complete 事件（output-block 故意不同步省带宽）；llm-d 的 KV indexer 在 pod-discovery 模式下每个 EPP 副本独立订阅每个 pod 的全量 KV 事件，各自收敛到同一索引（这是事件源的天然一致性）；Ray Serve 的 ingress 副本异步同步 token 负载。三者都是「最终一致」，短暂分歧可接受。
  • 有限（SGLang Router / Lodestar）：引擎内嵌或单实例 gateway，没有跨实例路由状态同步——多实例部署时各自独立，cache 命中会退化。

llm-d 的 active-active 模式有明确警告：禁用 leader 选举后，只能用「动态查询后端」的插件（queue depth、KV utilization），不能用 approximate prefix 缓存插件——因为副本不共享本地内存，前缀路由会分区。但它的 KV-Cache Indexer 用 pod-discovery 模式解决了这个问题（每副本独立订阅全量事件）。

② SGLang KV event 感知 —— 谁在做「块级精确」而非「前缀近似」

「读 KV event」和「前缀文本匹配」是两种完全不同的 cache hit 感知精度：KV event 是块级精确（引擎真实缓存了什么块，含分层 GPU/CPU、驱逐事件），前缀匹配是文本近似（猜引擎可能缓存了什么前缀，不感知驱逐）。

  • 块级精确（Dynamo / llm-d）：两者都订阅 vLLM 和 SGLang 的 ZMQ KV 事件（BlockStored/BlockRemoved/AllBlocksCleared），维护块级索引。llm-d 还支持 multimodal hash、LoRA、分层权重（gpu=1.0/cpu=0.8）、speculative indexing（路由后插入预测条目防背靠背同前缀的亲和断裂）。
  • 前缀近似（SMG / AIBrix / Lodestar）：维护 radix 树/前缀索引，匹配的是文本前缀，不感知引擎实际缓存状态和驱逐——高并发或长运行下视图会过时。
  • 引擎原生（SGLang Router）：SGLang 自己的 RadixAttention，引擎内部前缀复用（但这是引擎内，不是跨实例的 KV event）。
  • 受限（Ray Serve LLM）：KVAwareRouter 的 KV 事件是 vLLM-native；SGLang 引擎能跑（server_cls=SGLangServer），但社区支持早期，且 engine replicas / KV 利用率等 SGLang 特性尚未集成。

③ K8s / Ray 依赖 —— 能否脱离编排框架独立跑

  • 零依赖（Dynamo / SMG / SGLang Router）：引擎无关、纯进程内或独立二进制，K8s 只是可选的部署方式。下游推理服务也引擎无关（Dynamo/SMG 接 vLLM/SGLang/TRT-LLM；SMG 还接云 API）。
  • 强绑定 K8s（llm-d / AIBrix / Lodestar）：llm-d 依赖 Gateway API InferencePool，AIBrix/Lodestar 依赖 K8s pod 模型，下游推理服务必须跑在 K8s pod。
  • 强绑定 Ray（Ray Serve LLM）：路由和下游引擎都在 Ray Serve 部署模型内。

④ 调度方式 —— 谁在「cache hit + 负载」双目标上做得最干净

所有 gateway 都声称"同时考虑缓存和负载"，但实现质量差很多。结合学术论文（见下），可以把双目标组合分成四类范式：

范式代表机制是否需要调参
加权求和（线性组合）Dynamo（cache-credit）、llm-d 旧默认、AIBrix、vLLM Routerscore = α·KV 命中 + β·负载，权重手调⚠️ 需逐负载调参（LMetric 论文明确指出其缺点）
阈值过滤 + 择优llm-d sticky-until-saturated先过滤过载实例，再在剩余里选缓存最优；阈值 τ 可推导✅ τ = R_peak × T_max 闭式得出

关键洞察：学术界的「乘法/阈值/学习」三范式，正是对工业界「加权求和」缺陷的回应。 LMetric 论文系统性地否定了「加权求和」（需逐负载调参）和「filter 策略」（偏向负载、无法充分利用缓存）， 提出乘法路由作为零调参解；llm-d 的 sticky-until-saturated 用「阈值可推导」实现类似目标； Lodestar 用在线学习绕开手工规则。三者殊途同归：都在解决「如何同时均衡 cache hit 和负载」这个同一个问题。

结论：按你的四个关注点选型

  • 要「多实例 + 状态同步」最强 → SMG（SWIM+CRDT 同步了 cache-aware 路由树）；次选 Dynamo / llm-d（事件驱动最终一致）。
  • 要「SGLang KV event 块级感知」 → Dynamo 或 llm-d（都订阅 SGLang 的 ZMQ KV 事件）；SGLang Router 是引擎原生但仅限引擎内。
  • 要「脱离 K8s/Ray 独立跑」 → Dynamo / SMG / SGLang Router（引擎无关、零编排依赖）。
  • 要「cache hit + 负载均衡」最干净 → 学术上是 LMetric 乘法路由（零调参）；工业落地是 llm-d sticky-until-saturated（阈值可推导） 或 Dynamo（cache-credit 打分）。
横向结论：没有单一 gateway 在四维度全占优。Dynamo 和 llm-d 在「块级 KV 感知 + 调度质量」上最接近你的研究主线； SMG 在「多实例 HA 同步」上最完整但 KV 感知停留在前缀级；SGLang Router 零依赖但单实例、无跨实例同步。 若你的目标是「同时均衡 cache hit 和负载」且要生产可推导，llm-d 的 sticky-until-saturated 是当前工业侧最贴合的实现（对应你已精读的博客）。
