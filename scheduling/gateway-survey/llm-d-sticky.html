Sticky Until Saturated：llm-d 的 Token 感知路由

3 个场景（工作负载） 2 个瓶颈 2 个匹配配置

原文：llm-d.ai/blog/sticky-until-saturated-token-aware-routing

一句话：路由派活时先「认缓存」（快），但别让一台机器累死——忙到阈值 τ 就果断改派； 阈值靠一次硬件校准算出来，不靠拍脑袋。

博客真正的「场景」是三个工作负载（code-generation / reasoning / b2b-saas），只用两个匹配配置来路由。 本文按三个场景逐一讲解各自应用哪个配置、怎么路由；每个计算第一次出现时详细展开。

前置：三个场景怎么落到「两个配置」

三个场景都在回答「请求来了发哪台机器」，但瓶颈不同 → 用的配置不同。先交代两个背景。

地图一：路由器的三段式流水线（配置的骨架）

1
Filter 过滤器硬性筛掉一部分端点，得到候选集（管「缓存亲和性」）
▼
2
Scorer 评分器给候选集每个端点打分（管「负载」，分数越低越优先）
▼
3
Picker 选择器按分数挑出最终目的地

两个匹配配置都套这个骨架，区别只在第二步的 scorer：场景 1、3 用 token-load-scorer，场景 2 用 active-request-scorer。

地图二：两个瓶颈 → 决定用哪个 scorer

阶段干什么受什么限制对应场景
Prefill读 prompt，算成 KV 缓存GPU 算力（注意力 O(n²)）场景 1、3
Decode逐个吐输出 tokenKV-cache 内存 + decode 槽位场景 2

判据：prompt 与输出 token 的比例。prompt 长输出短 → prefill 受限（用 token-load）；prompt 短输出长 → decode 受限（用 active-request）。

为什么三个场景需要不同的路由策略（信号要匹配瓶颈）

三个场景用到的其实是两个策略：code-gen 和 b2b-saas 共用 token-load，只有 reasoning 换 active-request。为什么要分两个？因为瓶颈不同，「负载」的度量单位就不同——调度器要「把请求发给最不忙的端点」，但「忙」在两种瓶颈下是两回事。

根源：两个瓶颈的物理本质不同

prefill（算输入）decode（吐字）
受限类型compute-bound（GPU 算力）memory/slot-bound（KV-cache 内存 + 槽位）
每步干什么一次迭代处理一个 chunk（8192 token），token 越多算得越久每步每个请求只吐 1 个 token，但要读整个 KV cache
压力随什么增长token 数（prompt 越长越忙）请求数（并发流越多越忙）
「忙」的正确单位token（未缓存的）请求 / 流（活跃的）

实验结果：信号匹配瓶颈的配置才赢

三个场景的实测结果一致指向同一个结论——信号对上路，配置才赢：

场景瓶颈（单位）胜出的信号实测结果
code-generationprefill（token）token-load（在途未缓存 token 数）TTFT-p90 最低、输入吞吐最高（46k vs k8 16k in_t/s，2.9×）；k8 和 legacy blend 在多个并发点悬崖式失效
reasoningdecode（请求数）active-request（活跃请求数）TPOT-p90 最低、输出吞吐最高；token-load 有竞争力但未超过它；legacy blend 的前缀加权在 50 以上每个并发都受损
b2b-saasprefill（token）token-load（同 code-gen）维持高命中率（90–95%）与高吞吐（90k vs k8 45k，2.0×）；印证瓶颈相同则配置共用

注意 reasoning 这一行的对照：同样是 token-load 配置，在 prefill 场景（code-gen）赢，在 decode 场景（reasoning）却没能超过 active-request——这正是「信号必须匹配瓶颈」最直接的实验证据。

为什么 code-gen 和 b2b-saas 能共用 token-load

因为瓶颈相同——两者都是 prefill 受限，「忙」的单位都是「未缓存 token」。区别只在缓存动态（b2b-saas 是固定小语料反复循环的病态缓存），但度量单位没变，所以同一套 token-load 直接复用、参数都不改。

一句话总结：瓶颈决定「负载用什么单位度量」——prefill 受限用 token、decode 受限用请求。三个场景的实测结果都印证了这一点：信号对上路、配置才赢——不是策略越多越好，而是信号要匹配瓶颈。
1

场景 1：code-generation —— 应用 token-load 配置 prefill 受限

prefix-cache-affinity-filter (0.8, τ=286720) → token-load-scorer → max-score-picker

工作负载特征：长 prompt（均值 70k token，随对话轮次增长）、中等输出（均值 800）、无跨请求前缀重叠（每个对话的 prompt 唯一，缓存命中只来自对话内部的轮次连续性）。瓶颈 = 每端点 prefill 计算。

应用逻辑：因为瓶颈在「算输入」，所以 scorer 用「在途未缓存 token 数」这个信号。下面逐个展开这个配置里第一次出现的计算。

首次出现亲和性分数（affinity score）——过滤器怎么筛端点

affinity(endpoint) = 已缓存在该端点的 prompt token 数 / prompt 总 token 数

即「前缀缓存命中率」的逐请求版本。例：10000-token prompt，9000 token 的 KV 已缓存在端点 A → affinity(A) = 0.9。

首次出现过滤规则：0.8 阈值

  • affinity ≥ 0.8 的端点 → 进候选集（「缓存已预热」）；
  • 若没有任何端点达标 → 全部放行，评分器在全集上挑（不卡死）；
  • 0.8 在所有用该过滤器的配置里都一样，跨场景不重新配置。

首次出现饱和覆盖 τ —— 粘性什么时候打破

过滤器默认「粘缓存」：亲和性够高就优先发它。但粘过头会形成热点，于是有饱和释放机制：

maxTokensInFlightPenalty = τ

规则：若某非预热端点的「在途未缓存 token 数」比热端点少至少 τ，就把它也加回候选集——「热端点已多积压 τ 个 token 了，放个冷端点分担」。

首次出现τ 的推导（从硬件算出来）

R_peak = B / T(B)          # 峰值 prefill 吞吐
τ_sat  = R_peak × T_max    # = (B × T_max) / T(B)
  • B = max-num-batched-tokens = 8192（vLLM 配置：一个 prefill chunk 的容量）；
  • T(B) = 实测 prefill 一个满载 chunk 的墙钟时间（一次校准测量）；
  • T_max = 运维自定的 TTFT 退化容忍上限（本文 14s）。

代入实测：T(8192)=0.40s → R_peak = 8192/0.40 = 20480 tok/s → τ = 20480 × 14 = 286720。

τ = 286720 / 8192 = 35 个 chunk   # 等价于 35 × 0.40s = 14s 排队时间
τ 不能移植：R_peak 是完整服务路径的属性，不是加速器的属性（gpt-oss-120B 39k、Qwen3-32B/H100 20k、Qwen3-VL/H200 15.7k tok/s）。同是 H100：286720 挪到 gpt-oss-120B 会偏低 1.9 倍（阀过早触发、白丢缓存），挪到 Qwen3-VL/H200 会偏高 1.3 倍（阀迟到、排队超 SLO）。公式可移植，常量不可移植，换硬件必须重测。

首次出现lookahead 评分公式 —— token-load-scorer 怎么打分

score(endpoint) = current_uncached_in_flight(endpoint)
                + prompt_tokens × (1 − hit_rate(endpoint))
项含义例子（新请求 prompt=10000）
current_uncached_in_flight端点当前积压的、还没 prefill 完的、没命中缓存的 token 总数端点 A 积压 50000
hit_rate(endpoint)新请求 prompt 里已缓存的比例（= affinity）端点 A 命中 90%
prompt_tokens × (1−hit_rate)该请求若发过去会新增的未缓存工作量10000 × 0.1 = 1000

于是 score(A) = 50000 + 1000 = 51000。取 score 最小 = 「发过去后总 prefill 积压最少的端点」。只算「未缓存」是因为已缓存的 token 直接读 KV cache、不用重算。

首次出现in-flight 记账

流式下（addEstimatedOutputTokens=false），请求 token 在第一个 chunk 返回时即释放——prefill 一完成就不再占 prefill 算力。所以计数器精确反映「还有多少 prefill 活儿在排队」。

场景 1 完整走一遍：请求进来 → ① 算各端点亲和性，≥0.8 进候选集；② 检查饱和：某冷端点比热端点少积压 ≥ τ=286720 就也加入；③ token-load-scorer 打分（积压 + 新增）；④ max-score-picker 选分数最小。没饱和就粘缓存白赚加速，饱和了就果断改派冷端点。
2

场景 2：reasoning —— 应用 active-request 配置 decode 受限

prefix-cache-affinity-filter (0.8, τ=286720) → active-request-scorer → max-score-picker

工作负载特征：短 prompt（均值 1000 token）、长输出（均值 8000，最大 32k）、250-token 共享系统 prompt。瓶颈 = decode 槽位（并发流数把 KV-cache 撑满）。

应用逻辑：瓶颈从「算输入」变成「吐字」，所以把 scorer 换成 active-request-scorer，过滤器完全复用场景 1 的。

首次出现active-request-scorer —— 活跃请求数信号

score(endpoint) = 该端点当前活跃请求（流）数

取最少的。为什么用「个数」不用「token 数」？decode 是内存/槽位受限：每个活跃请求都占一块 KV-cache 空间和一个 decode 槽位，压力随并发请求数增长，而非请求规模。

首次出现亲和性过滤器在这里是「空操作」

场景 2 前缀太短（250-token 系统 prompt 对 1000-token 用户 prompt，亲和性最多 0.25），永远到不了 0.8 → 过滤器把所有端点放行，评分器在全集上挑活跃流最少的。所以这个场景实际等价于「纯按活跃请求数均衡」，但代码里仍挂着同一个过滤器、无需改配置。

场景 2 完整走一遍：请求进来 → ① 亲和性过滤（空操作，全放行）→ ② active-request-scorer 数各端点活跃流 → ③ max-score-picker 选最少的。信号直指 decode 瓶颈，所以在这个负载上它最优。
3

场景 3：b2b-saas —— 复用 token-load 配置 prefill 受限（病态缓存）

prefix-cache-affinity-filter (0.8, τ=286720) → token-load-scorer → max-score-picker（与场景 1 相同）

工作负载特征：7200-token prompt（6000 系统 + 1200 问题）、1000-token 输出、固定 150 个系统 prompt × 5 变体反复循环。瓶颈同样是 prefill 计算，但多了一个病态缓存动态——聚合可缓存内容（约 900k token）超过集群总 KV 容量。

应用逻辑：瓶颈和场景 1 一样（prefill），所以直接复用 token-load 配置，参数都不改。这印证了博客的主张——「同一配置覆盖典型（code-gen）和病态（b2b-saas）两种 prefill 受限情形」。

首次出现缓存分区 / 双稳态（这个场景特有的现象）

集群会随 τ 收敛到两种截然不同的稳态：

  • 稳定分区：每个端点拥有 150 个前缀的一个子集，重复请求本地命中，命中率 ~90–95%；
  • 驱逐抖动：每个端点都试图缓存所有前缀，互相驱逐，命中率崩盘。

两者之间无平滑过渡，τ 的微小变化可能让集群从一个状态翻转到另一个。所以作者明确：不用 b2b-saas 来声称精确最优 τ（τ 靠场景 1 的公式算），它只是用来验证 τ 作为「饱和阀」起作用。

场景 3 完整走一遍：和场景 1 完全相同——粘缓存直到热端点积压比冷端点多 ≥ τ=286720 才放手。区别在于：QPS 50+ 时热端点积压足够大、饱和阀频繁触发，命中率短暂从 96% 掉到 70%——这正是 τ 在「重新分配流量」的证据（而 legacy blend 没有这个阀，命中率一直死撑 96% 却让热点更严重）。

为什么剩下三个配置没被采用

五个配置里只有两个匹配配置被应用，剩下三个不是「忘了用」，而是各有定位——本文三个场景都是「单一、已知瓶颈」的负载，匹配配置正是为「单一瓶颈」设计的：

配置定位为什么没被选为这三个场景的匹配配置
k8无调度器基线根本不做路由决策（纯轮询），只是「最差参照物」，让 2~3 倍提升有对比对象
legacy blend旧默认（四信号加权）难预测、难调优，code-gen 上悬崖式失效；唯一赢处（b2b-saas）靠的是「为重复语料聊天流量专门调优」的权重，不是通用能力
latency-predictor通用替代（预测 TTFT）对付的是「瓶颈漂移」，三个场景都坐落在单一瓶颈、用不上；且有 sidecar 开销、实测也未超过匹配配置

① k8：不是路由策略，是基线

它只是 Kubernetes 轮询、完全绕过路由器，压根不做路由决策。存在意义就是当「最差情况」的标尺——匹配配置在 prefill 场景的 2~3 倍吞吐，正是相对它算出来的。

② legacy blend：被替换，因为「不可预测」

文章开头点出它两个致命问题：四信号加权混合的涌现行为难预测、更难调优；没有硬性过滤器 = 没有「什么时候放弃缓存」的开关，在 code-gen 上出现悬崖式失效。它唯一赢的地方（b2b-saas 的 TTFT-p90 最低）恰恰暴露了问题——那是权重专门为「重复语料聊天流量」调优的结果：赢了它自己设计的目标负载，换个负载就不行。token-load 取代它，要的是「跨负载可预测、可推导」，而不是「单一负载的最佳」。

③ latency-predictor：为「瓶颈漂移」准备的，三个场景用不上

它预测每个端点 TTFT、理论上无需「识别瓶颈」。但它有额外开销（预测器训练 + sidecar 部署），而且本文三个场景各自坐落在单一瓶颈机制（code-gen / b2b-saas 纯 prefill、reasoning 纯 decode），根本没有「瓶颈漂移」需要它来应对。实测也没超过匹配配置：code-gen 上比 token-load 差约 10s TTFT，reasoning 饱和时才持平，b2b-saas 达不到。作者明确保留它——在混合/高方差、瓶颈动态漂移的生产流量上它可能占优，只是本文未测。

这背后是文章的取舍：legacy blend = 「为单一负载定制调优」（自己负载上最好，但不可移植）；latency-predictor = 「通用但昂贵」（适合瓶颈漂移，但有 sidecar 开销）；匹配配置 = 「可预测 + 可推导 + 可移植」的折中。三个基准场景都是单一瓶颈 → 匹配配置正好够用且最优 → 所以只需要两个匹配配置，其余三个要么是基线、要么是为别的场景准备的。

具体 infra 实现

blog 给的是架构粒度；具体 configmap / workload YAML / 完整结果表都在附录 GitHub 链接里（feature 分支），不在正文。

硬件与服务栈

  • 模型服务器：10× Qwen3-32B（b2b-saas 压测用 8×），引擎 vLLM。
  • 并行：每台 TP=2，跑在专用 GKE 节点的 2× H100 GPU 上。
  • vLLM 关键配置：max-num-batched-tokens=8192 + continuous batching。

Kubernetes 编排层

  • 每个模型服务器 = 一个 pod；前端是 Gateway API 的 InferencePool，把流量汇入路由器再分发。
  • 「端点 endpoint」是逻辑概念：本文部署里 = 一个 pod，多节点部署可横跨多个 pod。

路由器插件清单（正文提到的）

  • Filter：prefix-cache-affinity-filter
  • Scorer：token-load、active-request、latency、prefix-cache、queue、kv-cache-utilization、no-hit-lru
  • Picker：max-score-picker、weighted-random-picker
  • 辅助：in-flight load producer、多模态 token-producer（按分辨率估图像 token）

负载生成、指标与校准

  • 负载生成：inference-perf（kubernetes-sigs 标准化压测工具）。
  • 指标：TTFT、TPOT、端到端延迟、吞吐、成功率、队列深度、KV 利用率、前缀命中率 → 导出 GCS JSON 聚合分析。
  • 校准：calibrate.sh 报告 peakPrefillThroughput = CHUNK_SIZE / median(TTFT)；configuration-matrix.md 记录按 (模型, 加速器, 引擎) 的实测 R_peak。

生产部署形态

  • 已在 Vertex AI / Red Hat / Mistral 生产集群运行。
  • 各指南：optimized-baseline（token-load 为默认）、agentic-serving（prefill 匹配配置）、multimodal-serving（affinityThreshold 0.8→0.6、T_max 18s→36s）、P/D-disaggregation（prefill 池用 token-load + decode 池用 active-request）。

值得借鉴与存疑

值得借鉴

  • 「一个正确信号 + 一个校准阈值」>「一堆加权信号」
  • 阈值可推导，以硬件可测量为锚
  • 组合性设计：filter/scorer 解耦，配置空间极小
  • 诚实区分「结构性配置」与「经验调参」

存疑 / 未覆盖

  • 瓶颈漂移的混合流量未实测
  • 匹配配置常量也会随负载漂移（多模态 0.8→0.6）
  • T_max 仍是主观选择（14s/18s 无严格依据）
  • 单次运行、b2b 双模态导致绝对数值不稳

一句话总结

三个场景、两个瓶颈、两个匹配配置：识别瓶颈 → 部署对应配置 → 先粘缓存、饱和即放；阈值 τ = 峰值 prefill 吞吐 × TTFT 容忍上限，由一次硬件校准闭式得出——公式可移植，常量必须重测。
