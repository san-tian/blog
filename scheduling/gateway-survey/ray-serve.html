Ray Serve LLM（KVAwareRouter）功能实现讲解

Ray 生态的 LLM 服务层（Python）。能力标注：✅ 块级KV感知✅ 前缀缓存感知✅ Token负载感知✅ 多实例HA✅ SLA自动扩缩⚠️ 多后端

块级 KV 感知 —— KVAwareRouter 怎么实现

KVAwareRouter 摄取引擎的 KV 块创建/驱逐事件，构建全局 KV radix 树。关键分工：Ray Serve 负责事件面/请求面/数据面，NVIDIA Dynamo 的 KV indexer（进程内库）消费事件、在块级算每个请求的前缀重叠。

  • vLLM 原生发 KV 事件（块创建/移除），Ray Serve 转发给 KVAwareRouter，广播到所有 ingress 副本。
  • 注意：文档写明 KV 事件是 vLLM-native；SGLang 引擎能跑（server_cls=SGLangServer），但社区支持早期。
来源：kv-aware-routing 文档（"Each replica reports KV block creation and eviction through vLLM-native KV events"）

Token 负载感知 —— cache-credit 打分

KVAwareRouter 用 KV 重叠度估算剩余 prefill 负载，再叠加活跃 decode 负载，合成 token 负载，选最低的副本。Dynamo selection service 负责打分，权重可调：

  • DYN_ROUTER_PREFILL_LOAD_SCALE（1.0）：prefill 项相对 decode 的权重。
  • DYN_ROUTER_KV_OVERLAP_SCORE_CREDIT（1.0）：GPU 驻留 KV 重叠能扣多少 prefill 成本（设 0 = 纯负载路由）。
  • GPU 驻留块全额信用，offload 到 CPU 的块打折。
来源：kv-aware-routing 文档（"How a replica is chosen" / "Tune the scoring weights"）

前缀缓存感知 —— PrefixCacheAffinityRouter

除 KVAwareRouter 外，Ray Serve LLM 还提供 PrefixCacheAffinityRouter（基于请求文本的前缀树）和 ConsistentHashRouter（会话亲和）。前缀树是文本近似，不感知驱逐——这是"前缀级"的兜底/简化方案。

来源：kv-aware-routing 文档（路由策略对比表）

多实例 HA —— ingress 副本 + 最终一致

路由器被复制成多个 ingress 副本，各自本地做路由决策，token 负载更新异步共享，最终收敛。文档明确：视图是 "eventually consistent"——某副本可能短暂基于稍旧视图决策，换取"路由不阻塞在同步路径"。

来源：kv-aware-routing 文档（"Scaling the ingress tier"）

SLA 自动扩缩 + 多后端

  • 自动扩缩：Ray Serve 的 autoscaling（autoscaling_config，min/max replicas、target_ongoing_requests）。
  • 多后端（⚠️）：vLLM 为主；SGLang 通过 server_cls=SGLangServer 支持，但明确"community support, early development"，且 engine replicas、KV 利用率等 SGLang 特性尚未集成。
来源：Ray Serve SGLang 文档（"Community SGLang support is in early development" / Limitations）

小结

Ray Serve LLM 的 KVAwareRouter 是「块级 KV 事件 + Dynamo radix 树 + token 负载打分」的组合，正是 Anyscale 博客（你已精读）的落地。它强绑定 Ray 集群，多后端以 vLLM 为主、SGLang 早期。
