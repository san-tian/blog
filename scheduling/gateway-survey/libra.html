Libra 论文讲解

NSDI 2026 · Flexible Request Partitioning and Scheduling for Serving Unbalanced and Dynamic LLM Workloads · NUS + USTC

一句话

提出 FPS（Flexible Partition and Scheduling）范式：把请求在任意 token 边界切分成 micro-request，两级调度（全局选切分点 + 本地 SLO 感知组批），把 PD 共置和 PD 分离统一进一个更灵活的空间，动态适应不平衡负载。

来源：NSDI 26 PDF

问题：共置 vs 分离的两难

LLM 推理分 prefill（计算密集）和 decode（内存受限）两阶段。真实负载的 prompt/response 长度高度动态，导致两阶段负载失衡：

  • PD 共置（colocation）：prefill/decode 同实例，吞吐高但互相干扰——长 prefill 阻塞 decode，P99 TBT 尾延迟爆表（实测 352ms，SLO 达成率低至 1.73%）。chunked prefill 只能粗粒度缓解，chunk size 是敏感超参。
  • PD 分离（disaggregation）：prefill/decode 分池，SLO 稳定但资源碎片化——固定 1P:1D 划分在 prefill-heavy 负载下 decode GPU 几乎闲置（MFU 0.19%）。

核心洞察：任何静态分区对动态负载都必然次优。

核心抽象：micro-request（FPS）

每个请求有 prompt 长度 P 和（预测的）decode 长度 D，总逻辑长度 L = P + D。在切分点 s ∈ [0, L] 把请求切成两个 micro-request：r_α（tokens 1..s）和 r_β（tokens s+1..L）。

  • s = 0 或 s = L → 无分区（即 colocation）
  • s = P → 在 prompt 末尾切（即 PD 分离）
  • 任意 s → 混合切分（如把部分 decode 并进 prefill 段，或把部分 prefill 搬到另一 GPU 与 decode 并跑）

所以 colocation 和 disaggregation 都是 FPS 的特例——FPS 在更广的切分空间里动态找最优。

两级调度框架

① 全局调度器：选切分点 + 路由

  • 对每个请求，二分搜索 partition ratio φ ∈ [0,1]（最多 K=6 次迭代），用轻量 cost model 预测两个服务器上的执行时间 T1、T2，平衡到 |T1 − T2| < ε。
  • 吞吐均衡约束：平衡两个 GPU 的吞吐，消除"木桶效应"（不平衡时快的一端空等慢的一端）。
  • 预测器：offline-profiled lookup table + LRU cache，每次 probe 微秒级；O(1) per-request 复杂度。
  • 路由：least-loaded 策略（r_α、r_β 分到负载最低的两个实例，round-robin 破平局）。

② 本地调度器：SLO-aware 组批

  • 每个 GPU 实例动态组 batch，调三个因素：batch size、prefill-to-decode token ratio、decode context length，在 P99 TBT SLO 下维持高利用率。
  • 流程：先纳入所有 decode 请求（延迟关键），再根据 profile table 决定最大 prefill token 预算 M，贪心加 prefill 请求。
  • profile table 用每批实测延迟（plen, ctx, dnum, time）持续校准。

③ chunk-based KV transfer

  • micro-request 跨实例执行时，KV cache 按 chunk 粒度传输（append-only，chunk 完成立即 DMA push 到对端），重叠通信与计算（RDMA/NCCL/Mooncake）。

扩展：多切分（multi-split）

FPS 自然推广到多段切分。例如 CoT 请求切成 prefill / think / decode 三段——think 阶段非用户可见，可用宽松 SLO，做更激进的负载均衡而不牺牲最终输出延迟。

效果

  • goodput 提升 up to 1.91×（vs PD 共置）、1.61×（vs PD 分离）；serving capacity 1.15–3.07×。
  • hybrid workload 下比不对称基线（TP/DP 优化）再提 74.2%；H100 严格 SLO 下 goodput 提升 up to 134%。
  • 实现：基于 vLLM（4K 行 Python），Qwen-2.5 14B/32B/72B，A100/H100。
  • 对 decode 长度预测误差不敏感（决策基于相对执行时间，非精确 token 数；保守 20 token 安全余量）。

和你研究主线的区别（重要）

Libra 的核心是「请求切分」（在任意 token 边界切请求）而非「实例间 KV 感知路由」——它不按 KV cache 命中选实例，而是按吞吐均衡切分请求、平衡两阶段的 GPU 负载。它是 PD 分离/共置之上的请求级调度范式，解决的是"prefill 和 decode 负载不平衡"问题，不是"哪个实例缓存了这个前缀"问题。所以它在全景调研里归「实例间调度」的边缘（有全局调度器路由 micro-request，但核心机制是切分而非 KV 路由）。
