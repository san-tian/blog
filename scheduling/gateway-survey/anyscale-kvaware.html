Ray Serve LLM 路由策略讲解：KVAwareRouter 的 Token 负载感知

KVAwareRouter NVIDIA Dynamo selection service vLLM KV 块事件 全局 radix 树

一句话：路由时别再只盯「能省多少 prefill」（KV 缓存命中），要盯「每台副本还欠多少活」（token 负载）。 KV 缓存重叠度从「路由目标」降级为「估算负载的输入」，请求始终发给 token 负载最低 的副本。
原文：anyscale.com/blog/llm-kv-token-aware-routing ｜ 文档：docs.ray.io/.../kv-aware-routing

总览：一个请求进来，走 3 步

1
ingress 侧 tokenize用与引擎相同的 chat 模板把 prompt 切成 token ID（打分基于 token）
▶
2
Dynamo 打分对每个候选副本估算 token 负载 = 剩余 prefill + 活跃 decode
▶
3
选最低者把请求发给 token 负载最低的副本（而非 KV 命中率最高者）

核心公式（一张图看懂）

token_load(replica) = PREFILL_LOAD_SCALE × prefill_load + decode_load

prefill_load = 活跃 prefill token  +  本请求未缓存的输入 token  −  KV 重叠信用   # 计算受限项
decode_load  = 活跃解码 KV 块占用  ×  按 max_tokens 估算的剩余输出        # 内存受限项

路由决策：选 token_load 最低的副本

每个变量是什么

变量是什么从哪来 / 怎么算单位
token_load(replica) 副本 r 的总 token 负载，也就是路由打分值 = PREFILL_LOAD_SCALE × prefill_load + decode_load；选最小的副本 token（折算）
PREFILL_LOAD_SCALE prefill 项相对 decode 项的权重系数 运维可调，对应 DYN_ROUTER_PREFILL_LOAD_SCALE，默认 1.0 无量纲
prefill_load 计算受限项：该副本在 prefill 上还欠多少活 = 活跃 prefill + 本请求未缓存输入 − KV 重叠信用（见下方拆解） token
decode_load 内存受限项：该副本在 decode 上还扛着多少 KV 内存 = 活跃解码 KV 块 × 估算剩余输出（见下方拆解） KV 块（折算）

prefill_load 的三项拆开看

活跃 prefill + 未缓存输入 − KV 重叠信用

活跃 prefill token：该副本当前正在算、还没算完的 prefill token 总数（别的请求已经占的坑，接纳时 +1、prefill 完成时 −1）。

本请求未缓存的输入 token：这次新请求的 prompt 里没命中 KV 缓存、必须从头算的部分 = 总输入 token − 命中缓存的 token。

KV 重叠信用：命中缓存能抵扣掉的工作量；GPU 驻留块全额抵扣，offload 到 CPU 的块打折（要先搬回 GPU）。

decode_load 的两项拆开看

活跃解码 KV 块 × 估算剩余输出

活跃解码 KV 块占用：该副本上正在解码的请求累计占用的 KV 块数（每个活跃请求按已生成 token 折算成 KV 块）。

估算的剩余输出：按 max_tokens（请求声明的最大输出 token 上限）估算每个活跃请求还要再生成多少 token，用来衡量「这份 KV 占用还要持续多久」。

⚠️ 这些量都是估算值而非精确值：输出长度在请求接纳时未知（非确定性生成）， 所以 decode 项的「剩余输出」只能按 max_tokens 上限估——这正是博客承认的「非确定性生成是开放问题」。

关键定位反转：KV 缓存重叠度（紫色）只出现在「扣减项」里——它告诉你 prefill 能省下多少， 而不是副本还欠下多少。真正决定路由的是「还欠多少」= 剩余 prefill + 活跃 decode。

核心洞察：KV 缓存重叠度 ≠ 负载

一个请求在两个阶段的实际工作量是不同的：

Prefill：先复用重叠的 KV 缓存 → 再为剩余未缓存 token 计算 KV 缓存    # 计算受限
Decode ：每生成 1 个 token，都要读全部已生成 token 的 KV 缓存 + 一次前向  # 内存受限
量回答的问题性质
KV 缓存重叠度prefill 能省下多少工作「省下的钱」
剩余 prefill 负载prefill 还要做多少工作「要还的债」
活跃 decode 负载还有多少解码 KV 块被占用「要还的债」
重叠度只反映「省下的」，完全没反映「欠下的」。 一个副本缓存命中率可以 100%，但它正扛着 8 个长输出 decode——把新请求塞给它依然是错的。 所以 KVAwareRouter 的定位是：KV 缓存亲和仍是「负载估计的代理」，不是「路由目标本身」。

三种「认缓存」方案，以及它们共同的短板

博客按递进关系介绍三种 KV 缓存亲和方案，越往后「认出缓存」越准，但都共享同一个致命缺陷：只回答了「能省多少」，没回答「还欠多少」。

① 会话亲和 · ConsistentHashRouter

按 session ID 一致性哈希 → 同会话轮次固定到同一副本

复用会话历史 KV，附带会话级负载均衡。
短板：把会话当均匀单位，会话数均衡 ≠ 负载均衡（掉队者会话会打爆副本）。

② 前缀亲和 · PrefixCacheAffinityRouter

维护请求文本前缀树 → 找前缀重叠最大的副本

短板：跟踪字符串而非 token 级 KV 缓存（近似）；不感知驱逐；对 offload 块一视同仁。

③ KV 缓存亲和 · KVAwareRouter（前身）

摄取 vLLM KV 块事件 → 全局 radix 树 → 块级精确重叠

最精确。但若只优化重叠度（PureKVCacheAffinityRouter）→ 请求聚集：全往缓存了系统提示词的副本挤。

三种方案在「认出缓存」上越来越准，但真正的矛盾是：认缓存只是手段，负载才是目标。

别误读成「三种方案 → 第四种方案」： 这三种不是并列候选，而是「最大化 KV 复用」这一种思路下、由粗到精的三种认缓存手段。 作者真正要提的新东西不是第四种认缓存手段，而是换掉路由目标（最大化命中 → 最小化 token 负载）， 而承载新目标的载体，正是最精确的第三种手段（KV 缓存亲和）本身—— KVAwareRouter = KV 缓存亲和（底座，认出缓存）+ token 负载感知（新目标，决定发给谁）。 实验里的 PureKVCacheAffinityRouter 就是人为砍掉 token 负载、只留重叠度的对照版。

路由策略详解：打分函数

（博客正文只给定性描述，精确细节来自官方文档 kv-aware-routing.html，此处合并讲解）

① Prefill 负载（计算受限项）

prefill_load(replica)
  = 该副本当前活跃的 prefill token      # 已经在算的
  + 本请求剩余未缓存的输入 token        # 新来的、算不完还要算的
  − KV 重叠信用                        # 能跳过的那部分

其中「KV 重叠信用」有分层：

  • GPU 驻留的 KV 块 → 全额信用（命中即省）；
  • offload 到 CPU/主存的 KV 块 → 打折信用（要先搬回 GPU，不能算全额命中）。

② Decode 负载（内存受限项）

decode_load(replica) = 活跃解码请求累积的 KV 块占用 × 按 max_tokens 估算的剩余输出

解码每一步都要读全部已生成 token 的 KV 缓存，所以用「KV 块占用 × 剩余输出估计」刻画这份持续开销。

③ 合成分数，选最低者

score(replica) ≈ PREFILL_LOAD_SCALE × prefill_load + decode_load
→ 选 score 最小的副本

完整例子：为什么「全命中缓存」也可能落选

来了一个 2000 token 的请求 r，有 3 个候选副本（设 PREFILL_LOAD_SCALE=1，KV 信用全额、GPU 驻留）：

第 0 步：三个副本的当前状态

副本缓存了 r 的前缀活跃 prefill token活跃 decode KV 块
P11500 / 20003,0008,000
P20（冷实例）00
P32000 / 2000（全命中）9,00025,000

第 1 步：估算每个副本的 token 负载

副本剩余 prefill = 未缓存输入 + 活跃 prefilldecode 负载token 负载
P1(2000−1500) + 3000 = 3,5008,00011,500
P2(2000−0) + 0 = 2,00002,000 ✓ 选中
P3(2000−2000) + 9000 = 9,00025,00034,000
看懂这个例子就懂了 KVAwareRouter：
  • P3 前缀全命中（省下 2000 token prefill），但它正扛着 9000 prefill + 25000 decode，负载最重 → 落选。
  • P2 完全冷（要全算 2000 token），但它空闲，token 负载最低 → 胜出。
  • 这正是「纯 KV 亲和」（选 P3，请求聚集）与「token 负载感知」（选 P2）的分野：省 2000 不如躲开 34000。

可调打分权重（DYN_* 环境变量）

打分由 NVIDIA Dynamo selection service 执行（进程内嵌在 ingress），暴露四个权重，清晰体现「KV 重叠度是可调的负载修正项，而非目标」：

变量默认作用
DYN_ROUTER_PREFILL_LOAD_SCALE1.0prefill 项相对 decode 的整体权重。prefill 密集调高，decode 密集调低
DYN_ROUTER_KV_OVERLAP_SCORE_CREDIT1.0GPU 驻留 KV 重叠能削减多少 prefill 成本。设 0.0 = 完全忽略 KV 复用、纯按负载路由
DYN_ROUTER_KV_OVERLAP_SCORE_CREDIT_DECAY0.0（关）副本 prefill 积压越大越衰减 KV 重叠收益，防止缓存亲和反复偏向忙副本
DYN_ROUTER_DECODE_ACTIVE_REQUEST_WEIGHT0.0（关）给副本已服务的每个请求加一份成本，防止大量小请求挤到同一副本

具体 infra 实现

这套策略背后是一套完整可部署的工程栈（细节来自官方文档）。下面按数据流、职责、同步机制、配置四层拆解。

5.1 总体架构与请求数据流

client ──► HAProxy ──► LLMRouter ingress（tokenize + 打分）
                    │
                    │ 返回选中的副本
                    ▼
client ◄── HAProxy ──► 选中的 LLMServer 引擎副本（direct streaming 回 client）

关键点：打分逻辑跑在 LLMRouter 的 ingress 副本进程内，Dynamo selection service 作为进程内库（in-process）运行，不额外起服务。Ray Serve 负责打分之外的一切编排。

职责内容
Replica discovery跟踪哪些 LLMServer 副本在跑、哪些可接流量，只给可用副本打分
Request orchestrationingress 接收并 tokenize 每个请求 → 选副本 → 派发
Request lifecycle引擎上报 prefill 完成、decode 进度、请求完成，ingress 据此维护 token 负载视图
Event transport & syncKV 缓存事件广播给所有 ingress；ingress 之间同步 token 负载

5.2 KV 事件采集与全局 radix 树

  • 源头：vLLM 原生地在 KV 块被创建/驱逐时发出事件（不是路由器轮询）。
  • 传输：Ray Serve LLM 把这些事件转发给 KVAwareRouter，广播到所有 ingress 副本。
  • 索引：NVIDIA Dynamo 的 KV indexer（Rust 实现）消费事件，构建全局 KV radix 树，在块级计算每个请求的前缀重叠。
  • 模块化分工：事件面/请求面/数据面保持 Ray 原生，Dynamo 只贡献「KV 索引 + 请求打分」两个模块。

Dynamo 两个模块的精确分工：KV indexer + selection service

Ray Serve 只引用 Dynamo 的这两个模块，并以进程内库（in-process，Rust 的 SelectionServiceBuilder）嵌入 ingress，不起独立服务。一句话分工：

KV indexer 是「记忆」（谁缓存了什么），selection service 是「决策」（综合记忆 + 负载，选谁）。

KV indexer（KV 索引器）

职责：维护「每个引擎 worker 现在缓存了哪些 KV 块」的全局索引，回答「这个请求的前缀和谁重叠、重叠多少」。

输入：引擎经 ZMQ 事件流上报的 KV 块创建/驱逐事件。
输出：分层重叠度 gpu / cpu / disk——不只知道「重不重叠」，还知道重叠的块躺在哪层存储（搬回来用的代价不同），这正是「KV 重叠信用」分层的数据来源。
恢复：新起的 indexer 可拉取 /dump 快照重放 KV 事件，避免冷启动失忆。

selection service（选择服务）

职责：把 KV indexer 的重叠信息 + 各 worker 的活跃负载，综合成「每个候选副本一个分数」，选出最优。

组合四件事：① KV overlap indexing（内嵌 indexer）；② KV + 负载双重感知的 worker 选择；③ 活跃负载记账（生命周期事件）；④ 副本同步 / 恢复。

核心输出 effective_prefill_tokens：官方定义它是权威的加权 prefill 负载，由与调度器相同的 cache-credit 公式算出——即博客打分公式里「剩余 prefill」那一项。DYN_ROUTER_KV_OVERLAP_SCORE_CREDIT 调的正是这个公式的系数。 

引擎 worker ──ZMQ KV 事件──► KV indexer（记忆：谁缓存了哪些块，分层 gpu/cpu/disk）
                                  │
                                  ▼ 重叠度查询
请求 prompt ──哈希────────► selection service（决策）
                                  │
                                  ├─ 综合：KV 重叠度（来自 indexer）
                                  │         + 活跃 prefill/decode 负载（生命周期记账）
                                  │         → cache-credit 公式 → effective_prefill_tokens
                                  ▼
                          返回选中的 worker + 重叠摘要

1

▶
2
首 token 生成prefill 完成，转入 decode
▶

decode 进行中持续上报进度（可选）
▶

可选开关 RAY_SERVE_LLM_ENABLE_DECODE_BLOCK_PROGRESS=1 让引擎在生成过程中持续上报 decode 进度，负载跟踪更准（代价：每个引擎副本要向每个 ingress 发更新，高并发下增加网络开销）。

5.4 ingress 侧 tokenize + 独立 token 通道

  • 为什么：打分基于 token ID，ingress 必须用与引擎完全相同的 renderer / chat template 先 tokenize。
  • 好处：token 化只在 ingress 做一次，引擎不重复 tokenize。
  • 代价：tokenize 给 ingress 带来 CPU 开销，这是扩容 ingress 副本数（RAY_SERVE_INGRESS_ROUTER_REPLICAS_PER_NODE）的主因。
  • 独立通道：token 走单独通道发送，可能先于 HTTP 请求到达引擎，引擎临时 staging（暂存） token 直到请求到达；best-effort，缺失/过期则引擎自己重 tokenize。由 RAY_SERVE_LLM_KV_TOKEN_STAGING_* 控制暂存时长/条数/字节。

5.5 可扩展性：最终一致性

  • 路由器被复制成多个 ingress 副本，各自本地做路由决策。
  • token 负载更新在 ingress 间异步共享，最终收敛到同一视图。
  • 设计取舍：路由和 token 流式传输不阻塞在同步路径上，代价是某 ingress 可能短暂基于稍旧的视图做决策——用「可能轻微滞后」换「路由不成为同步瓶颈」。

5.7 已知限制

  • 仅支持 direct streaming：单模型 per application，无 LoRA/multiplex 感知路由。
  • 不支持数据并行部署（计划中）；不支持 prefill-decode 分离（计划中）。

放到坐标系里：与 llm-d「sticky-until-saturated」对照

本篇与本目录另一篇 sticky-until-saturated（llm-d）是同一方向的两个独立实现，对照极有价值：

维度llm-d sticky-until-saturatedRay Serve KVAwareRouter（本篇）
核心机制显式「粘性 + 饱和释放」：命中缓存就粘，超阈值 τ 就改派连续打分：KV 重叠折算进「剩余 prefill」，选 token 负载最低者
阈值来源τ = R_peak × T_max，一次硬件校准闭式推导无单一硬阈值，靠 DYN_* 四个权重软调
KV 感知方式前缀文本命中率（affinity-filter，阈值 0.8）vLLM KV 块事件 → 全局 radix 树（块级精确）
负载信号匹配瓶颈：prefill 看 in-flight 未缓存 token，decode 看活跃请求数统一 token 负载 = 剩余 prefill + 活跃 decode，合成一个分
session ID不需要（也按前缀）不需要，自动发现 KV 复用
第三方集成纯 llm-d 自研深度集成 NVIDIA Dynamo 的 KV indexer + selection service
共同的方法论内核（两篇都强调）：① KV 缓存重叠/命中是「负载估计的代理」，不是路由目标；② 「负载均衡」要到 token/负载粒度，而非请求/会话粒度；③ 都用一个实验证明「牺牲缓存命中率、换取负载均衡」反而更快。
差异：llm-d 用二进制阈值（粘/放）换可推导性；Ray Serve 用连续打分 + 可调权重换细粒度软权衡。

值得借鉴与存疑

值得借鉴

  • 「目标」与「手段」的分离：KV 缓存重叠度是手段（估算负载的输入），token 负载才是目标——全文最干净的方法论贡献。
  • 负载刻画「剩余工作」而非「已省工作」：剩余 prefill + 活跃 decode 才是引擎真实欠账。
  • 块级精确感知：vLLM 原生 KV 块事件 + radix 树，比前缀文本近似准，且能对 offload 块打折、能感知驱逐。
  • 模块化分工：Ray Serve 管编排/生命周期/事件传输，Dynamo 只出 KV 索引 + 打分——第三方引擎能力「模块化接入」的范本。
  • 诚实边界：明确写出会话亲和仍适用的三种负载，不搞「新方案万能」。

存疑 / 未覆盖

  • 非确定性生成是未解死角：输出长度接纳时不可知，短请求可能变长 decode，负载「意外」失衡——博客只提「让 agentic harness 给提示」，无解法。
  • 打分权重仍是「软调参」：DYN_* 没有像 llm-d 的 τ 那样闭式推导，工程上仍要按负载试。
  • 最终一致性的代价未量化：ingress 异步同步，短暂基于陈旧视图决策的偏差，博客没有实验。
  • 范围受限：direct streaming only、无 P/D 分离、无数据并行、无 LoRA/multiplex。
  • 与 llm-d 的「分叉」：一个走阈值可推导、一个走连续打分，哪个在真实漂移流量上更稳，两篇都未正面回答。

一句话总结

Ray Serve LLM 的 KVAwareRouter 把路由目标从「最大化 KV 缓存命中」反转为「最小化 token 负载」：用 vLLM 的 KV 块事件 + Dynamo 的 radix 树精确估算每个副本「还欠多少 prefill 和 decode」，把请求发给欠账最少的副本——KV 缓存重叠度从目标降级为估算负载的输入之一。
