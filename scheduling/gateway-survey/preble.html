Preble：分布式 LLM 推理的 prompt sharing 调度

NSDI 2024 系统 分布式 KV 复用 E2 算法

论文：Zijian He, Reyna Abhyankar, Dongming Li, Yiying Zhang (UCSD), "Preble: Efficient Distributed Prompt Scheduling for LLM Serving"。arXiv:2407.00023。第一个把 KV 前缀复用从单 GPU 扩展到分布式集群的 serving 平台，也是后来 Dynamo / llm-d / SMG「全局路由 + 本地调度」架构的学术前身。

背景：长 prompt + 共享 prompt，但复用只在单 GPU

LLM 的 prompt 用法在 2023 年后出现两个新特征：

  • prompt 远长于输出：文档 QA、视频 QA、工具调用、长指令——prompt 是输出的 37×–2494×。prefill 阶段主导，优化 prefill 是关键。
  • prompt 高度共享：同一文档被多次提问、同一工具说明被反复引用、CoT 逐步调用复用上下文——85%–97% 的 prompt token 与其他请求共享。

这正适合 KV cache 复用。但现有复用（SGLang RadixAttention 等）都局限在单 GPU，而生产系统是分布式的。

它解决的两难：分布式下复用 vs 负载均衡

分布式系统里，如果调度器不感知 prompt 共享，会出现死结：

做法结果
均匀分流（负载均衡，不感知前缀）共享前缀的请求被打散到不同 GPU，每个 GPU 都重复算同样的 KV——浪费
总把共享前缀的请求发到同一 GPU「热门前缀」聚集海量请求，那台 GPU 过载，其余闲置

Preble 的核心：在「复用前缀」和「均衡负载」之间做动态权衡——这正是「复用 vs 公平」张力在分布式路由层的落地。

核心算法：E2（Exploitation + Exploration）

每个请求到来时，先在前缀树里匹配它的 prompt，然后二选一：

匹配前缀长度 > 剩余未匹配长度？
  ├─ 是 → Exploitation（复用）：发到缓存了最长匹配前缀的 GPU
  └─ 否 → Exploration（探索）：发到「负载最轻」的 GPU

直觉：复用省下的计算 > 新计算时，才值得复用（否则复用带来的负载集中不划算）；否则去探索，把负载摊开。

「负载最轻」= prompt-aware load（三部分成本）

探索时，不是简单数请求数，而是算每个 GPU 的三种成本（都折算成 GPU 计算时间，靠离线回归函数从 token 数估算）：

成本含义
L_i：窗口计算负载时间窗口 H（默认 3 分钟）内，GPU 上所有请求的 prefill+decode 时间之和；可复用的前缀算零成本（prompt-aware 的关键）
M_i：驱逐成本为新请求腾内存需驱逐的 KV 节点，其「重算时间 × 命中率」——把缓存淘汰的机会成本纳入路由
P_i：新请求运行成本新请求未命中 token 的 prefill 时间（decode 时间各 GPU 相同，不计）

选三者之和最低的 GPU。这个定义比「数 token / 数请求」精细得多——它同时考虑了历史负载、缓存淘汰代价、新请求成本三个维度。

架构：全局 + 局部两层调度

  • 全局调度器（request-level）：维护全局前缀树（radix tree，记录每个节点：token 数、缓存它的 GPU 集合、历史窗口内共享它的请求数）+ 集群负载视图，做 E2 决策。
  • 局部调度器（per-GPU，iteration-level）：组批、本地前缀树、优先级队列、chunked prefill、LRU 驱逐。
  • 设计理由：全局集中一处维护「集群负载 + 前缀缓存」的全局视图（E2 必需）；request-level 粗粒度让单个全局调度器能扩展到数百 GPU；iteration-level 细粒度让局部调度器快速适应资源变化。
谱系地位：这个「全局路由 + 本地组批」分层架构，正是后来 Dynamo / llm-d / SMG 的共同架构雏形。Preble（2024 年 5 月）是这批工业 KV 感知 gateway 的学术前身之一。

三个补充设计

① 负载动态调整 + 前缀 autoscale

  • 负载转移：最重 GPU 负载 > 最轻 GPU 的 Th_bal 倍时，把未来本该复用重 GPU 的请求重定向到轻 GPU。
  • 前缀 autoscale：某热门前缀的负载仍过高（队列时间翻倍）时，把前缀复制到多个 GPU（按负载拆分其子树）——「前缀缓存分区」的早期版本。

② prefill/decode 平衡的新思路

洞察：命中缓存前缀的请求 ≈ decode 单元（只做 decode），长未缓存 prompt + 短输出 ≈ prefill 单元。于是可以用路由混合这两类请求来平衡 prefill/decode 计算——而不是 chunked prefill 或 PD 分离。这是「用 KV 命中状态反推 prefill/decode 负载」的早期思想，与 Lodestar 的「inflight prefill/decode tokens 分开」同源。

③ 优先级队列保公平（局部调度）

  • 现有：FCFS（忽略复用，多算）vs 前缀共享优先（忽略公平，饿死）。
  • Preble：按「缓存 token 百分比」分 P 个优先级组，按比例从各组选请求（高优先级组多选）——兼顾前缀复用与公平。
  • 这与 k-LPM 的「k 步贪心 + 1 步兜底」、QUARTZ 的「成本 + aging」是同一思想的不同实现。

效果与实现

  • 实现：vLLM / SGLang 之上的独立调度层（两个后端都支持，仅微改）。
  • 评测：Mistral 7B + Llama-3 70B，4×A6000 集群 + 8×H100 服务器，五个真实 workload（工具调用、具身 agent、代码生成、视频 QA、长文档 QA）+ Azure trace。
  • 结果：vs SGLang/vLLM，平均延迟 1.5×–14.5×，P99 延迟 2×–10×。
  • 无共享 prompt 的负载下，性能与 vLLM 持平（不引入额外开销）。

和你的研究的关系

  • 它是「KV 感知路由」的早期完整实现：E2 的 exploitation（路由到缓存前缀的 GPU）+ prompt-aware load（三成本）＝「KV 指标 × 负载指标」的雏形——LMetric 后来用乘法把它公式化了。
  • M_i（驱逐成本）这个维度很超前：把「缓存淘汰会导致未来哪些请求重算」纳入路由，后来 llm-d/SMG 在块级 KV 管理里才做得更细。
  • 全局前缀树 + 命中率记录＝后来「块级 KV 感知」的前身：Dynamo/llm-d/SMG 订阅引擎 KV 事件、精确镜像 KV cache，是 Preble 前缀树思想的精细化。
