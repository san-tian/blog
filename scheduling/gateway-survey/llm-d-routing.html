llm-d 路由策略讲解

Endpoint Picker（EPP） 插件化打分器 Kubernetes Gateway API

一句话：llm-d 的路由就是「给每个候选 pod 打分，选总分最高的那个」。 它有两套打分方式：一套是手写规则（看前缀命中、排队、KV 占用）， 一套是机器学习预测延迟（XGBoost 预测 TTFT/TPOT）。

总览：一个请求进来，走 5 步

1
Request Control处理 header、流控准入、定位候选 pod、全局强制过滤
▼
2
Data Producers准备数据：分词、前缀缓存匹配、采集负载、预测延迟
▼
3
Filter过滤掉不合适的 pod（模型不兼容、资源不足、SLO headroom 不够）
▼
4
Score（核心）多个 scorer 各自打分，按权重加权求和
▼
5
Pick选总分最高的 pod（max-score-picker）

核心公式：加权求和

total_score(pod) = Σ scoreᵢ(pod) × weightᵢ

每个 scorer 输出 0~1 的分数，乘上一个权重（默认都是 1.0），累加得到总分。权重只有相对比例有意义。

方式一：规则式打分 默认

手写规则，不学习。每个 scorer 的公式如下（都输出 0~1，分数越高越优先）：

1. 前缀缓存命中（prefix-cache-scorer）

把 prompt 切成固定大小的块，逐块查 pod 的缓存索引，看命中多少块：

matchRatio  = 命中块数 / 总块数          # 命中比例
score = 命中比例   # 默认只看命中比例，命中越多分越高

命中多 = prefill 省 = 分高。这是把请求送到「已经算过相同前缀」的 pod。

2. 负载类 scorer（负载越低，分越高）

load-aware（排队长度）

等待 0 个 → 0.5 否则 → 0.5 × (1 − 等待/128)

排队越少分越高，阈值 128。

queue-depth（排队深度）

min-max 归一化

在所有候选 pod 里比较，排队最短的最高分。

active-request（活跃请求）

空闲 → 1.0（满分） 忙 → (max−count)/max × maxBusyScore

空闲 pod 直接满分。

token-load（token 负载）

score = 1 − tokenLoad/阈值 tokenLoad = inflight + 未命中投影

inflight token 越多分越低。

kv-utilization（KV 占用）

score = 1 − KV利用率

KV 占用越低分越高。

running-requests

min-max 归一化

运行中请求数越少分越高。

3. 亲和类 scorer

lora-affinity（LoRA 适配器已加载）、session-affinity（会话亲和）、context-length-aware（上下文长度感知）。

方式二：预测延迟路由 XGBoost

把「规则信号」换成「ML 预测的延迟」，再用 SLO 余量打分。

1
sidecar 在线训练 XGBoost从真实请求持续学习，预测每个 pod 的 TTFT / TPOT
▼
2
算 SLO 余量headroom = SLO − 预测延迟
▼
3
latency-scorer 打分score = 0.8×headroom(TTFT) + 0.2×headroom(TPOT)
headroom = SLO − predicted_latency
score = 0.8 × headroom_ttft + 0.2 × headroom_tpot

两种策略：least（默认，选余量最接近 SLO 的，省资源）或 most（选余量最大的，最保守）。

sidecar 挂掉时，回退到「KV + queue + prefix」三个规则信号加权（即退回方式一）。

两套方式对比

方式一 · 规则打分方式二 · 预测延迟
打分依据前缀命中、排队、KV 占用等聚合信号ML 预测的 TTFT/TPOT
模型无XGBoost / Bayesian Ridge / LightGBM
训练不需要在线持续训练
SLO 概念无headroom = SLO − 预测
失败兜底—回退到规则

两者共享同一个骨架（打分 → 加权 → 选最高分），区别只在「打分的依据」。这也解释了为什么 Lodestar 论文说它是 rule-based、LMetric 论文说它是 simulation-based——各看到一面。

完整例子：一个请求怎么被打分、选 pod

来了一个 2000 token 的请求 r，有 3 个候选 pod。假设只启用 3 个 scorer（权重全 1.0）。

第 0 步：三个 pod 的当前状态

podprefixloadtoken总分
P10.750.460.92.11 ✓ 选中
P200.51.01.50

看懂这个例子就懂了 llm-d：
  • P3 前缀全命中（1.0），但它排队 100 个、负载很重，被 load 和 token 两项拖下去。
  • P2 完全冷（前缀 0 分），但它空闲，靠 load 和 token 两项拉回来。
  • P1 是「命中不错 + 负载适中」的折中，三项都中上，总分最高，胜出。
这就是「前缀亲和」和「负载均衡」两个目标，通过加权求和做 trade-off 的过程。

关键：它缺了什么

无论方式一还是方式二，llm-d 看到的都是聚合信号：

  • 方式一：前缀命中比例、排队数、KV 占用、inflight token 总量 —— 都是「一共多少」
  • 方式二：预测的一个延迟标量 —— 也是「一个数」
它看不到「队列里每个请求分别还剩多少 prefill、谁排在前面」。 一个正跑着 50 万 token 长 prefill 的 pod，在它的眼里可能只是「排队 0 个、inflight 1 个」，看起来还很闲——这正是你要解决的「队列组成」盲区。
