KV 前缀复用 + 排队调度：理论 / 启发式 / 系统

KV cache hit 排队调度 复用 vs 公平

三篇工作从三个层次攻克同一个问题：「KV 缓存命中（前缀复用）」和「排队/负载均衡」是两个冲突的目标——贪心复用会让"前缀不匹配"的请求饿死，纯均衡又会浪费前缀复用。本文串讲三篇：k-LPM（理论）、LMetric（启发式）、Preble（系统）。

核心张力：复用 vs 公平，为什么是冲突的

前缀复用（RadixAttention 等）让「共享前缀」的请求省掉重复的 prefill 计算。但它引入一个调度上的两难：

  • 偏向复用（LPM 贪心）：把"和当前缓存前缀重叠最大"的请求优先处理 → 前缀命中高、省计算，但前缀不匹配的请求被无限延后（饿死）。
  • 偏向公平（FCFS 先到先服务）：按到达顺序处理 → 无人饿死，但完全放弃前缀复用，高负载下 TTFT 尖峰。

这个张力在两个层次都存在：

层次「复用」的表现「公平」的表现
实例内（单实例队列排序）先处理前缀命中的请求先到先服务，防止饿死
实例间（跨实例路由）路由到 KV 命中最多的实例均匀分散，负载均衡

下面三篇工作分别覆盖：k-LPM 在实例内给出理论最优，LMetric 在实例间给出零调参启发式，Preble 在分布式做系统级联合优化。

k-LPM：理论层（NeurIPS 2025） 详解 →

来源：Dexter et al., "LLM Query Scheduling with Prefix Reuse and Latency Constraints", NeurIPS 2025, arXiv:2502.04677。SGLang v0.4.1 默认 LPM、vLLM v0.6.6 默认 FCFS 的出处即本文 §1。

它揭示了什么：FCFS 和 LPM 各自的局限

  • FCFS（先到先服务）：完全不利用前缀复用，高负载（burst 流量）下 TTFT 尖峰。
  • LPM（longest prefix match，贪心最大化复用）：离线（所有 query 已知）时确实最优（Zheng et al. 2024 的 Theorem 3.1）；但在线（query 随时间到达 + 严格 TTFT 约束）下，会饿死前缀重叠不够高的 query——它们永远排不上队。

核心贡献 1：证明问题是 NP-Hard

把「判断是否存在满足 TTFT 约束的调度」归约到 3-PARTITION，证明在 RadixAttention（前缀复用）下是 NP-Hard（Theorem 1）。

对照：无前缀复用时 FCFS 平凡最优；均匀到达时间（离线）时 LPM 最优。只有「前缀复用 + 在线到达 + TTFT 约束」三者叠加，问题才变难——这正是真实 serving 的场景。

核心贡献 2：k-LPM 算法（复用 ↔ 公平的插值）

k-LPM 每轮调度 k 个请求：
  for i = 1 .. k-1:  处理「前缀命中率最大」的 query   （LPM 的贪心）
  处理「等待最久」的 query                        （FCFS 的兜底）

k = 1  → 退化为 FCFS（纯公平）
k = ∞  → 退化为 LPM（纯复用）

直觉：每 k 步强制处理一次最老的 query，给"前缀不匹配"的请求兜底，防止饿死；其余 k-1 步仍贪心复用，保留 LPM 的省计算优势。

核心贡献 3：理论保证（Theorem 2）

在「树形 prompt + 均匀随机到达顺序」（Regular Arrival Shuffled Queue）下，最大 TTFT 的上下界：

算法最大 TTFT 界含义
LPM≥ T + n·(u/k + d)下界（高概率）
FCFS≥ T + n·(u + d − s)下界（高概率）
k-LPM≤ T + n·(u/k + d − s/k)上界（确定性）

当 0 < s < u 且 k > 1（中间负载）时，k-LPM 的上界严格低于 FCFS 和 LPM 的下界（Corollary 3）——即 k-LPM 同时优于两者。直觉：低负载（s 大）FCFS 好、高负载（s 小）LPM 好，中间负载 k-LPM 最优。

实验：k=2 就够

  • Llama-3.1-8B-Instruct + 8×A100 + SGLang v0.4.1；360Brew 的 8k-context prompt（Instruction / Member Profile / Past Interactions 为共享前缀，仅 Question 变化）。
  • 关键发现：k=2 就足够，在广泛 request rate 下 P99 TTFT 最低；大 k（1000）退化为 LPM。
  • FCFS 低负载好、LPM 高负载好、k-LPM 全负载稳健——与理论一致。

LMetric：启发式层（OSDI 2026）

已在 LMetric 详解页 展开，这里只讲和本专题相关的一层。

LMetric 解决的是实例间的同款张力——用「乘法路由」同时平衡 KV 命中和负载：

score = KV 感知指标（需新算的 prefill token）× 负载指标（batch size）
  • 它系统性否定了「加权求和」（需逐负载调参）和「filter 策略」（偏向负载、无法充分利用缓存）——这两个正是"复用 vs 公平"两端摇摆的失败案例。
  • 乘法让 KV 项和负载项互相约束：KV 命中高但实例已过载（batch 大）时，乘积被负载项拉低，不会一味复用；反之亦然。

和 k-LPM 的呼应：k-LPM 在实例内用"k 步贪心 + 1 步兜底"插值复用和公平；LMetric 在实例间用"乘法"让两个维度互相制衡。同一个张力，两个层次，两种解。

Preble：系统层（NSDI 2024） 详解 →

来源：Y. Zhang et al. (UCSD), "Preble: Efficient Distributed Prompt Scheduling for LLM Serving", NSDI 2024, arXiv:2407.00023。

它解决的问题

KV cache 复用此前都局限在单 GPU；而生产 serving 系统是分布式的——前缀可能分散在不同实例上，单机复用救不了跨机场景。Preble 是第一个针对 prompt sharing 优化的分布式 serving 平台。

核心机制：E2 算法（Exploitation + Exploration）

每个请求到来时，先在前缀树里匹配 prompt，然后二选一：

匹配前缀长度 > 剩余未匹配长度？
  ├─ 是 → Exploitation（复用）：发到缓存了最长匹配前缀的 GPU
  └─ 否 → Exploration（探索）：发到「负载最轻」的 GPU

「负载最轻」用 prompt-aware load（三部分成本，都折算成 GPU 计算时间）：

成本含义
L_i时间窗口 H 内 GPU 的计算负载（prefill+decode 时间，可复用的前缀算零成本）
M_i驱逐现有 KV 腾内存的成本（被驱逐节点 token 数 × 该节点命中率）——把「缓存淘汰的机会成本」纳入路由
P_i新请求在该 GPU 运行的成本（未命中 token 的 prefill 时间）

选三者之和最低的 GPU。

架构：全局 + 局部两层调度

  • 全局调度器（request-level）：维护全局前缀树 + 集群负载视图，做 E2 决策（发到哪个 GPU）。
  • 局部调度器（per-GPU，iteration-level）：组批、前缀树、优先级队列。
  • 这个「全局路由 + 本地组批」分层架构，正是后来 Dynamo / llm-d / SMG 的架构雏形。

三个补充设计

  • 负载调整 + 前缀 autoscale：热门前缀请求暴涨时，先把本该复用它的请求重定向到轻 GPU；若队列时间翻倍，把前缀复制到多个 GPU——后来「前缀缓存分区」的早期版本。
  • prefill/decode 平衡的新思路：命中缓存前缀的请求≈ decode 单元（只做 decode），长未缓存 prompt + 短输出≈ prefill 单元；用路由混合这两类请求来平衡两阶段计算，而非 chunked prefill 或 PD 分离。
  • 优先级队列保公平：局部调度按「缓存 token 百分比」分优先级组，按比例选请求，兼顾前缀复用与公平（避免 LPM 式饿死）。

效果

  • 两个开源 LLM + 真实负载：平均延迟 1.5×–14.5×，P99 延迟 2×–10×（vs SOTA serving 系统）。
和 k-LPM / LMetric 的呼应：Preble 的「联合优化 KV reuse + load-balancing」就是「复用 vs 公平」在分布式路由层的落地——它没有像 k-LPM 那样给出最优性证明，也没有像 LMetric 那样给出零调参公式，而是用分层调度把这两个目标在系统里协调起来。三篇正好补全了「理论 → 启发式 → 系统」的完整链条。

共性结论（对「组合范式」的回响）

三篇殊途同归：它们都在解「如何同时均衡 cache hit 和负载」这同一个问题，只是层次和手法不同。这条线补上了全景调研页「组合范式」表里的理论底座——k-LPM 用 NP-hard 证明了这个权衡本身是难的（不是工程技巧），LMetric 和 Preble 分别给出启发式和系统化的解。

对「细粒度负载路由设计」的意义：k-LPM 的「复用 vs 公平」张力，在实例间路由同样成立——把请求全路由到"KV 命中最多的实例"就是实例间版的 LPM，会饿死"前缀不匹配的实例"（造成负载不均）。这正是 细粒度路由设计页 里「瓶颈向量」要解决的问题之一。
