Llumnix（动态重调度）论文讲解

OSDI 2024 · Dynamic Scheduling for Large Language Model Serving · Alibaba（开源 AlibabaPAI/llumnix）

主线：一条因果链

一句话：现有调度把「请求发给哪个实例」当成一次性的、不可撤销的决定；Llumnix 把它变成可撤销的——请求带着 KV cache 在实例间实时搬家（类比 OS 在 CPU 核间做上下文切换），停机仅 ~20–30ms 且与序列长度无关，换来 P99 first-token 最高 15×、高优请求 1.5×、同等尾延迟省 36% 成本。

主线：派发不可逆（问题）→ 用改派让它可逆（手段）→ 但改派必须足够便宜，否则是空话——靠 append-only KV + 多阶段流水线把停机压成常数（使手段可用）→ 有了便宜的可逆，再解决「何时迁、迁谁」的规模化（决策）。
记住一句：改派是手段，不是问题本身。就像 OS 的上下文切换是手段，多租户调度才是问题。

论文标题「serving LLMs as Unix」就是这个类比：现代 OS 的上下文切换之所以成立，一半靠「有切换这个机制」，一半靠「硬件让切换变快」。Llumnix 照搬了这个结构——它的技术贡献一半是引入迁移这个自由度，一半是让迁移便宜到可用，剩下一小半是「何时迁移」的调度策略。读的顺序：先看问题为什么必须可逆（§问题），再看可逆为什么不能是空头支票（§手段里的 3.5s 对照），最后看便宜的可逆解锁了什么（§规模化、§效果）。

来源：arXiv 2406.03243（Biao Sun、Ziming Huang 等，Alibaba Group）

问题：不可逆的派发，遇上最糟糕的决策时机

LLM 服务本质是「多租户动态 OS」：两个根源特性——工作负载异构（输入/输出长度、延迟要求差异巨大）+ 执行不可预测（输出 token 数先验未知，KV 内存需求随生成动态增长）。而派发发生在信息最匮乏的时刻：请求刚到达时，没人知道它会生成多长、占多少内存。于是初始决策必然随时间变错，错误表现为三族尾延迟病：

病表现论文实测证据
抢占停顿（Isolation）内存竞争 → 抢占与批内干扰A10 + LLaMA-7B、平均内存负载仅 62% 时仍有 8% 请求被抢占；P99 per-token decode = 3.8× P50，其中抢占损失占 70%（P99 请求被抢占两次、累计停顿 50s）
碎片排队（Fragmentation）负载均衡把空闲内存摊碎在各实例；PagedAttention 只消除 decode 阶段碎片，prefill 要一次性要一大块4 实例实验：集群总空闲内存够 3 个队头请求，但各实例都因本机空间不足而排队
优先级干扰（Priorities）所有请求一视同仁，交互型/付费高优被普通请求干扰batch 内干扰：decode 单步耗时差距最高 2.6×

关键观察：某个实例出问题时，集群整体往往仍有余量——但请求被绑定在首次派发的实例上，动不了。这就是「不可逆」三字要付出的代价。

手段：把派发变成可逆的（改派）

解法不是「派得更准」（那要预测，而预测在异构+不可预测下必然失手），而是把派发从不可撤销改成可撤销——请求可以在实例间迁移。派错了就搬，不必在到达时刻赌对。

一次性派发（现有 gateway/调度器）运行时重调度（Llumnix）
预测压力必须在对请求一无所知时做对决策初始派发可以错，跑歪了就搬
响应对象到达时刻的负载快照运行中的真实增长（输出长度、内存占用逐渐显形）
度量要求越细/越预测式越好实例级聚合即可 + 决策可逆

改派落到四个场景（论文 Figure 1）：负载均衡（减少抢占/干扰）、去碎片（腾出连续空间给长输入）、优先级（给高优动态腾出低负载环境，无需静态预留机器）、伸缩（排干待终止实例 / 快速填满新实例）。

使手段可用：把改派成本压成常数

改派谁都会提，但直接搬一个 decode 中的请求 = 把它的 KV cache 整个重算或拷贝——8k 序列要 3.5s，这个成本会让改派永远停在纸面上。Llumnix 的关键贡献是把迁移成本压到常数，方法是一个洞察 + 一个机制：

  • 关键洞察：KV cache 是 append-only——自回归生成只追加、不修改已有 KV → 可以边继续解码、边拷贝历史块。
  • 多阶段流水线：stage 0 拷历史块同时继续算新 token → stage 1 拷 stage 0 期间新增的（量很小）→ … → 只有最后一个迭代真正停机，拷的也只是一步的 KV。停机时间 = 拷一个迭代的 KV ≈ 常数，与序列长度无关（borrow 自 VM live migration 的 working-set 思想，且不需要 dirty page 追踪）。
  • handshake 协议处理迁移中的异常：目标实例预分配并预留块；每阶段后检查请求是否已完成/被抢占；任何一侧失败即 abort 并释放——正确性不依赖运气。
迁移方式停机时间
Llumnix 流水线迁移~20–30ms 常数（比一个 decode step 还短；实测最少两阶段即完成）
重算（recompute）8k 序列 LLaMA-30B = 3.5s ≈ 54 个 decode step 的服务停顿
阻塞式拷贝随序列长度增长，最高达迁移方式的 111×
  • 对同实例其他请求的开销 ≤1%，且只在有迁移进行时存在（实测实例仅 ~10% 时间有迁移进行）。
  • 工程细节：KV 传输用 Gloo 而非 NCCL（NCCL 并发调用不安全，无法与推理并行；Gloo 需 GPU→CPU 拷贝，走独立 CUDA stream 不阻塞推理）；block fusion——vLLM 的小块（128KB/块，1k token = 4k 块）先融合成连续 CPU buffer 再整体发送。
  • 诚实标注：跨机迁移走网络（实验机 PCIe 64Gb/s）；论文假设现代 TP 部署限于单机内高速互联，跨机迁移不与 TP 通信争抢。

规模化：何时迁、迁谁

便宜的可逆只是「能做」，还得解决「什么时候做、对谁做」。Llumnix 用两级架构 + 一个统一策略回答：

① 两级架构：全局调度器只看实例，llumlet 管请求

  • global scheduler + 每实例 llumlet（local scheduler + migration coordinator）：全局调度器不追踪具体请求，只面向实例决策（看内存负载），迁移也只配对 source/destination 实例，由 llumlet 自己挑请求（偏好低优先级、短序列）并执行。
  • 复杂度与集群规模解耦 → 可扩展性实测：64 实例压测下，中心化 baseline 每迭代调度停顿 40ms（1.7× 减速），Llumnix 近零。
  • 实现：3,300 行 Python，非侵入式独立库；vLLM 后端；Ray actor 编排多实例 + OpenAI 风格 frontend（生成 token 经 frontend 转发，用户对迁移无感）；全局调度器故障时降级为直连派发（迁移暂停，服务不停）。

② virtual usage：一套规则统一四个场景

核心观察：四个场景其实只有两类——负载均衡，与「在某实例上制造空闲」（去碎片/优先级/排干）。后者可以统一进前者：给请求设「虚拟用量」让实例虚拟过载，负载均衡策略就会自然触发迁出。

请求情形virtual usage 规则触发效果
普通运行中请求物理内存占用常规负载均衡
排队队头请求其真实内存需求（物理占用为 0）实例虚拟过载 → 迁走别的请求腾空间（= 去碎片）
高执行优先级请求物理占用 + headroom（同实例多高优平分；headroom = profile 出的「保持理想 decode 速度」水位，实验取 1600 token 负载）普通请求被迁走，高优获得动态「专属」余量
fake request（待终止实例）∞排干实例（autoscaling 缩容）

freeness 公式：F = (M − ΣV) / B（M 总内存、V 虚拟用量、B batch size）——除以 B 意味着「按当前消耗速度还能跑多少个 decode 迭代」，即把剩余容量换算成剩余时间；F 可为负（有排队/高优请求时）→ 自动视为过载。决策规则：派发 = 高调度优先级先、同级 FCFS、派给 F 最高的实例；迁移 = 周期触发，F 低于/高于阈值的实例配对（最低配最高）；autoscaling = 集群平均 F 维持在区间内（默认 [10, 60]）。

适用条件：什么时候这条链会真正兑现

把主线折算成一条账：Llumnix 赚的钱 = 「初始派发错误暴露后的事后修正价值」 − 迁移成本（~20–30ms + ≤1% 开销）。它不是普适加速器——四个条件同时满足才进入甜点区：

条件为什么论文证据
① 负载高方差、先验不可知输出长度逐 token 显形、内存随生成增长——初始派发必然有错可纠；同质负载下 RR ≈ JSQ ≈ Llumnix，没东西可纠收益全部来自 power-law 长尾 / ShareGPT 高方差 trace
② 利用率在中高档低载无事发生；饱和无处可搬——迁移只搬运排队，不创造算力，饱和该上准入控制/扩容auto-scaling 把平均 freeness 维持在 [10,60]，本质是守甜点区
③ 在乎的损失是它修的三族抢占停顿 / 碎片排队 / 优先级干扰——全是尾延迟问题，只看均值吞吐则收益 ≈ 062% 负载仍 8% 被抢占、P99 decode=3.8×P50；总空闲够 3 个队头请求仍排队；批内干扰 2.6×
④ 修正窗口存在且迁移便宜decode 长才有时间"活在错误的位置"；append-only KV 把迁移压成常数是工程前提——无页表级 KV 拷贝能力的引擎退化为 recompute（8k=3.5s），只剩排队中请求可搬停机 20–30ms 与长度无关；同模型同构 + PD 共置是隐含前提

收益分解：迁移的真实贡献边界

vs Round-robin 的巨大差距（prefill 26.6×）大半来自负载感知派发本身——INFaaS++ 也做负载感知派发，对照它的净增量才是「迁移」的真实贡献：e2e 1.5–1.6×、长输入 prefill 7.7–14.8×、碎片 7.9%→0.7%、抢占损失 −70%。准确地说：到达时刻的静态不均衡，派发策略就够；迁移真正起作用的场景是"派发后负载漂移"——输出长度显形、内存增长、其他请求完成导致的负载再分布。

反适用条件（不起作用甚至负收益）

  • 均匀短请求 / 低载 / 单实例 / 全饱和：分别对应"没错误可纠 / 不触发 / 无处搬 / 无去处"；
  • 输出长度可预测的负载（确定性、可缓存任务）：一次性知情派发（SJF）就能做对，不需要为纠错能力付复杂度；
  • PD 分离部署：它修的 prefill 碎片问题换了形态，decode 侧迁移收益仍在但变小；
  • 前缀缓存重度亲和的负载：迁移把请求搬离其前缀所在实例，后续共享该前缀的请求失去亲和——对照 cache hit 22× 是一阶项（实测报告 →），这类负载下迁移代价可能盖过收益。这是 Llumnix 与 cache-aware 路由（Dynamo/llm-d 一族）的真实张力，论文未讨论。
落地判据（三个信号扫自己的负载）：① 输出长度分布的 CV（双峰/长尾？）② 稳态利用率区间 ③ 抢占 + 碎片排队在 P99 里的占比。三个都高 → 甜点区；都低 → Llumnix 是纯复杂度净值。

主线收束：对照你的研究

  • 「度量粗 + 决策可逆」是队列组成盲区的另一条出路：Llumnix 的全局度量也是实例级聚合（virtual usage / freeness）——它绕开盲区的方式不是把度量做细，而是把决策做可逆。与 routing-design 的细粒度准入排序（事前算准）正交、可组合：迁移摊薄初始派发错误的代价，准入重排决定队列内次序。
  • 但它不解决 TTFT 排队：llumlet 挑迁移请求按「低优先级、短序列优先」，是负载均衡的执行细节；排队请求只以「队头 demand 计入虚拟用量」参与触发，路由层没有逐请求队列、没有 SJF——队列组成盲区依然存在。
  • freeness 除以 batch size（剩余迭代数）与 token 预算模型 steps×t_step 同族：都是把「剩余容量」换算成「还能跑多久」，而非裸内存/裸 token 数。
  • 对经典调度理论的修复：SRPT/SPT 假设「抢占免费」在 LLM 里不成立（KV cache 丢失代价大）——Llumnix 用 live migration 把「搬走一个请求」压到 20–30ms 且与长度无关，部分恢复了抢占式调度的设计空间。
  • 对长上下文时代尤其重要：KV 随 128k+ 上下文膨胀，「迁移停机与序列长度无关」这条性质让重调度从理论选项变成工程可行的一等自由度——代价模型不再随 KV 变大而恶化。
