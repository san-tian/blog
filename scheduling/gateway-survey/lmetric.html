LMetric（Simple is Better）论文讲解

OSDI 2026 · Multiplication May Be All You Need for LLM Request Scheduling · 阿里（已部署百炼生产）

一句话

用「一个 KV 感知指标 × 一个负载指标」的乘积作为调度分数，同时兼顾 KV cache 命中与负载均衡，且零超参调优（超参在跨实例比较时约去）。相比 vLLM-v1 和生产调度器，TTFT 最多降 92%。

来源：arXiv 2603.15202 / OSDI 26 PDF

问题：集群级请求调度的两个目标

LLM 提供商部署多个 serving 实例（引擎最小部署单元）+ 一个全局调度器，把请求路由到实例。调度要同时满足两个目标：

  • KV cache 感知：请求的部分输入命中某实例的 KV cache，该实例能跳过这些 token 的 prefill，加速 TTFT。
  • 负载均衡：把请求均匀分到各实例，避免热点。

只做负载均衡（vLLM 默认）不够——不同请求因 KV cache 命中的计算量不同；只做 KV 感知也不够——会偏向有命中的实例，损害负载均衡。

现有三种组合策略的缺陷

策略机制缺陷
线性组合（加权求和）score = α·KV 指标 + β·负载指标需逐工作负载调超参；静态调好的超参在动态负载下次优（阿里百炼现用方案）
Filter 策略先过滤过载实例，再选 KV 命中最多的阈值需调参；偏向负载均衡，无法充分利用 KV cache
Simulation 策略仿真器预测路由到各实例的期望延迟依赖仿真器精度；需逐模型/硬件/部署开发

核心解法：乘法路由

score(实例) = KV 感知指标 × 负载指标

KV 感知指标 = 路由到该实例、考虑 KV 命中后需新算的 prefill token 数
负载指标   = 该实例当前的 batch size
  • 关键思想：把线性组合的加法换成乘法。乘积保持了与线性组合相似的趋势，但超参在跨实例分数比较时相互约去，无需调参。
  • 指标选择：KV 感知用「需排队的新 prefill token 数」比「KV 命中率」更好（命中率是比例，不能反映绝对计算量）。

鲁棒性：乘法何时失效

  • 论文数学推导了乘法可能失效的近似条件：只在损害负载均衡的极端 KV 偏斜下发生，实践中极罕见。
  • 设计两阶段检测：检测到极端偏斜时，回退到纯负载均衡策略。

效果

  • H20 集群（最多 16 GPU），dense + MoE 模型，负载覆盖 chatbot / API 调用 / coding agent。
  • 对比 vLLM、ai-Dynamo、llm-d、阿里百炼生产调度器：TTFT 最多降 92%。
  • 已部署阿里百炼数百 GPU 生产环境（金丝雀验证）。
  • 聚焦 PD 共置（prefill/decode 同实例），论文第 7 节讨论如何扩展到 PD 分离。
来源：论文 §5（乘法组合）、§6（评测）、§7（PD 分离讨论）

为什么它重要（对照你的研究主线）

这篇论文系统性否定了「加权求和」（Dynamo cache-credit、llm-d 旧默认、AIBrix 等工业方案的底层范式），论证了它的根本缺陷：需逐负载调参、静态超参在动态负载下次优。乘法路由给出了零调参的替代——这正是「如何同时均衡 cache hit 和负载」这个问题的学术最干净解。对照：llm-d 的 sticky-until-saturated 用「阈值可推导」达到类似目的，Lodestar 用「在线学习」绕开手工规则，LMetric 用「乘法」。
