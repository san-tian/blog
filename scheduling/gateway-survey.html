① 多实例 HA / 状态同步 —— 谁真正解决了「路由状态跨实例一致」

核心矛盾：KV cache 状态是路由决策的输入，但多实例路由时每个实例看到的状态必须一致，否则会做出冲突决策。各家分三档：

  • 最强（SMG）：SWIM gossip + CRDT 同步了包括 cache-aware routing tree 在内的全量路由状态——唯一把「KV 路由树」纳入跨实例同步的方案，3/5 节点容忍 1/2 节点故障。
  • 事件驱动收敛（Dynamo / llm-d / Ray Serve）：Dynamo 的 selection service 用 ZMQ 同步 admission/prefill-complete（output-block 故意不同步）；llm-d 的 KV indexer pod-discovery 模式每副本独立订阅全量 KV 事件各自收敛；Ray Serve ingress 异步同步 token 负载。三者都是「最终一致」。
  • 有限（SGLang Router / Lodestar）：引擎内嵌或单实例 gateway，无跨实例路由状态同步——多实例时 cache 命中退化。

② SGLang KV event 感知 —— 谁在做「块级精确」而非「前缀近似」

  • 块级精确（Dynamo / llm-d）：都订阅 vLLM 和 SGLang 的 ZMQ KV 事件（BlockStored/BlockRemoved/AllBlocksCleared），维护块级索引。llm-d 还支持 multimodal hash、LoRA、分层权重、speculative indexing。
  • 前缀近似（SMG / AIBrix / Lodestar）：维护 radix 树/前缀索引，匹配文本前缀，不感知引擎真实缓存和驱逐。
  • 引擎原生（SGLang Router）：SGLang 的 RadixAttention，引擎内前缀复用（非跨实例 KV event）。
  • 受限（Ray Serve LLM）：KVAwareRouter 的 KV 事件是 vLLM-native；SGLang 能跑但社区支持早期。

③ K8s / Ray 依赖 —— 能否脱离编排框架独立跑

  • 零依赖（Dynamo / SMG / SGLang Router / DLRouter）：引擎无关、纯进程内或独立二进制，K8s 只是可选。
  • K8s 可选（llm-d）：新增 EndpointDiscovery + file-discovery，可无 K8s 运行（Slurm / Ray / 裸机），路由逻辑不变。
  • 强绑定 K8s（AIBrix / Lodestar）：依赖 K8s pod 模型，下游推理服务必须跑在 K8s pod。
  • 强绑定 Ray（Ray Serve LLM）：路由和下游引擎都在 Ray Serve 部署模型内。

分类说明：Preble 做了跨实例 KV 复用，但它是「分布式 prompt sharing 平台」——分层调度（全局路由 + 局部组批）内嵌在自有服务栈里，不是可插拔在任意引擎前的独立 gateway，故归 C 不归 A；其「复用 vs 负载均衡联合优化」的思路与 A 类高度相关。

背景前提（引擎侧，非调度本身）：vLLM / PagedAttention（SOSP 2023，块级 KV 管理）与 SGLang / RadixAttention（NeurIPS 2024，前缀复用）——它们是「KV 感知负载估计」的引擎侧基础： 路由要估算「能省多少 prefill」，靠的就是这两篇定义的块级/前缀缓存语义。此处仅作背景，不展开。
关键洞察：学术界的「乘法/阈值/学习」三范式，正是对工业界「加权求和」缺陷的回应。 LMetric 系统性否定了「加权求和」（需逐负载调参）和「filter 策略」（偏向负载、无法充分利用缓存），提出乘法路由零调参解； llm-d 的 sticky-until-saturated 用「阈值可推导」实现类似目标；Lodestar 用在线学习绕开手工规则。 三者殊途同归：都在解决「如何同时均衡 cache hit 和负载」这同一个问题。
专题：KV 前缀复用 + 排队调度——k-LPM（理论 NP-hard）、LMetric（乘法启发式）、Preble（分布式系统）三篇从三个层次攻克「复用 vs 公平」的张力，见 KV 前缀复用 + 排队调度 →。

关键洞察：prefill / decode token 必须分开。Lodestar 明确强调 inflight prefill tokens 和 inflight decode tokens 要分开保留——prefill 是计算密集、decode 是内存带宽密集，合并会掩盖实例正逼近哪个瓶颈。llm-d 的「瓶颈匹配」是同一条思路：prefill 受限看 in-flight 未缓存 token，decode 受限看活跃请求数。这是「负载感知」最容易被忽视、也最关键的细节。
延伸设计：基于「逐请求 prefill 等待」的细粒度负载路由，见 细粒度负载路由设计 →——把负载从聚合计数升级到队列组成，路由时精确计算「新请求插进去要等多久」，选等待最短的实例。

结论与建议

第一部分：工业级 gateway 选型

结论：只有 Dynamo、llm-d、SMG 三家——同时满足「块级 KV 感知 + Token 负载感知 + 多实例 HA 同步 + 引擎无关」四个条件的，目前只有这三家。选型从这三家出发即可，其余项目都是冗余选项（见下方备查行，不再展开）。
注意「四个条件」是多实例生产部署的严格口径，不是唯一权重集：2–4 副本的实验/小规模场景可把 HA 同步降权（SGLang Router 单实例、零编排依赖，反而最省事）；跨引擎多后端优先则 Dynamo/SMG 升权。把上面的矩阵当打分表按需加权——「三家」是默认权重下的答案，不是唯一答案。

其余六家（冗余备查）：SGLang Router（块级靠外部 indexer 可选，单实例无 HA）· AIBrix（前缀级 + 必须 K8s）· vLLM Router（前缀级 + vLLM 专用）· Ray Serve LLM（块级 KV 与 token 负载已具备，但 KV indexer 复用 Dynamo、且绑定 Ray 编排）· Lodestar（学术，单实例，学习式部署重）· DLRouter（新项目，前缀级）。

按四个关注点选型：
  • 要「多实例 + 状态同步」最强 → SMG（SWIM+CRDT 同步了 cache-aware 路由树）；次选 Dynamo / llm-d（事件驱动最终一致）。
  • 要「SGLang KV event 块级感知」→ Dynamo 或 llm-d（都订阅 SGLang 的 ZMQ KV 事件）。
  • 要「脱离 K8s/Ray 独立跑」→ Dynamo / SMG / SGLang Router（引擎无关、零编排依赖）。
  • 要「cache hit + 负载均衡」最干净 → 学术是 LMetric 乘法路由（零调参）；工业落地是 llm-d sticky-until-saturated（阈值可推导） 或 Dynamo（cache-credit 打分）。

第二部分：路由方式调研

四个方法回答的是同一个问题：「这个新请求，该发给哪个实例？」。它们的分歧只有一处——怎么判断一个实例「忙不忙」，以及怎么把「命中缓存能省多少」和「实例多忙」合成一个决定。四种答案，从手写到学习：

方案怎么决定（人话）一句话本质
LMetric
OSDI 26 · 学术 详解 →		 乘法路由：给每个实例算「命中缓存能省的活儿 × 现在多忙」的乘积，谁小发给谁。命中越多乘积越小、越忙乘积越大，两项自动平衡，不需要人调权重。 命中缓存 = 活儿变少 = 更划算
llm-d
sticky-until-saturated · 工业 详解 →		 先粘后放：请求优先发给缓存了它前缀的实例（省 prefill）；等那个实例忙到超过一个校准阈值 τ，就改按负载选——prefill 吃紧看「还有多少 token 没算」，decode 吃紧看「还有多少请求在跑」。 缓存亲和优先，忙过头才让位给负载
Anyscale / Ray Serve
KVAwareRouter · 工业 详解 →		 算总欠账：给每个实例算一笔「还欠多少活」——没算完的 prefill token ＋ 正在 decode 占着的 KV 内存，加权合成一个数，发给欠账最少的。命中缓存只是从这笔欠账里「抵扣」掉一部分。 命中是打折券，真正比的是谁欠的活少
Lodestar
arXiv · 学术 详解 →		 让模型学：不手写公式，训练一个小模型（MLP）直接预测「发给它，首 token 要等多久」，选等得最短的。输入还是那几样（命中率、prefill/decode token 数），但「怎么组合」交给模型从线上数据里学。 不写规则，让模型学出该发谁

共同的结论只有一句：命中缓存只是「估计负载」的输入，不是路由的目标；目标始终是「把活分匀」。前三种是手写规则，区别只在把「命中」和「负载」捏合的方式（乘法 / 阈值 / 加权求和）；Lodestar 干脆不捏合，交给模型学。递进看，Anyscale 已经比 llm-d 更进一步——把 prefill 和 decode 合成一个总分数，而不是「二选一」；但这个总分数仍是一个标量，prefill 和 decode 两个维度的「饱和程度」被压成了一个数。把它拆成两个维度、各自建模的设计见 细粒度负载路由设计 →。

开放问题：现有工作的公共边界（下一步设计的入口）

  • 负载度量全是实例级聚合：token 总和 / 请求数 / batch size，看不到队列组成与预算稀释——「逐请求」一栏在上表空缺（→ 细粒度设计 →）。
  • 逐请求状态的跨副本同步无先例：连聚合 token 负载都只有最终一致（Dynamo 对 output-block 故意不同步），逐请求队列的同步成本更高。
  • prefill 成本被当成裸 token 数线性可加：未建模实测中的分段成本（45→93 μs/token）与 cache 折扣的交互。
  • 路由层与准入层割裂：只有 QUARTZ 在准入层做逐请求排序，路由层全部把次序交给引擎 FCFS——两层共享同一套逐请求状态的设计不存在。
贯穿性共识：Dynamo、llm-d、Ray Serve（KVAwareRouter，KV indexer 复用 Dynamo）、SGLang Router 多个工业实现，加上 LMetric（OSDI 26）、Llumnix（OSDI 24）两篇顶会论文，以及 Anyscale 官方博客的明确表述——「KV cache affinity is a proxy for load estimation, not the routing objective itself」——在「负载感知路由」上殊途同归：KV 重叠度只是负载估计的输入，真正的路由目标是让 token 负载均衡。
  • 学术侧核心会议：OSDI / NSDI / SOSP（系统方向）+ ICML（ML 系统方向）。
  • 最该精读的三篇：Llumnix（OSDI 24，动态重调度） 详解 →、LMetric（OSDI 26，乘法路由）、AlpaServe（OSDI 23，统计复用——虽归 C 类资源分配，但其「聚合实例吃掉负载波动」的容量视角对路由层设计最有启发，故列精读）。
  • 你目录里已有的：Lodestar、LMetric、QUARTZ、llm-d、Anyscale KV+token 路由博客——已覆盖「学习式」和「启发式」两条主线，与本次调研的 A 类高度重合，形成闭环。
