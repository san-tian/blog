细粒度负载路由设计：基于「逐请求 prefill 等待」

insight 路由策略设计 队列组成盲区

核心问题：计算负载时，现有方案用的都是实例级聚合指标（inflight token 总数、活跃请求数），看不到实例队列内部每个请求各自的 prefill 等待量。本文展开这个盲区，并设计一个基于逐请求细粒度负载的路由策略。全文前提已按 GLM-5.2 实测校准（α≈1.12 / 集中度 1.3× / cache 22×），并给出验证方案与适用域。

缺陷分析：路由策略在两个层次都太粗

把现有路由策略的缺陷拆成两个独立层次——它们叠加，就是「长 prefill + 长 decode 混合负载下路由失准」的根源。

缺陷 1：负载度量太粗（聚合 → 逐请求）

  • 现状：inflight token 总数、batch size、活跃请求数——都是聚合标量。
  • 缺陷：看不到队列组成——「谁挡在前面、挡多久」。
  • 症状：1×30k 大块头 vs 30×1k 碎片，聚合值一样——实测总成本差仅 ~1.3×，但预算被谁稀释、谁排在前面天差地别（见下节实测校准）。

缺陷 2：瓶颈被当作「二选一」，而非「统一度量」

  • llm-d 已经说对了一半：prefill-heavy（长 prompt，计算受限）和 decode-heavy（长输出，slot 受限）是两种性质不同的任务，该用不同的 load metric——prefill 看「在途未缓存 token」，decode 看「活跃请求数」（llm-d 称之为「瓶颈匹配」）。出处 →
  • 但它的解法是二选一：operator 先判定 workload 属于哪种瓶颈，再部署对应配置。llm-d 自己承认「没有一个配置能同时覆盖三种 workload」——瓶颈动态变化的混合负载下二选一失效，只能退回 latency-predictor（带训练开销）。
  • 缺陷的本质：把 prefill 和 decode 当成两个独立配置去切换，而不是综合成同一个 metric——一个能同时表达「计算维度和内存维度各自饱和度」的统一度量。这正是本文要做的。
一句话 gap：现有路由策略在「度量」和「瓶颈」两个维度都太粗——度量上只有聚合值（看不到队列组成），瓶颈上只有二选一或标量（无法同时表达 prefill/decode 两个维度的饱和度）。两者叠加，导致「长 prefill + 长 decode」混合负载下路由失准。解法：度量逐请求 + 瓶颈综合成同一个 metric。

两个缺陷的对应解方向

缺陷解方向本页对应
度量太粗（聚合）逐请求队列 W_i(r)「细粒度负载模型」+「新路由策略」
瓶颈二选一 / 压标量综合成同一个 metric：瓶颈向量 (P_i, D_i)「瓶颈向量路由」

实测校准：前提按 GLM-5.2 数据定标

本文初稿的动机建立在「长 prefill 阻塞队列」的直觉上。用实测数据校准后，这个直觉要降级——先摆数据，再重述真正站得住的动机（实测详情见 GLM-5.2 prefill 实测报告 →）：

直觉前提实测（GLM-5.2-fp8，DSA+MoE 架构）判定
prefill 成本 ∝ n（线性）α≈1.12；中段 ~45μs/token 平坦，>128k 回升到 93μs（2×）✅ 近似成立
长请求集中 → 成本平方级放大（O(n²) 直觉，曾有「30×」推演）1×300k vs 10×30k 总 prefill 仅 1.3×⚠️ 高估——DSA O(n·k) + chunked prefill 已把非线性抹平到温和超线性
长请求 prefill 期间，后续短请求等待暴涨后台 30k–240k（prefill 窗口 1.3–13.4s）时，短请求 TTFT 0.744–0.765s ≈ 空闲 0.768s⚠️ 未观测到——归因待裁决（多副本分流 or chunked prefill 插队），待单副本重测
cache 命中只是「折扣」896k prompt：命中 3.75s vs 未命中 83.38s = 22×✅ 最大量级效应，一阶项
校准后的动机（不依赖「堵队列」叙事，两种归因下都成立）：
  • 公理：FIFO 下逐请求信息 ≡ 聚合信息——引擎 FCFS 时「排前面的总剩余」就是聚合 inflight token，聚合指标完全够用。逐请求信息的全部增量价值 = 支持准入重排：把新请求插到比它短的请求后面，跳过 Σ_{j: c_j>c_r} c_j 的长请求工作量——这只有在 router 拥有准入队列时才可能（引擎只上报聚合值时，路由器无从重排）。QUARTZ 已在准入层做了逐请求 SJF+aging，「路由层与准入层共享同一套逐请求状态」的设计还不存在。
  • 预算稀释：聚合 token 指标看不到「预算被谁稀释」——chunked prefill 引擎每步只给 prefill B_i−d_i 的 token 预算，活跃 decode 越多 prefill 越慢；两个聚合 token 数相同的实例，(B−d) 可以差数倍。这是聚合指标的真盲区，与「堵队列」是否发生无关。
  • 量级排序决定设计重心：cache hit（22×）是一阶项 >> 集中度（1.3×）与长段非线性（2×）。逐请求细粒度是二阶修正，主战场在「高利用率 × 长短双峰 × 低局部性」的交集负载。

你的 insight：聚合负载指标的「队列组成盲区」

现有路由策略计算负载时，看到的都是聚合值：

方案负载指标粒度
llm-d token-loadin-flight 未缓存 token 数实例聚合
LMetricbatch size实例聚合
Dynamotoken 负载（剩余 prefill + 活跃 decode）实例聚合
Lodestarinflight prefill/decode tokens、running/queued 数实例聚合

聚合值的致命盲区：同样的聚合数字，队列组成可以完全不同，新请求的实际等待时间也完全不同。

一个反例（按实测定标）：两个实例，聚合 inflight prefill 都是 30k token，但——
  • 实例 A：1 个请求剩 30k prefill（一个"大块头"在算）。
  • 实例 B：30 个请求各剩 1k（prefill 都在收尾），队列里还有几十个活跃 decode。
按 GLM-5.2 实测，两者「总 prefill 成本」只差 ~1.3×（近线性）——反例的威力不在总量差，而在瓶颈维度差：
  • 到 A：新请求排在大块头后面等它算完（无 chunked prefill 的引擎上这是独占窗口）；
  • 到 B：prefill 总量小，但几十个活跃 decode 把每步预算稀释到 B−d，单步变慢、KV 压力高。
「总共多少 token」掩盖了「预算被谁稀释、谁挡在前面」——这是聚合盲区的准确表述。

细粒度负载模型：把实例负载拆成「逐请求队列」

把实例的负载从"一个聚合数"升级为"一个有序的逐请求队列 + 引擎预算状态"：

Q_i = [ (r_1, c_1, s_1), (r_2, c_2, s_2), ..., (r_k, c_k, s_k) ]  +  ( B_i, d_i )

  c_j = 请求 j 的剩余 prefill 成本（token 数，考虑 KV 命中后还需新算的；
        >128k 长段按实测成本曲线折算 45→93 μs/token）
  s_j = 请求 j 的状态（prefill 中 / 排队中 / decode 中）
  B_i = 引擎 max_num_batched_tokens（每步 token 预算）
  d_i = 活跃 decode 请求数（决定 prefill 每步实际可用预算 B_i − d_i）

四个关键字段：

  • c_j（剩余 prefill 成本）：LMetric 已经证明该用"需新算的 prefill token 数"（而非命中率）——这里把它细化到每个请求。
  • 逐请求而非聚合：这样才知道"排在新请求前面的具体是哪些请求、各剩多少"，而不是只知道"总共还剩多少"。
  • 动态更新：c_j 随 prefill 推进递减，prefill 完成后请求转入 decode（对后续 prefill 不再构成阻塞）。
  • (B_i, d_i) 是队列之外的第二半状态：只有逐请求视图能同时回答「排在前面的是谁」（→ W_i(r)）和「decode 把预算稀释到多少」（→ B_i−d_i）——两半合起来才是完整负载。

新路由策略：最小化「新请求的期望 TTFT」

路由目标从"平衡聚合负载"改为"最小化新请求的期望 TTFT"——期望 TTFT 由逐请求队列 + 引擎 token 预算模型算出。

设计第一原则（公理）：若引擎 FCFS 且路由器不做准入重排，则 W_i(r) = 队列全部剩余 prefill 之和 = 聚合 inflight token——逐请求信息退化为聚合信息，模型零增益。因此本设计的第一承诺是 router 拥有准入队列（请求在路由器侧排队/派发时即确定次序）：重排策略是核心自由度，也是逐请求信息唯一的变现方式。

打分公式（引擎保真版：token 预算调度模型）

steps(r → i) ≈ ( Σ_{j ∈ ahead(r)} c_j  +  c_r ) / max(B_i − d_i, 1)
TTFT(r → i)  ≈ steps(r → i) × t_step(d_i, kv_i)

  ahead(r)   = 准入重排后排在 r 前面的请求集合（由下表策略决定）
  B_i − d_i  = chunked prefill 每步分给 prefill 的 token 预算（活跃 decode 越多越少）
  t_step     = 单步时长，随 decode 批与 KV 压力变化；
               GLM-5.2 实测 45–93 μs/token 曲线可直接作 lookup 常数
  • c_r：新请求自己的 prefill 成本（输入 token − 命中 KV 的 token，长段按成本曲线折算）。
  • Σ_{j∈ahead(r)} c_j（即 W_i(r)）：排在 r 前面的剩余 prefill 之和——这才是"r 实际要等多久"的精确度量，也是聚合指标算不出来的部分。
  • 对比简化式 TTFT ≈ (W_i(r) + c_r) / throughput（吞吐常数假设）：本式把两处失真显式建模——分母的预算稀释（decode 挤占 prefill 预算，聚合 token 指标完全看不到）与分子的成本非线性（c_j 按分段成本折算，而非裸 token 数）。
  • 路由决策：选 TTFT 最小的实例（配 K=2 随机候选防 herding）。

「排在 r 前面」由队列重排策略决定——这是设计的核心自由度

重排策略W_i(r) 的计算效果
FIFO（不重排）r 排队尾，W = 队列里全部剩余 prefill 之和等价于聚合指标（退化为 llm-d 的 inflight token），无新增信息
SJF（短请求插队）r 排到所有比它短的请求之后、比它长的请求之前：ahead(r) = {j: c_j < c_r}，W = Σ_{c_j<c_r} c_j短请求等待大幅缩短；长请求可能饿死，需 aging 兜底
分位感知（QUARTZ 式）用每个请求的 prefill 分位（而非精确值）排序对不确定性的鲁棒性更好

关键：FIFO 下逐请求信息没有新增价值（退化成聚合）；逐请求信息的价值在于支持队列重排（SJF/分位）——而这正是 QUARTZ 在"准入层"已经做了、但"路由层"还没做的事。

瓶颈向量路由：把 prefill/decode 综合成同一个 metric（缺陷 2 的解）

缺陷 2 的解方向：把 prefill 和 decode 两个维度综合成同一个 metric——用二维向量 (P_i, D_i) 表达，而不是二选一或压成标量。

实例状态 = 瓶颈向量

实例 i 的状态 = (P_i, D_i)
  P_i = prefill 饱和度（计算维度）
  D_i = decode 饱和度（内存/带宽维度）

新请求冲击 = 冲击向量

请求 r 的冲击 = (c_r, m_r)
  c_r = prefill 冲击（需新算 token，瞬时计算）
  m_r = 内存冲击（KV cache 大小 ≈ 总 token 数，长期占用）

关键：不同请求对两个维度的冲击不同——长 prefill 请求 c_r 大、m_r 小；长 decode 请求 c_r 小、m_r 大。这正是标量 score 表达不了的。

路由决策（方向性示意，但有两个未解决问题）

cost(r → i) = max( P_i + c_r / C_i,   D_i + m_r / M_i )

# C_i、M_i = 实例 i 的计算 / 内存容量
# 取 max：任一维度超载都会拖垮实例（木桶原理），选 cost 最小的实例
这个 max 公式有两个未解决的问题（诚实标注）：
  • 时间常数不一致：P_i 是瞬时量（毫秒–秒级，随 batch 组成每步刷新）；D_i 是持久量（请求生命周期级，KV 占用要到完成/驱逐才释放）。把秒级快照和生命周期水位放进同一个 max 做代数比较，「统一度量」目前是伪统一。
  • m_r 的输出长度未知：m_r ≈ (prompt_len + Q̂_out) × per-token KV bytes，而 Q̂_out 路由时不可知——只能 max_tokens 封顶（保守，系统性高估长输出请求）或 QUARTZ 式分位预测（精细，有误差）。per-token KV bytes 可从引擎 config 算出（MLA 压缩到 512 维后极小，GLM-5.2 即此类）。

修正方案：两段式（推荐）或三方消融（保留 max）

方案机制代价
两段式（推荐）D 做硬准入：D_i + m_r/M_i > 阈值（如 0.9）的实例直接出局——与 llm-d 的 τ 过滤同构，且用的是 D 的正确时间常数；P 做等待最小化：幸存实例按 steps(r→i) 排序。两个维度各用各的调度语义，不做伪统一。多一个阈值（KV 容量 × 安全水位，可推导）
保留 max 形态作为「统一度量」假说保留，但必须与乘法基线（LMetric：新算 token × (BS+1)）、加权和基线做三方消融，证明 max 的额外增益若消融打平，max 只是又一个待调参的归约，应舍弃
两个缺陷的解是天然互补的：瓶颈向量 P_i 的精确值，正是逐请求队列的 Σ c_j / C_i——「度量细粒度」（逐请求队列）提供了精确的 P_i，「维度细粒度」（向量化）保证 P_i 和 D_i 不被压成一个标量。在两段式修正下：P 由逐请求队列精确给出，D 由硬准入过滤——互补关系不变，只是不再假装它们能压进同一个 max。

算法谱系与依据：这个设计基于哪些旧指标

严格说，这个设计没有发明新指标——它是几个「已有旧指标/旧方法」的细粒度组合。逐组件追溯：

本设计的组件直接继承的旧指标/方法来源
c_j / c_r：逐请求的「剩余 prefill 成本（token 数）」 LMetric 的「需新算的 prefill token 数」（KV 指标，而非命中率） LMetric（OSDI 26）
W_i(r)：排在 r 前面的成本之和 llm-d / Lodestar 的「inflight prefill token 总和」，拆成「逐请求前缀和」 llm-d token-load；Lodestar
路由目标：最小化期望 TTFT 排队论 JSQ（join the shortest queue）的 LLM 化——把「最短队列」换成「最短剩余工作量」 经典排队论（见下）
队列重排：SJF + aging QUARTZ 的准入队列（逐请求分位成本 + SJF + λ·a_r aging） QUARTZ（ACL 26 findings）

概念来源：经典调度理论（注意：结论不能直接套用）

  • SRPT 最优性：单机、已知处理时间下，SRPT（最短剩余处理时间优先）最小化平均响应时间。来源：Schrage & Miller, "The Queue M/G/1 with the Shortest Remaining Processing Time Discipline", Operations Research 14(4):670–684, 1966。 DOI →
  • SPT（Smith 规则）：最短处理时间优先最小化平均等待时间。来源：W. E. Smith, "Various Optimizers for Single-Stage Production", Naval Research Logistics Quarterly 3(1-2):59–66, 1956。 DOI →
  • Size-based dispatching：按 job size 路由 + size-aware 排序。来源：Harchol-Balter, Schroeder, Bansal, Agrawal, "Size-Based Scheduling to Improve Web Performance", ACM TOCS 21(2), 2003。 论文 →
这些经典结论在 LLM 推理场景下假设不成立，只能当「概念来源」、不能当「理论依据」：
  • 「处理时间已知」只对 prefill 成立：SRPT/SPT 假设 job size 到达即知；LLM 里 decode 长度不可预测（用户随时停），只有 prefill 的「需新算 token」可估计。
  • 「可抢占且无成本」不成立：SRPT 依赖免费抢占；LLM 里抢占 = 丢弃/换出 KV cache，代价不小。例外：Llumnix（OSDI 24）的 live migration 把「迁走一个请求」的代价压到 ~20–30ms 且与序列长度无关（KV append-only + 多阶段流水线），部分恢复了抢占式调度的设计空间——详解 →。
  • 「服务时间外生」不成立：经典模型里 job 处理时间与调度无关；LLM 里 batching 让处理时间内生（取决于和谁同批）。
  • 「size 不随服务器改变」不成立（最关键）：经典 size-based 里同一 job 到处一样；LLM 里 size = KV 命中后需新算 token，因实例缓存状态而异——这正是 KV 感知路由存在的原因，也是经典结论失效的根源。
  • 「最小化平均」目标不匹配：SRPT/SPT 优化平均响应时间；LLM 要的是尾延迟（P99 TTFT）和 SLO 达成率，SRPT 甚至会恶化长请求的尾延迟。
所以：这些文献的价值在于提供正确的概念框架 + 「短任务优先」的普适直觉；真正可直接作为依据的前身是 QUARTZ——它已经用「分位预测」处理了「处理时间未知」、用「aging」处理了「短任务优先的公平性」，这两个正是经典文献没解决、而 LLM 场景必须解决的问题。
一句话谱系：
经典调度理论（JSQ 路由目标 + SPT/SRPT + size-based dispatching，作为概念来源，结论见上限定）
→ LLM 系统的旧指标（LMetric 的需新算 prefill token、llm-d/Lodestar 的 inflight token 总和、QUARTZ 的逐请求准入队列）
→ 本设计（把这些旧指标的粒度统一推进到「逐请求」，路由层直接算 W_i(r) 而非聚合值）。
所以它不发明新指标，真正的增量只有一处：把「队列总成本」换成「排在 r 前面的成本之和」（逐请求前缀和），以及把 QUARTZ 的准入层逐请求机制提前到路由层。

和现有方案的关系：把 QUARTZ 的准入粒度提前到路由

这个设计不是凭空发明，而是把几篇论文的边界往前推一步：

方案路由层（选实例）用什么准入层（排顺序）用什么
LMetric聚合 batch size × 新请求 prefill无（交给引擎 FCFS）
llm-d聚合 inflight token / 活跃请求无（粘性 + 饱和释放）
QUARTZ聚合 Ŵ + 新请求分位（K=2 候选）逐请求分位 + aging + 公平（SJF 类）
本设计逐请求队列（精确 W_i(r)）同一套逐请求队列（路由 + 准入统一）
一句话定位：QUARTZ 已经证明「逐请求成本 + SJF + aging」在准入层能降尾延迟；本设计把它提前到路由层——路由决策直接看"插进这个实例的逐请求队列后，新请求要等多久"，而不是看聚合的 inflight 数。同时把 QUARTZ 的"分位预测"（有误差）升级为"逐请求精确队列"（无预测误差，代价是状态维护）。

与学习式预测器的关系：解析骨架 + 学习残差

LMetricPlus 的设计（XGBoost 预测 TTFT + blitz-router 执行）常被看作与本文「解析公式」竞争的另一个方案。不是——它们是同一方案的两层：

层职责冷启动 / 数据积累后
解析骨架（本文）steps×t_step 调度器模型给出先验预测；同时定义特征集：W_i(r)、前方长请求工作量 Σ_{c_j>c_r} c_j、B_i−d_i、命中折扣——学习式模型的特征就是解析模型的组成部分零训练，新实例/新负载立即可用；始终作为兜底
学习残差（LMetricPlus）XGBoost 只学解析模型没覆盖的部分：多租户干扰、t_step 漂移、未建模的引擎行为数据积累后逐实例接管置信度；残差小 → 退回解析先验
一句话：解析模型负责「结构」（机制上必然成立的项），学习模型负责「残差」（机制外干扰）。骨架不学习、残差不发明——两层拼起来才是可部署的完整方案，而不是两个竞争设计。

打分公式的两种实现（精确 vs 分位）

实现 A：精确逐请求队列

steps(r → i) = ( Σ_{j: c_j < c_r} c_j  +  c_r ) / max(B_i − d_i, 1)   # SJF：比 r 短的先走，r 只等它们
TTFT(r → i)  ≈ steps × t_step(d_i, kv_i)

优点：精确，无预测误差。缺点：需要实时维护每个实例的逐请求队列（成本动态递减、完成即移除），且多实例路由时这个状态的跨副本同步更难。

实现 B：分位逐请求队列（QUARTZ 的细粒度版）

用 Q̂_prefill_α(r_j) 替代精确 c_j，其余不变

优点：对成本估计误差更鲁棒。缺点：分位预测本身有误差（QUARTZ 用决策树 + pinball loss）。

挑战与代价（诚实标注）

  • 状态维护成本：路由器要实时追踪每个实例里每个请求的剩余 prefill（c_j 动态递减）。落地不需要改引擎——router 侧影子记账：按 admission / first-token / 完成 / 取消事件维护队列进出与 c_j 递减（Anyscale KVAwareRouter 已按请求生命周期更新聚合负载，同一事件流升级为逐请求即可）；yaullm 已有 step-level SSE，逐请求进度有现成通道。
  • 跨副本同步：多实例路由下逐请求队列的同步比聚合值更难。建议单 router 起步（状态天然一致），多 router 时接受最终一致的逐请求队列（短暂分歧可接受，Dynamo 对 output-block 的处理同款）。
  • SJF 的公平性：短请求插队会让长请求饿死，必须配 aging（QUARTZ 的 λ·a_r 项）——现成解法。
  • t_step 不是常数：token 预算模型已显式处理主项（B_i−d_i 稀释）；剩余波动（KV 压力、专家路由不均）用实测成本曲线 lookup 打底，残差交给学习层。
  • 突发同步冲击（herding）：同一窗口到达的多个请求会算出同一个「最优实例」挤过去——需要 power-of-two（K=2 随机候选，QUARTZ 同构）或小抖动打散。
  • 预期效应量级（最重要的一条）：cache hit 22× 是一阶项，逐请求细粒度是二阶修正。适用域 = 高利用率 × 长短双峰 × 低局部性的交集——低利用率下队列本来空，负载单峰时聚合够用。验收线应对齐 P99 TTFT 降幅 ≥10%，而不是乘法级的戏剧性收益。

验证方案：先测预测精度，再谈端到端

这个设计能否成立，取决于两个可分离的问题：① 模型准不准（W_i(r) + steps×t_step 能否预测真实 TTFT）和 ② 收益大不大（用预测做路由，P99 比基线好多少）。①是②的前置，顺序不能反。

步骤做法通过标准
第一步 · 预测精度trace 回放：固定路由决策，对比模型预测 TTFT vs 实测，按（短/长请求 × 高/低 d_i）分桶看误差中位相对误差有界（如 <30%）；长段误差用成本曲线 lookup 收敛
第二步 · 端到端 A/B基线族：RR / JSQ / 聚合 token（llm-d 式）/ LMetric 乘法 / sticky-until-saturated；负载用长短双峰 + 低局部性合成P99 TTFT 降幅 ≥10%（LMetricPlus 验收线）

消融（证明每个机制各自挣到钱）

  • −重排：准入退回 FIFO——验证「逐请求信息」本身的贡献（公理预言：FIFO 下与聚合基线打平，消融可裁决）；
  • −预算稀释：分母换回常数吞吐——验证 (B_i−d_i) 项的贡献；
  • −D 硬准入：去掉两段式第一段——验证 D 维度过滤的贡献。

最小隔离实验（单 GPU，可控负载，先于端到端）

  • A1 单副本复测忙等待（pin 副本 + 流式 TTFT）——裁决实测报告图 5 的归因（chunked prefill 插队 vs 多副本分流）；
  • A2 chunked prefill 开/关对照；
  • A3 预算稀释扫描：固定 Σc，扫 d_i，直接验证 steps×t_step 模型——本设计的核心方程；
  • A4 1.3× 集中度实验的并发版。

待验证的开放问题

  • 验证顺序：先测 W_i(r)+steps×t_step 的预测精度（trace 回放、分桶误差），再谈端到端收益——预测不准，路由收益免谈（见上节验证方案）。
  • 二阶修正够不够：在 cache hit（22×）主导的一阶效应下，逐请求细粒度在真实 trace 上能再拿多少 P99？适用域假设（高利用率 × 双峰 × 低局部性）需要用真实负载分布验证。
  • SJF 重排 vs FIFO（路由层）：QUARTZ 在准入层的答案是"值得"；公理预言路由层若不做准入重排则收益为零——端到端差异是否恰好等于「准入重排的贡献」，用 −重排 消融即可裁决。
  • 和 KV 命中的交互：c_r 已扣掉 KV 命中，但新请求的 prefill 会改变 KV 状态、影响后续请求的成本（二阶效应）——是否需要建模待定。
  • 两段式阈值的泛化：D 硬准入阈值（KV 容量 × 水位）跨引擎/跨模型（MLA vs MHA 的 per-token KV bytes 差异巨大）如何自动标定？

一句话总结

完整的 gap 是「双重粗粒度」，但动机按实测定标：度量层面只有聚合值（看不到队列组成与预算稀释），瓶颈层面只有二选一或标量；实测表明「堵队列」叙事不成立（集中度仅 1.3×、忙碌等待未升高），真正站得住的是两个机制：
① 准入排序——router 拥有逐请求队列，SJF + aging 让 W_i(r) 兑现（公理：FIFO 下逐请求信息退化为聚合，重排是唯一变现方式）；② 预算稀释——steps ≈ (Σ_{j∈ahead} c_j + c_r)/(B_i − d_i)、TTFT ≈ steps × t_step，把 chunked prefill 的调度语义显式建模。
③ 瓶颈向量改两段式——D 硬准入（时间常数正确）+ P 最小化，替代量纲不一致的 max；④ 与学习式统一——解析骨架（零训练冷启动 + 天然特征集）+ 学习残差（XGBoost 修干扰）。
量级预期要诚实：cache hit 22× 是一阶项，逐请求细粒度是二阶修正；适用域 = 高利用率 × 长短双峰 × 低局部性；验收 = 预测精度先行，P99 降幅 ≥10%。
