GLM-5.2 prefill 实测报告

endpoint: http://38.255.28.13:10100 · glm-5.2-fp8 · 冷缓存 / 随机独立内容 / 每点 2 次取中位数 · 2026-08 实测
核心结论 1

prefill 随 prompt 长度呈弱超线性增长

α ≈ 1.12

实测 prefill ∝ n1.12（弱超线性）：每 token 成本中段稳定 ~45μs，长段（>128k）回升到 93μs。架构上，GLM-5.2 用 DSA 稀疏注意力 + MoE，attention 复杂度为 O(n·k)。

核心结论 2

300k×1 与 30k×10 的总 prefill 接近

1.3×

实测 1×300k ≈ 17s、10×30k ≈ 13s，比值 1.3×。对比之下，cache hit 的影响（22×）远大于长度的影响。

⚠️ 待重测（下次看到这条，先跑 5 分钟探针）

图 5 的 null 结果无法归因：这是共享多租户 endpoint，短请求只有 1/N 概率与长请求落在同一副本——「短请求没变慢」既可能是 chunked prefill 插队，也可能只是被分流到空闲副本。单副本 SGLang 默认配置（FCFS + chunked prefill）下若真同副本，短请求应等待 ~10s 量级而非 0.74s，所以「无影响」更可能是分流假象。结论 1/2（α≈1.12、1.3×、22×）不受影响，可作方向性证据。

实验环境

GLM-5.2 关键架构（config.json）：glm_moe_dsa，256 路由专家（每 token 激活 8+1）， DSA 稀疏注意力 index_topk=2048，MLA（KV 压缩到 512 维），78 层，1M 上下文。 这些架构让 prefill 的 attention 是 O(n·k) 而非 O(n²)。

方法论教训（3 条）

#教训踩坑表现
1构造 prompt 必须用随机独立内容，不能重复重复文本让长 prompt 前缀命中缓存，prefill 低估 ~22 倍
2必须测冷缓存（每个 prompt 第一次请求）同 prompt 第二次请求命中前缀缓存，加速数倍
3必须多次测量取中位数多租户共享服务单次测量有 2~4 倍噪声（曾出现 5.2s、23.2s 异常值）

脚本与复现

python3 scripts/cold_prefill_test.py prefill   # prefill vs 长度（拟合 α）
python3 scripts/cold_prefill_test.py cache     # cache hit 影响
python3 scripts/cold_prefill_test.py busy      # 忙碌节点等待（图5 归因待重测，见顶部提醒）
多租户共享 endpoint，绝对秒数会漂移，结论以相对形状（斜率、比值）为准；定案需在独占 GPU 复测。
