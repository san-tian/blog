格式层确认 · 最后请求失败 · 归属：格式（换取法）/ 全失败→丢弃 · 深究主文档 §3 修法①

最后请求失败（无应答）MAX_BY 取最新不问有效性——失败请求也在 dwd 里有行

末尾请求 resp 为空；全失败 session 数量待修后对账（验收 V4）
机制失败请求在 dwd 也有行——网关记了请求（request_body 正常，完整历史），上游失败时 response_body 是错误 JSON（不是空），解析不出 choices → resp_choices = NULL。实测（pt=2026083000 单小时）：200 共 14,626 条，502 × 13、400 × 1——502 的响应体是 {"error":{"code":502,"message":"Upstream access forbidden…","type":"upstream_error"}}。
tsreq_messagesresp_choices说明
100第 1 轮历史第 1 轮应答成功
200第 2 轮历史第 2 轮应答成功
300第 3 轮历史（最新最全）NULL上游 502 → 响应体是错误 JSON，解析不出 choices
MAX_BY 的关键误区：它不是「取最后一个非空的值」，是「取时间最新那一行的值」——那行恰好是 NULL 就拿到 NULL，不会回退到上一行：MAX_BY(resp_choices, ts) = 第 3 轮的 NULL，而不是第 2 轮的应答。
背景：session 有 3 次请求，第 3 次失败（resp 是错误 JSON → 解析出 resp_choices = NULL）
现状 ❌
MAX_BY(req_messages, ts) → 第 3 次的历史（最新，但它的 resp 拼不上）→ 缺口
修复后 ✅
行级 WHERE 排除无应答请求（resp_choices IS NOT NULL AND != '' AND != '\N'）
→ 两个 MAX_BY 落在同一个最后有效请求上（历史+应答天然配对，不会错配）
→ 少最后一轮（那轮本来就没答），但结构完整闭环；全 session 失败 → 整行消失
为什么前两轮天然在：客户端每次重发全量历史——ts=200 那行的 req_messages 本来就装着第 1+2 轮完整对话
第 3 轮整轮丢（含它的 user message）：没得到应答，保留就是"有问无答"的尾巴（不闭环）
三问判定：① 部分在 ✓（最后交换缺一半，但前一次有效交换在）→ 换取法（取最后有效交换）= 格式·修；全 session 失败 → ①✗ → 格式层丢弃。副作用（正向）：COUNT(*) 变成有效轮数。
验收 V4：chat 源行数下降量 = 无应答 session + 续话碎片，可解释
这个行级 WHERE 同时是 P0-1 修法①的组成部分（CTE 里加），一改两得。
