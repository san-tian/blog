RBG 讲解 · sgl-project/rbg @ 4acd5a7 · v0.7.0

RBG（RoleBasedGroup）把多角色 LLM 推理服务当『一个有机体』编排的 Kubernetes Operator

  • 一句话：SGLang 项目开源的 K8s Operator（Go，Apache-2.0），把 PD 分离推理服务的部署拓扑、启动顺序、跨角色协同、服务发现、gang 调度全部声明式接管

01 · 痛点

原生 K8s 原语，编排不了一个 PD 分离服务

① 多角色拓扑gateway → router → prefill → decode 是一个服务的四个角色。Deployment/StatefulSet 各管各的：谁先启动、谁跟谁配对，原生没有这个语义，只能 init container / Helm hook 人肉拼
② 性能敏感GPU 亲和（NVLink → PCIe → RDMA → VPC）、跨角色共置，直接决定 KV 传输带宽。原生调度器对推理服务的拓扑语义一无所知
③ 跨角色操作不原子滚动升级 prefill 全换完、decode 还是旧版 → 中间态版本漂移（KV 传输协议可能不兼容）；扩容 prefill 扩了 decode 没跟上 → 容量失衡
  • RBG 的解法：整个服务声明成一个对象 RoleBasedGroup，角色间协同是控制器语义，不是人肉胶水
  • 来源：README「Why RBG?」
02 · 核心抽象

一个 CRD，四层对象 RoleBasedGroup → Role → RoleInstanceSet → RoleInstance → Pod

配角对象（控制器自动建）每角色 headless Service（服务发现）· ControllerRevision（版本）· PodGroup（gang 调度）· ScalingAdapter（HPA 挂钩）· CoordinatedPolicy（独立 CRD，跨角色协同）
出处
doc/reference/api.md · doc/features/multiroles.md
03 · 部署模式

三种 pattern：一个 role 怎么组织自己的 pod

  • 同一个 RoleBasedGroup 里不同角色可用不同 pattern：router 用 standalone，prefill/decode 用 leader-worker——一个 YAML 混搭
  • leader-worker 是为大模型 TP 设计的：size: 4 = 1 leader + 3 worker，配合注入的环境变量自动组网（下下页）
  • 出处：doc/features/patterns.md
04 · 服务发现

三件套免手写 DNS：headless Service + 环境变量注入 + 组件发现注解

  • 服务名 s- 前缀是故意的：DNS-1035 要求服务名不能以数字开头（helper.go:106-119）
  • ③ customComponentsPattern 还有组件发现注解（把同实例某组件的 FQDN/端口注入为环境变量）+ 端口分配器注解（component_discovery.go）
  • 官方 README 称之为 topology self-aware service discovery：容器里不需要硬编码任何对端地址
05 · 实战走读

SGLang PD 分离：一个 YAML，三个角色，全部自动接线

# examples/inference/pd-disagg-leader-worker.yaml（节选，角色间无任何手工 Service）
roles:
- name: router                     # standalone × 1
  - --prefill "http://pd-disagg-lws-prefill-0.s-pd-disagg-lws-prefill:8000"   # ← headless DNS 寻址 prefill leader
  - --decode   "http://pd-disagg-lws-decode-0.s-pd-disagg-lws-decode:8000"

- name: prefill                    # leader-worker × 2 实例，size 4（TP4）
  rolloutStrategy: { type: RollingUpdate, rollingUpdate: { type: InPlaceIfPossible, maxUnavailable: 1 } }
  leaderWorkerPattern:
    size: 4
    template:                      # SGLang 启动参数全用注入变量：
      - --dist-init-addr $(RBG_LWP_LEADER_ADDRESS):6379
      - --nnodes       $(RBG_LWP_GROUP_SIZE)      # = 4，组网自动完成
      - --node-rank    $(RBG_LWP_WORKER_INDEX)   # leader=0，worker=1..3

- name: decode                     # leader-worker × 4 实例，size 2（TP2）
  restartPolicyConfig: { type: None }   # 实例内生命周期交给 RBG 管
routerstandalone ×1 · 入口路由 + PD 分发 · 纯 headless DNS 寻址
prefill2 实例 × TP4（1 leader + 3 worker）· 独立 rollout 策略
decode4 实例 × TP2 · 与 prefill 异构配比（2:4）
完整文件：examples/inference/pd-disagg-leader-worker.yaml；同目录还有聚合推理、单卡、Dynamo、Mooncake（SGLang + vLLM）样例 · 顶部注意 scalingAdapter 开启后 HPA 用的 RoleBasedGroupScalingAdapter 由控制器自动创建
06 · 启动顺序

角色依赖：拓扑排序，分层推进 不 ready 就不创建下一层

  • YAML 里就是一行：dependencies: ["frontend"]——backend 等 frontend Ready 后才创建
  • 源码链：SortRoles（拓扑排序） → reconcile 主循环逐层 CheckDependencyReady
  • 循环依赖、依赖不存在的角色名 → 校验直接报错（webhook + preCheck）
07 · 跨角色协同

CoordinatedPolicy：prefill 和 decode 锁步升级 独立 CRD，管 maxSkew

# 独立 CRD，挂在要协同的角色上（不侵入 RoleBasedGroup 本体）
apiVersion: workloads.x-k8s.io/v1alpha2
kind: CoordinatedPolicy
spec:
  policies:
    - name: prefill-decode-rollout
      roles: [prefill, decode]
      strategy:
        rollingUpdate: { maxSkew: "1%", maxUnavailable: "10%" }
  • 管两件事：协同滚动更新（maxSkew / maxUnavailable）和协同扩缩（角色按配对比例一起扩；进度推进可选 OrderScheduled 等档位——调度成功即算推进，快但风险高）
  • 出处：doc/features/coordinated-policy.md
08 · 更新策略

原地更新（In-place Update）：升级不换"壳" pod 身份不变，只重启容器

策略行为
RecreatePod重建 pod（传统行为）
InPlaceIfPossible能原地就原地（改镜像→只重启容器），不行再重建 ← 推理负载默认选这个
InPlaceOnly只允许原地，否则报错
作用单元是 RoleInstance（pod 组整体升级）；定义在 rolebasedgroup_types.go:108-116 · 官方演示（改镜像后 RESTARTS+1、AGE 连续）见 doc/features/instance.md
09 · 调度

性能两板斧：gang 调度 + 独占拓扑

  • 两条都是一个注解的事：声明在 RoleBasedGroup 上，控制器翻译成 PodGroup / pod 亲和规则，用户不用碰调度器配置
  • 出处：doc/features/gang-scheduling.md · doc/features/exclusive-topology.md
10 · 控制器

reconcile 链条走读 RBG → 依赖排序 → 逐角色 RoleInstanceSet → RoleInstance → Pod

  • 三层各管各的：RBG 控制器管组（依赖、gang、协同），RoleInstanceSet 管角色（实例集合），RoleInstance 管实例（pod 组）
  • 每角色还顺带 reconcile 一个 ScalingAdapter（HPA 直接挂它，实现每角色独立伸缩）
  • 完整链：rolebasedgroup_controller.go:475-580（行号锚定 commit 4acd5a7）
11 · 生态位

每一层管一个维度：RBG 不是替代 LWS，是在它上面加一层

SGLang同门项目，RBG 头号场景就是 SGLang PD 分离部署
NVIDIA Dynamo数据中心推理编排栈，官方提供 Dynamo 运行时集成样例
MooncakeKV cache 传输/复用引擎；SGLang 与 vLLM 的集成样例都有

12 · 版本与迁移

v0.4 → v0.7：一年四级跳 v1alpha2 已 stable

⚠ 迁移注意v1alpha1 及其 Deployment/StatefulSet/LeaderWorkerSet workload 类型已被 v1alpha2 + RoleInstanceSet 取代。chart 值 deprecatedWorkloadTypes.enabled：true（默认，两代共存，存量部署必须保持）/false（彻底拒绝废弃类型，仅限全新安装——已在跑的集群没有官方支持的关闭路径，对象会无人 reconcile）
依赖变轻v0.7.0 起不再要求安装 LWS CRD（自带 RoleInstanceSet）；K8s 要求降到 ≥ v1.22；转换 webhook 处理 v1alpha1 ↔ v1alpha2
  • 官方迁移指南（v1alpha1 → RoleInstanceSet）承诺后续版本提供，存量用户先保持 true 等文档
  • 来源：README「Latest News」「Deprecated workload types」「Version Compatibility」
13 · 总结

三句话 + 证据索引

① 是什么SGLang 项目的 K8s Operator：一个 RoleBasedGroup CRD 声明整条多角色推理链路（router/prefill/decode/…），角色依赖、协同更新、服务发现、gang 调度全是控制器语义
② 换来什么部署从「N 个 YAML + Helm hook + 人肉 DNS 约定」压缩成「一个 CRD + 一组注解」；代价是接受一个新的 workload 抽象层（RoleInstanceSet 等 v1alpha2 API）
③ 什么时候用多角色推理拓扑（PD 分离 / router+engine / engine+KV 传输）、TP 多卡组、需要跨角色协同升级或配对扩缩——单体推理一个 Deployment 就够，不要为了用而用
  • SGLang / Dynamo / Mooncake 生态用户是第一受益人：官方例子 + planner + runtime + CLI 全套现成
