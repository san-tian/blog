RBG（RoleBasedGroup）在 Kubernetes 上部署大模型推理服务的『总管』

先统一词汇 读不懂任何一页时，翻回这页

Kubernetes（K8s）容器编排系统：把「哪些程序跑几份、各用多少资源」声明成 YAML，集群负责持续拉起和维持
Operator / CRDOperator 是用自定义控制器扩展 K8s 的模式；CRD（自定义资源定义）是注册新对象类型的机制——RBG 就是装进 K8s 的一套新对象 + 控制器
prefill / decode / PD 分离术语索引已登记（首次详解见 pd-decode-kvcache-offload.md），本篇直接使用；部署编排视角的展开见第 4 页
TP（张量并行）一个大模型由多张 GPU 协同计算；1 个 leader + N 个 worker 组成一个推理实例
headless Service不分配虚拟 IP 的 K8s Service：DNS 直接解析到每个 pod，pod 名稳定、可直接按名寻址
gang 调度一组 pod「要么全部调度成功，要么全部不调度」，避免 8 卡只上 7 卡白占资源
原地更新改镜像只重启容器、不重建 pod——名字 / IP / 节点 / GPU 绑定都不变
名词约定（全文统一）「角色」= 服务成员（router / prefill / decode）；「实例」= 角色的一副本（可能是一组 pod）；「组件」= 实例内的单个 pod（leader / worker）
术语遵循 glossary.md 跨文章复用：讲过的引用不重复解释，本页新讲的（K8s / Operator / TP / headless Service / gang / 原地更新）发布后登记；PD 概念图解：doc/quick_start.md · README（角色/实例定义）
第 1 层 · 它是用来做什么的

管『一个服务里的多个角色』：先看最小例子

原生 K8s 写法frontend、backend 各一个对象。backend 要等 frontend 就绪再起？原生没有这个语义——init container 探测、Helm hook、或手动分两次 apply，怎么土怎么来
RBG 写法一个 YAML、一个对象。dependencies: ["frontend"] 一行，backend 等 frontend Ready 后才创建
apiVersion: workloads.x-k8s.io/v1alpha2
kind: RoleBasedGroup            # 一个对象 = 一组角色 + 它们的关系
metadata:
  name: nginx-cluster
spec:
  roles:
    - name: frontend
      replicas: 1
      standalonePattern: { template: { spec: { containers: [{ name: nginx, image: nginx:1.14.1 }] } } }
    - name: backend
      replicas: 3
      dependencies: ["frontend"]   # ← 顺序语义：frontend Ready 之前，backend 根本不会被创建
      standalonePattern: { template: { spec: { containers: [{ name: nginx, image: nginx:1.14.1 }] } } }
  • 这就是 RBG 的全部出发点：角色之间的「关系」本身成为声明式 API 的一部分——顺序、寻址、协同升级、配对扩缩，都写进一个 YAML
  • nginx 是官方 quick start 例子；真实场景是下一页的 LLM 推理服务
例子出处：README「Quick Start」（原文照抄，格式压缩）· 依赖语义源码：pkg/dependency/dependency.go:43-79
第 1 层 · 它是用来做什么的

头号场景：PD 分离的 LLM 推理服务

  • PD 分离后资源利用率更高（官方 quick start：分离消除了两阶段的计算干扰、解耦了资源分配）——这是官方动机，不是实测结论
  • 代价是部署复杂度暴涨：三种角色、多卡组、KV 传输、配对扩缩——这正是 RBG 存在的理由
PD 概念与聚合/分离部署图解：doc/quick_start.md「PD Colocation / PD Disaggregated」 · 官方完整例子：examples/inference/pd-disagg-leader-worker.yaml
第 2 层 · 它有什么效果

同样的活，人做 vs 声明

要做的事不用 RBG（人肉）用 RBG（声明式）
启动顺序init container 探测 / Helm hook / 手动分两次 applydependencies: ["frontend"] 一行
对端地址手写 N 个 headless Service + ConfigMap 硬编码地址自动建 Service，DNS 规律固定 + 环境变量注入
多卡组网手算 node-rank / nnodes / dist-addr 塞进每个容器容器里直接读 RBG_LWP_* 注入变量
升级不漂移prefill、decode 两个对象各自滚，中间版本不一致maxSkew: "1%" 两角色锁步推进
多卡原子调度没有现成语义，起一半卡白占资源一个注解开 gang 调度：全成或全不成
拓扑共置手写 pod affinity / nodeSelector一个注解声明拓扑域，同组共置
整体拓扑router/prefill/decode + Service + ConfigMap ≥ 5 类对象一个 YAML、一个对象，删除即全删
  • 右列每一项都是机制上的收益（做的事从「运维技能」变成「几行 YAML」）；性能收益取决于场景，本文无实测数字
  • 一句话：部署一个 PD 分离服务的门槛，从「K8s 高级运维」降到「会写一个 YAML」
⚠ 本页是机制对比（源码/文档可查证），不是 benchmark——性能、稳定性收益需按场景实测。各机制的出处见后面功能页与证据索引。
第 3 层 · 它能实现什么功能

功能总览 接下来 6 页逐个展开

① 多角色混搭一个 YAML 里 router / prefill / decode 各自独立副本数、独立策略
② 三种部署模式单 pod / leader-worker 多卡 / 异构组件组
③ 启动依赖拓扑排序，依赖不 Ready 下一层不创建
④ 服务发现headless Service + 环境变量 + 组件发现注解，免手写
⑤ 协同升级 / 扩缩CoordinatedPolicy：maxSkew 锁步、配对扩容
⑥ 原地更新改镜像只重启容器，pod 身份不变
⑦ gang 调度多卡组全成或全不成（scheduler-plugins / Volcano）
⑧ 独占拓扑一个注解让同组共置同节点 / 机架 / 可用区
⑨ 每角色独立伸缩ScalingAdapter 自动创建，HPA 直接挂
⑩ 生态集成SGLang / vLLM / NVIDIA Dynamo / Mooncake KV 传输
⑪ CLIkubectl-rbg 管理资源与 LLM 部署
⑫ AI 助手部署rbg-agent-guide：让 Claude Code 等替你写 RBG YAML
功能清单出处：doc/ 目录（TOC） · README「Key Features — SCOPE」（Stable / Coordination / Orchestration / Performance / Extensible）
第 3 层 · 功能 ①②

多角色混搭 + 三种部署模式

  • 同一个 RoleBasedGroup 里不同角色用不同模式：router 用 standalone、prefill/decode 用 leader-worker——一个 YAML 混搭
  • leader-worker 专为 TP 设计：size: 4 = 1 leader + 3 worker；多机组网参数由注入的环境变量直接给出（功能 ④ 详述）
  • 出处：doc/features/patterns.md · doc/features/multiroles.md
第 3 层 · 功能 ④（先讲它，因为最直观）

服务发现三件套：容器里不写死任何地址

  • 多卡组网零手算：SGLang 启动参数直接写 --dist-init-addr $(RBG_LWP_LEADER_ADDRESS):6379 --nnodes $(RBG_LWP_GROUP_SIZE) --node-rank $(RBG_LWP_WORKER_INDEX)
  • ③ customComponentsPattern 还有组件发现注解（把同实例某组件的 FQDN / 端口注入为环境变量）+ 端口分配器
  • 服务名 s- 前缀是故意的：DNS 规范要求服务名不能以数字开头（helper.go:106-119）
变量定义：api/workloads/constants/env.go:60-67 · 组件发现：pkg/component-discovery/component_discovery.go:34-40 · 全表：doc/reference/variables.md
第 3 层 · 功能 ③

启动依赖：拓扑排序，分层推进 不 ready 就不创建下一层

  • YAML 里就是一行：dependencies: ["frontend"]（第 3 页例子）——依赖写错角色名、循环依赖，校验直接报错
  • 源码链：SortRoles（拓扑排序，dependency.go:43-79） → reconcile 主循环逐层 CheckDependencyReady（controller:475-522）
第 3 层 · 功能 ⑤

协同升级 / 扩缩：CoordinatedPolicy，prefill 和 decode 锁步

# 独立 CRD，挂在要协同的角色上（不侵入 RoleBasedGroup 本体）
apiVersion: workloads.x-k8s.io/v1alpha2
kind: CoordinatedPolicy
spec:
  policies:
    - name: prefill-decode-rollout
      roles: [prefill, decode]
      strategy:
        rollingUpdate: { maxSkew: "1%", maxUnavailable: "10%" }
  • 管两件事：协同滚动更新（maxSkew / maxUnavailable）和协同扩缩（角色按配对比例一起扩；进度推进可选 OrderScheduled 等档位）
  • 出处：doc/features/coordinated-policy.md
第 3 层 · 功能 ⑥

原地更新：升级换镜像，不换"壳" pod 身份不变，只重启容器

策略行为
RecreatePod重建 pod（传统行为）
InPlaceIfPossible能原地就原地（改镜像 → 只重启容器），不行再重建 ← 推理负载默认选这个
InPlaceOnly只允许原地，否则报错
作用单元是「实例」（RoleInstance，pod 组整体升级）；策略定义：rolebasedgroup_types.go:108-116 · 官方演示（改镜像后 RESTARTS+1、AGE 连续）：doc/features/instance.md
第 3 层 · 功能 ⑦⑧

调度两板斧：gang 调度 + 独占拓扑

  • 两条都是一个注解的事：声明在 RoleBasedGroup 上，控制器翻译成 PodGroup / pod 亲和规则，不用碰调度器配置
  • 出处：doc/features/gang-scheduling.md · doc/features/exclusive-topology.md
第 4 层 · 怎么部署

四步跑起来 装 operator → 最小例子 → 看对象 → 上真模型

# ① 装 operator（二选一）——K8s 集群 ≥1.22，1 核 1G 空闲即可跑控制器
helm upgrade --install rbgs deploy/helm/rbgs --create-namespace --namespace rbgs-system --wait
kubectl apply --server-side -f ./deploy/kubectl/manifests.yaml      # 或纯 kubectl
kubectl wait deploy/rbgs-controller-manager -n rbgs-system --for=condition=available --timeout=5m

# ② 最小例子：nginx 两角色（第 3 页那个 YAML）
kubectl apply -f nginx-cluster.yaml

# ③ 看对象：RBG 一层，workload 一层，pod 一层
kubectl get rbg nginx-cluster                  # RoleBasedGroup 本体
kubectl get roleinstanceset -l rbg.workloads.x-k8s.io/group-name=nginx-cluster
kubectl get pods -l rbg.workloads.x-k8s.io/group-name=nginx-cluster   # 全组 pod 一目了然

# ④ 上真模型：SGLang PD 分离（需 GPU 节点 + lmsysorg/sglang:v0.5.9+ 镜像）
kubectl apply -f examples/inference/pd-disagg-leader-worker.yaml
还有个 CLImake build-cli 构建 kubectl-rbg，管 RBG 资源与 LLM 部署；v0.7.0 起支持多节点 LLM serving
⚠ 版本要求两处不一致README 版本表写 v0.7.0 需 K8s ≥ v1.22，install.md 仍写 ≥1.28——保守按 1.28+ 准备

第 5 层 · 什么设计 ①

四层对象：一个 CRD 拆成可管理的层级

配角对象（控制器自动建）每角色 headless Service · ControllerRevision（版本）· PodGroup（gang）· ScalingAdapter（HPA 挂钩）· CoordinatedPolicy（独立 CRD）
为什么要分层组管依赖/协同、角色管实例集合、实例管 pod 组——每层职责单一；跨角色的事只在最上层做，不用每个 workload 都懂"别的角色"
API 参考：doc/reference/api.md · 对象/标签全表：doc/reference/variables.md
第 5 层 · 什么设计 ②

控制器 reconcile 链 + 版本演进

版本演进v0.4（2025-09）RBGS 伸缩 → v0.5（2025-12）原生 InstanceSet + 原地更新 + Mooncake → v0.6（2026-02）协同扩缩 → v0.7（2026-06）v1alpha2 stable + CoordinatedPolicy + gang 调度 + CLI 多节点
⚠ 迁移注意v1alpha1 的 Deployment/STS/LWS workload 类型已被取代。开关 deprecatedWorkloadTypes.enabled：true（默认，存量必须保持）/false（仅限全新安装）；v0.7.0 起不再需要装 LWS CRD

总结 · 三句话

回到五个问题的答案

① 用来做什么把多角色 LLM 推理服务（PD 分离 / router+engine / engine+KV 传输）在 K8s 上当一个对象部署、扩缩、升级、寻址
② 有什么效果部署门槛从「K8s 高级运维」降到「会写一个 YAML」：顺序、寻址、协同、调度全是声明式（机制收益，非实测）
③ 能实现什么功能多角色混搭 + 三种模式 + 依赖 + 服务发现 + 协同升级 + 原地更新 + gang + 独占拓扑 + 每角色 HPA + 生态集成
④ 怎么部署helm 一条命令装 operator → kubectl apply 一个 YAML → kubectl get rbg 看三层对象 → SGLang 官方例子直接上真模型
⑤ 什么设计架构RoleBasedGroup → Role → RoleInstanceSet → RoleInstance → Pod 四层；reconcile 链拓扑排序分层推进；Go + controller-runtime，复用 LWS 代码
什么时候不用单体推理（一个 Deployment 完事）不要为了用而用；v1alpha1 存量迁移要等官方指南
