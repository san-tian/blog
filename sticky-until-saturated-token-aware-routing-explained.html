Sticky Until Saturated：LLM 路由为什么要“粘住直到饱和”

一篇关于 token-aware routing 的中文讲解：先亲和，再释放；先粘住，饱和后分流
📝 DRAFT讲解稿 HTML 版

这篇文章讨论的是 LLM 推理请求的路由策略：如何在 缓存亲和 和 负载均衡 之间找到平衡。作者的核心主张是：不要用一堆权重硬凑一个“看起来聪明”的分数，而要先识别 workload 的瓶颈，再用与瓶颈匹配的信号做路由。

它背后的直觉很简单：请求应该尽量留在已经拥有前缀缓存的 endpoint 上，但这份“粘性”不能无限持续；一旦 warm endpoint 接近饱和，就必须释放出来，让 cold endpoint 接管一部分负载。

先说结论

核心思想路由不是“永远追着缓存跑”，而是“先跟着缓存走，直到 endpoint 背不动了，再按真实瓶颈分流”。
Prefill-bound长 prompt 场景用 prefix-cache-affinity-filter + token-load-scorer，负载信号看的是未缓存的 prefill tokens in flight。
Decode-bound长输出场景用 prefix-cache-affinity-filter + active-request-scorer，负载信号看的是活跃请求数。
阈值 ττ 不是拍脑袋的经验值，而是从硬件吞吐和可接受 TTFT 上限推导出来的饱和阈值。

1. 这篇文章在反对什么？

作者先批评的是一种常见但不够稳的默认做法：把多个信号加权混合起来做路由。比如把 prefix-cache 匹配、队列深度、KV cache 利用率、LRU 等一起算分。

这种做法的问题不在于“完全不能用”，而在于它有三个工程上的缺点：

  • 难解释：最后为什么选了这个 endpoint，不好说清楚。
  • 难调参：一个权重改了，整体行为可能大幅变化。
  • 容易放大热点：越热的 endpoint 越容易继续吸流量，最后被粘爆。

所以作者换了一个更直接的思路：先判断 workload 的瓶颈是什么，再选一个和瓶颈匹配的负载信号。这就是文章里的 token-aware routing。

2. 两个阶段，两种瓶颈

LLM 推理通常分成两个阶段：

  • Prefill：处理 prompt，把输入 tokens 一段段算进去。
  • Decode：逐 token 生成输出，依赖 KV cache 和并发解码槽位。

不同 workload 的瓶颈不一样：

  • prefill-bound：prompt 很长，输入处理先成为瓶颈。
  • decode-bound：输出很长，解码槽位先成为瓶颈。

因此，路由信号也不应该统一。

Prefill-bound 用什么信号？

文章推荐的组合是：

prefix-cache-affinity-filter + token-load-scorer

含义是：

  • 先尽量把请求留给已经有前缀缓存的 endpoint
  • 但在比较负载时，不看“总请求数”，而看未缓存的 prefill tokens in flight

也就是说，谁当前还要处理的“新输入工作”更少，谁就更值得接这个请求。

Decode-bound 用什么信号？

文章推荐的组合是：

prefix-cache-affinity-filter + active-request-scorer

这里的核心变量变成了活跃请求数。因为 decode 阶段真正卡住的往往不是 prompt 处理，而是并发生成流的数量。

换句话说，decode 侧更关心的是：谁的并发生成已经太多了？

3. “Sticky until saturated” 到底是什么意思？

这是标题的核心。

可以把它理解为一句很朴素的策略口号：

只要某个 endpoint 还没饱和，就让请求尽量粘在它上面；一旦超过阈值，就不再死守亲和性，改按负载分流。

这和“永远优先缓存命中”的思路不一样。后者容易导致：

  • warm endpoint 越来越热
  • cold endpoint 一直吃不到活
  • 最后 warm endpoint 比 cold endpoint 还慢

所以文章引入了一个释放阈值 τ，用来控制“粘性”什么时候结束。

4. τ 是什么？

τ 可以理解成：

一个 warm endpoint 最多允许比别的 endpoint 多背多少“未缓存的 in-flight token 工作量”；超过这个量，就必须释放粘性。

它不是随便定的，而是从硬件吞吐和服务目标推出来的。文章给出的简化形式是：

τ_sat = R_peak × T_max

其中：

  • R_peak 是峰值 prefill 吞吐
  • T_max 是可接受的 TTFT 退化上限

直觉上很简单：如果 warm endpoint 已经背了太多未完成的输入工作，继续把请求粘过去，就会让 TTFT 超过你能接受的范围；到点就该“解粘”。

文中的示例参数是：

  • B = 8192
  • R_peak = 20480 tok/s
  • T_max = 14s
  • 得到 τ = 286720

可以把它理解成：允许 warm endpoint 领先大约 35 个 8192-token chunk 的未缓存 prefill 工作量。

5. 三个 workload 说明了什么？

文章拿了三类 workload 来验证这个方法。

5.1 code-generation：典型 prefill-bound

这个 workload 的特征很明显：

  • prompt 很长
  • 输出相对短
  • 跨请求共享前缀不多

所以瓶颈是 prefill compute。

结论是：

  • prefix-cache-affinity + token-load 表现最好
  • TTFT 更低
  • 输入吞吐更高
  • 传统 round-robin 更容易更早撞到拐点

一句话理解：在长 prompt 场景里，最值钱的是“谁的未完成输入更少”，而不是单纯谁最近命中过缓存。

5.2 reasoning：典型 decode-bound

这个 workload 的特征是：

  • prompt 较短
  • 输出很长
  • 并发生成流很多

所以瓶颈是 decode slots。

结论是：

  • prefix-cache-affinity + active-request 更合适
  • 因为它直接按活跃流数均衡 decode 压力
  • 在 decode 侧更容易保持均衡

这说明：对 decode-bound 负载来说，token 不是最合适的负载单位，活跃请求数更贴近真实瓶颈。

5.3 b2b-saas：病态 prefill-bound 压力测试

这个 workload 不是普通业务流量，而是一个重复小语料的压力测试：

  • 很多 system prompt 会重复出现
  • 缓存命中会变得很关键
  • 如果分流不对，容易出现 cache churn

它说明两件事：

  • 缓存亲和策略确实有用，能把重复语料稳定分到不同 endpoint 上
  • τ 太小或太大都不好：太小会过早释放，太大会粘得太久，热点会过载

它像是一个验证“饱和阀门”是否合理的实验。

6. 为什么旧的加权混合不如这个方案？

不是说加权混合一定错，而是它有几个工程上的问题。

  • 不可解释：很难一眼说清楚到底是哪个信号起了作用。
  • 不可迁移：一组权重可能只对某个 workload 好，换场景就不稳。
  • 不容易做饱和释放：如果没有明确阈值，就容易一路偏向 warm endpoint。

文章把复杂度收敛成了三个东西：

  • 一个 affinity filter
  • 一个与瓶颈匹配的负载信号
  • 一个可计算的 saturation threshold

这就更像一个能落地的系统，而不是一堆经验权重。

7. 这篇文章真正想传达什么？

工程启发

先识别瓶颈不要先问“用什么算法”，先问 workload 卡在哪：prefill、decode，还是两者混合。
信号要贴近瓶颈prefill 看 token load，decode 看 active requests，混合场景再考虑 predictor。
亲和性不是越强越好缓存亲和有价值，但必须有释放机制，否则“粘住”会变成“粘死”。
阈值尽量可推导如果能从硬件吞吐和 SLO 反推，策略就更稳、更可解释，也更容易迁移。

8. 一句话总结

LLM 路由的关键，不是永远追着缓存跑，而是让请求先跟着缓存走，直到某个 endpoint 背不动了，再按真实瓶颈分流。这样既保留缓存收益，又避免热点过载。
