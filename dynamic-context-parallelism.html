一句话总结

DCP（Decode Context Parallel）是 vLLM 提供的一个参数开关，通过改变 KV Cache 的切分维度（从头维改为序列维），消除 GQA 模型在高张量并行度下的重复存储问题，让显存容量翻倍。

问题：为什么会产生 KV Cache 重复存储？

张量并行的常规做法

推理大模型时，单卡显存装不下，需要用张量并行（Tensor Parallelism, TP）把模型切分到多张卡。

常规张量并行的切分方式：沿注意力头维度切分 KV Cache。

举例：模型有 24 个注意力头，TP4 时每张卡分到 6 个头。

GQA 模型的特殊性

GQA（Grouped Query Attention） 是一种优化技术，让多个 Query 头共享少量 KV 头，减少 KV Cache 显存占用。

典型配置：

  • Query 头数：24 个（用于计算注意力）
  • KV 头数：只有 4 个（用于存储 KV Cache）

冲突产生

当 TP 并行度超过 KV 头数 时，问题出现了：

场景：Qwen3.6-27B 模型，4 个 KV 头，使用 TP8（8 张卡并行）

  • KV 头数：4 个
  • 要分配给：8 张卡
  • 结果：4 个头分不到 8 张卡上

引擎的处理方式：让多张卡共用同一个 KV 头 → KV Cache 被复制存储

具体分配（vLLM 源码 vllm/config/model.py:1270）：

return max(1, total_num_kv_heads // parallel_config.tensor_parallel_size)
# num_kv_heads=4, TP8:
# 4 // 8 = 0，但 KV 头数不能为 0
# max(1, 0) = 1 → 每张卡分配 1 个头
# 8 张卡 ÷ 4 个头 = 每个头被复制 2 份

rank 分配：

rank0、rank1 → 共用 KV头1（复制 2 份）
rank2、rank3 → 共用 KV头2（复制 2 份）
rank4、rank5 → 共用 KV头3（复制 2 份）
rank6、rank7 → 共用 KV头4（复制 2 份）

复制倍数 = TP 并行度 ÷ KV 头数 = 8 ÷ 4 = 2 倍

为什么是"静默"的问题

这不是 bug，是引擎的兜底设计：

  • ✅ 好处：模型可以正常运行，不会报错启动失败
  • ❌ 坏处：显存被浪费了，但没有任何告警

唯一的线索：启动日志里的 KV 池容量与手算不符。

解决方案：DCP 如何消除重复？

核心思想

改变切分维度：从沿头维切分，改为沿序列维切分。

维度 常规 TP DCP
切分对象 不同的 KV 头 同一个 KV 头的不同 token
每张卡存什么 完整的若干个 KV 头 每个 KV 头的一部分序列
受限因素 KV 头数（GQA 模型只有 4-8 个） 序列长度（可以很长）

具体做法

开启 DCP 后（--decode-context-parallel-size 2）：

同一个 KV 头的 token 序列被切成两段，分给两张卡：

原来（TP8 无 DCP）：
rank0: [KV头1 的全部 token]  ← 重复
rank1: [KV头1 的全部 token]  ← 重复
rank2: [KV头2 的全部 token]  ← 重复
rank3: [KV头2 的全部 token]  ← 重复
...

开启 DCP（TP8 + DCP=2）：
rank0: [KV头1 的前半段 token]
rank1: [KV头1 的后半段 token]  ← 不重复了！
rank2: [KV头2 的前半段 token]
rank3: [KV头2 的后半段 token]  ← 不重复了！
...

每张卡只存 1/2 的 KV Cache → 重复消除，显存翻倍。

收益：显存翻倍 + 解码加速

收益1：显存容量翻倍（无条件收益）

实测数据[1]（8 × 昇腾 910B4-32GB，Qwen3.6-27B，TP8）：

指标 TP8 无 DCP TP8 + DCP 提升
每卡物理显存 20.54 GiB 20.54 GiB 无变化
全机 KV 容量 1.32M tokens 2.61M tokens 1.98 倍 ✅
关键点：物理显存没有增加，增量来自释放了原本存放重复数据的那一半。精确值：1,318,741 → 2,612,705 tokens，比值 1.981，复现测试抖动仅 0.06%，非常稳定。

收益2：解码加速（TPOT 下降）

每张卡只需计算一半序列的注意力 → 每 token 时间（TPOT）下降

实测数据[1]（并发度 1）：

上下文长度 每秒吐字提升 TPOT 下降
64K +16% −13.8%
128K +28% −22.4%
250K +45% −31.2%

规律：上下文越长，收益越大（250K 时每秒吐字速率提升 45%！）

代价：Prefill 通信开销

为什么有代价？

两张卡各持一半序列，计算注意力时需要：

  1. 每张卡计算自己那部分的局部结果
  2. 跨卡通信，归并两张卡的结果

这份通信开销打在 prefill 阶段 → 首 Token 时间（TTFT）上升

实测代价

首 Token 延迟增幅[1]：

上下文长度 并发 1 并发 2 并发 4
64K +3.2% +9.8% +21.4%
128K +3.9% +12.1% +25.7%
250K +4.5% +14.9% +30.0%

规律：并发越高，代价越大（250K 并发 4 时 TTFT 增加 30%）

为什么并发高时代价大？

  • 并发低：prefill 可以充分利用 GPU，通信相对快
  • 并发高：多个请求同时 prefill，GPU 和通信资源竞争激烈，通信延迟放大

综合判断：什么时候该开启？

端到端时间计算

单个请求的总时间 = TTFT（首 token）+ TPOT × 输出长度

实测输出 512 tokens，端到端时间变化[1]：

上下文 并发 TTFT 变化 TPOT 变化 端到端变化 判定
64K 1 +3.2% −13.8% −7.4% 值得
128K 1 +3.9% −22.4% −15.3% 值得
250K 1 +4.5% −31.2% −23.8% 值得
250K 2 +14.9% −21.5% −13.5% 值得
250K 4 +30.0% −7.1% +2.9% 净亏损
64K 4 +21.4% −10.2% +7.9% 净亏损
规律：长上下文 + 低并发时，收益 >> 代价，大幅加速；短上下文 + 高并发时，代价 >> 收益，反而变慢。

开启建议

场景 是否开启 DCP 原因
显存不足，请求被拒绝 必须开 KV 容量翻倍，解决根本问题
长上下文（≥128K）+ 低并发（≤2） 建议开 端到端加速 15%-24%
短上下文（<128K）+ 高并发（≥4） 不建议 端到端变慢 3%-8%
SLO 严格限制 TTFT 不建议 TTFT 增加 5%-30%

如何判断你的模型需要 DCP？

查看模型配置

grep num_key_value_heads /path/to/model/config.json

计算复制倍数

公式：复制倍数 = TP 并行度 ÷ KV 头数

KV 头数 TP2 TP4 TP8 TP16
1 (MQA) 2× 4× 8× 16×
2 1× ✅ 2× 4× 8×
4 (实测模型) 1× ✅ 1× ✅ 2× 4×
8 1× ✅ 1× ✅ 1× ✅ 2×
16+ 1× ✅ 1× ✅ 1× ✅ 1× ✅
  • 1× ✅：分片干净，无重复，不需要开启 DCP
  • ≥2×：有重复存储，可以考虑开启 DCP

格内数值也是 --decode-context-parallel-size 可设的最大值。

⚠️ 不要混淆两个"头数除不尽"问题

问题类型 检查字段 后果 本质
硬约束 num_attention_heads
（Query 头数）		 直接报错：ValueError
服务无法启动		 Query 头数除不尽 TP
软降级（本文） num_key_value_heads
（KV 头数）		 静默复制
浪费显存但能运行		 KV 头数除不尽 TP
常见错误 Total number of attention heads (52) must be divisible by tensor parallel size (3) 是硬约束问题，与 DCP 无关。

实测验证：三方互证

手算、源码、实测三者完全一致，验证了重复存储的机制。

每 token 的 KV 显存（全机合计）[1]：

来源 计算方式 结果 相对手算
手算 2 × 16层 × 4KV头 × 256 × 2字节 64.0 KiB 1.000
TP8 实测 20.54 GiB × 8 ÷ 1,318,741 tokens 130.7 KiB 2.042 ✅
TP4 实测（参照） 16.37 GiB × 4 ÷ 1,040,564 tokens 66.0 KiB 1.031
结论：TP8 实测值 = 手算值 × 2，与源码推导的 8÷4=2 倍复制完全一致；TP4 分片干净，实测与手算仅差 3%（记账误差）。

这是问题的唯一外部线索：启动日志里与手算不符的 KV 池容量。

开启方式

vllm serve model_name \
  --tensor-parallel-size 8 \
  --decode-context-parallel-size 2

四条约束

  1. 上限：DCP ≤ TP ÷ KV头数（本文实测：4 个 KV 头，TP8，上限 = 8÷4 = 2）
  2. 整除：TP 必须能被 DCP 整除，否则直接报错
  3. 版本：vLLM ≥ v0.11.1（GQA 支持需要 PR #24864）
  4. 作用范围：只管 decode 侧（prefill 侧是 --prefill-context-parallel-size）

布局对比：DCP 不是唯一选择

DCP 消除的是一个布局内部的冗余，但还有另一个选择：降低 TP，增加数据并行（DP）。

TP8+DCP vs TP4×2

TP4×2 = 2 个数据并行副本，每副本 TP4（4 个 KV 头正好分给 4 张卡，无重复）

布局选择建议

场景 推荐布局 原因
长上下文（≥128K）+ 低并发（≤2） TP8 + DCP TPOT 领先 1.79 倍
短上下文（~64K）+ 高并发（≥8） TP4×2 端到端快 8.6%，TPOT 快 22.5%

关键要点总结

  1. 问题根源：GQA 模型 KV 头数少（4-8 个），TP 并行度超过头数时，引擎让多张卡复制存储同一个 KV 头
  2. DCP 原理：改变切分维度，从沿头维切分改为沿序列维切分，每张卡只存 1/N
  3. 显存收益：无条件翻倍（1.98×），与长度、并发无关
  4. 性能收益：TPOT 下降（解码加速），长上下文时提升 45%，收益随上下文增长
  5. 性能代价：TTFT 上升（prefill 通信），高并发时增加 30%，代价随并发增长
  6. 开启判据：显存不足 → 必须开；长上下文（≥128K）+ 低并发（≤2） → 建议开；短上下文 + 高并发 → 不建议
  7. 静默问题：重复存储没有告警，唯一线索是启动日志的 KV 池容量
  8. 通用性：不是 vLLM 特有问题，TensorRT-LLM 等引擎也有相同机制
