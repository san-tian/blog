indexer KV share（DSA 融合写 kernel）
为什么「只能兼容 dcp=8」？

结论一句话：新 kernel 丢掉了 DCP 的「虚拟 id → 物理行」映射，把虚拟 id 当物理行号直接写——先错位、后越界。它对任何 dcp>1 都不正确，dcp=8 的「正常」只是没跑到越界拐点。

背景 · 术语定义：全文统一四个名词

四个术语的直接定义

KV cache（键值缓存）注意力机制为每个 token 生成的中间状态缓存；decode 时每生成一个 token 都要读取之前全部 token 的 KV。本文的「写 kernel」就是把新算出的 KV 写入这个缓存
indexer（索引器）GLM-5.2 稀疏注意力的选路模块：对历史 KV 做低精度打分、选出 top-k（约 2048）条，注意力只对选中条目计算。它与 attention 共用同一份 KV——优化名 "indexer KV share" 即由此而来
DCP（decode context parallelism）把 KV cache 按 token 轮转分布到 dcp 张 GPU（dcp=4 即 4 卡各存 1/4），每卡只存自己那份。因此写入前必须把全局 slot 编号换算成本卡物理行号——本文的 bug 正是丢掉了这步换算
kernel（GPU kernel）GPU 上执行的并行计算函数；本文的排查对象就是一个新写的 KV 写入 kernel（量化 + 写入一步完成）
名词约定：slot / 行 = KV cache 的一个 token 槽位；loc = 写入目标 slot 编号；rank = 一个 DCP 参与方（一张 GPU 一个 rank）
「乱码」= 模型输出突然变成无意义文字（生成质量崩坏）；「优化」= 让 KV 写入更快的一个 kernel 改动，dcp=1 时输出与改动前完全一致。
背景 · 技术版：这份共享 KV 与这次优化

fp8 下 indexer 与 attention 共用一行 656B 的 KV

两个读者：indexer 选路打分 ↓  ·  attention 稀疏计算 ↓（读同一份 KV）
k_nope fp8
512 B
scales
16 B
k_rope bf16
128 B
一份 KV，两边读 —— 即 "indexer KV share"（GLM-5.2 + --kv-cache-dtype fp8_e4m3：512 + 16 + 128 = 656）
  • fp8 = 8 位浮点（常规 16 位的一半内存）：k_nope 压缩成 fp8 存，配每 128 维一个缩放系数；rope 保持 bf16——一行共 656 字节（布局公式）
  • 这次优化（commit 0a60805df4）把这一行的写入从「量化 + 写回」两步并成一步 kernel——更快、输出字节级一致（性能目的合理）
  • 但 DCP 下（上页定义），写入需先做「全局 slot 编号 → 本卡物理行号」的换算——换算规则就是排查的主角：归属 rank = v % dcp，物理行号 = v // dcp
「关掉优化」= 回到 bf16 KV / 旧写路径（带换算），所以怎么开 dcp 都正常——这是后面「变量隔离」的线索。
现象 · 三个变量：dcp 值 / 优化开关 / 时间

观察到的四种组合

dcp=4 + 优化开头正常 → 突然乱码
dcp=8 + 优化暂未复现
dcp=4/8 + 关掉优化都正常
dcp=1（对照）虚拟域=物理域，数学上正确

从现象读出三条线索

线索 1：变量隔离关掉优化就正常 ⇒ 问题范围锁定在这个 commit 改动的东西
线索 2：时间形态不是立刻坏，而是「开头正常 → 跑一段时间突然乱码」⇒ 内存状态积累型（错位写 / 越界写）特征
线索 3（误导项）dcp=8 暂未复现 ⇒ 后面会看到这是「没跑到拐点」的假象，不是兼容

收敛 ② · DCP 下写入的 loc 是什么

loc 是「虚拟 id」，不是物理行号

虚拟 id = allocator 发放的全局 slot 编号；物理行号 = 本 rank KV 池内的行号。DCP 下写入前必须先换算：归属 rank = v % dcp，物理行 = v // dcp
allocator 容量 = size×dcp、虚拟页 = 64×dcp（kv_cache_configurator.py:1775-1783）；物理池每 rank 只有 size 行（memory_pool.py:4105-4113）。
现象→ ① 变量隔离→ ② 虚拟 id→ ③ 全库契约→ ④ 根因→ ⑤ 定位
收敛 ③ · 正确写法是什么

全库契约：KV 写路径都要做 mask + divide

# mla_buffer.py:39-43 —— set_mla_kv_buffer_kernel（commit 之前 fp8 路径必经）
loc = tl.load(loc_ptr + pid_loc).to(tl.int64)
is_valid = (loc != reserved_skip_index) & (loc % DCP_WORLD_SIZE == DCP_RANK)  ① 归属过滤：只写自己的 token

tl.store(dst_ptr + safe_loc * buffer_stride + offs, src, mask=mask & is_valid) ③ 无效 token 不写

定位 ⑤-A · 错误写在哪个行号

应写 v//dcp，实写 v：错位 + 越界

token归属 rank应写行 v//4新 kernel 实写行结果
v=1101⚠ 行内错位（还踩掉 v=5 的槽）
v=5115⚠ 行内错位
v=9129✗ 越界（size=8）
v=131313✗ 越界
错位写：写入本池内错误的行，后续按正确行号读取的一方拿到错误数据；越界写：写入超出本 layer buffer 范围，破坏相邻 layer 的 KV buffer 等内存。⚠ 读侧行号换算的两种可能（契约读法 v//dcp / 本分支 DSA 原始 v）详见 md 版第 5 节——无论哪种，写侧行号错了就是错的。

定位 ⑤-B · 错误何时开始发生

allocator 从低位顺序发页：越过 size = 拐点 解释「开头正常、突然乱码」

  • 水位 = 累计分配的虚拟 slot 数（allocator 已发出的编号总数，即高水位）；越过 size 后出现 v ≥ size 的行号 → 越界写相邻内存
  • 拐点前（v < size）：错位写 + 读侧若恰好也用原始 v（本分支 DSA 读路径无任何 dcp 换算），读写暂时自洽 → 看起来正常
⚠ 拐点前的「自洽」与拐点后的具体乱码形态属推断（读侧 sgl-kernel C++ 无法静态全核，md 版已逐条标注）；写侧丢失 mask+divide 是确定性事实。
现象→ ① 变量隔离→ ② 虚拟 id→ ③ 全库契约→ ④ 根因→ ⑤ 定位→ 复盘 · dcp=8
复盘 · 线索 3 的解释

那为什么 dcp=8 「没事」？拐点与 dcp 值无关 —— 只是没跑到

  • 越界阈值都是「累计分配 > size」，dcp 值不改变拐点位置——dcp=8 的「正常」是没跑到，不是兼容
  • 数学上只有 dcp=1 正确：v//1 == v，虚拟域与物理域重合
  • 同负载长跑，dcp=8 同样会炸；「兼容 dcp=8」这个结论不要采信
⚠ dcp=8 未复现的精确机理（水位/时长/读侧自洽区间差异）需压测复核；「kernel 对任何 dcp>1 都不正确」不依赖此点——写侧丢失 mask+divide 是代码事实。

方案 A（推荐）kernel 内补 DCP mask + divide，与旧 kernel 逐行对齐；顺带补回 slot 0 跳过
方案 B（保守）dcp_enabled() 时回退旧两步路径（quantize + set_mla_kv_buffer_triton），fused 仅用于 dcp=1
附带：HIP fp8 分支（set_mla_kv_buffer_fp8_quant_kernel）同样没有 DCP 换算——AMD 上开 DCP+fp8 share 会踩同坑（存量，非本 commit 引入） rebase 到生产分支时，读侧那批 DCP 修复（_localize_index_k_cache_locals 等，37231e4884）需一并核对
验证建议：dcp=4 长时压测，监控累计分配越过 size 后的输出质量；对照 dcp=1 应全程正常。

总结 · 三句话
