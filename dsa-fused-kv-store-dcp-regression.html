背景 · 术语 1/2：DSA（本文首次详细解释）

DSA（DeepSeek Sparse Attention，稀疏注意力架构）

是什么GLM-5.2 采用的注意力架构。dense 注意力（MHA/MLA）每步对全部历史 token 计算，长上下文下计算量不可控
怎么做两段式：先选路、再计算——先选出相关的历史条目，attention 只对选中条目计算；每步计算量从 O(全部历史) 降到 O(top-k)
query当前 token 的查询向量
→
① 选路（indexer，下页）低精度打分，选出 top-k 条目 id
→
② 稀疏 attention只对选中的 top-k 条目做完整计算
→
输出每步计算量 O(top-k)
本文首次详细解释 DSA，已登记术语索引（glossary.md）；dense 侧的 MLA 见姊妹篇《在 H200 上服务 GLM-5.2》（glm52-llm-d-agentic-serving.md）。
背景 · 术语 2/2：indexer（本文首次详细解释）

indexer（索引器）：DSA 的选路模块

是什么对每个 query 用低精度（fp8）打分器给全部历史 KV 打分，选出 top-k 条（GLM-5.2 约 2048）——它决定 attention「看哪些历史」
与本文的关系indexer 打分与 attention 计算读同一份 K（同一行 656B）——优化名 "indexer KV share" 的由来；本文排查的正是这份数据的写入 kernel
📄 DCP：本文第 5-9 页详解（概念 / 省显存 / 怎么用）；实测见 《DCP 实测》 📄 KV cache / kernel / MLA：旧文已讲过，直接使用（glossary.md）
名词约定：slot / 行 = KV cache 的一个 token 槽位；loc = 写入目标 slot 编号；rank = 一个 DCP 参与方（一张 GPU 一个 rank）；「乱码」= 模型输出变成无意义文字。indexer 为本文首次详细解释，已登记术语索引。
背景 · 技术版：这份共享 KV 与这次优化

fp8 下 indexer 与 attention 共用一行 656B 的 KV

两个读者：indexer 选路打分 ↓  ·  attention 稀疏计算 ↓
k_nope fp8
512 B
scales
16 B
k_rope bf16
128 B
一份 KV，两边读 —— 即 "indexer KV share"（GLM-5.2 + --kv-cache-dtype fp8_e4m3：512 + 16 + 128 = 656）
  • fp8 = 8 位浮点（常规 16 位的一半内存）：k_nope 压缩成 fp8 存，配每 128 维一个缩放系数；rope 保持 bf16——一行共 656 字节（布局公式）
  • 这次优化（commit 0a60805df4）把这一行的写入从「量化 + 写回」两步并成一步 kernel——更快、输出字节级一致（性能目的合理）
  • 但 DCP 下，写入需先做「全局 slot 编号 → 本卡物理行号」的换算——换算规则就是排查的主角：归属 rank = v % dcp，物理行号 = v // dcp
「关掉优化」= 回到 bf16 KV / 旧写路径（带换算），所以怎么开 dcp 都正常——这是后面「变量隔离」的线索。656B 布局与量化公式的逐字节解读见姊妹篇《GLM-5.2 decode TPOT 优化》（glm52-tpot-decode-optimization.html）。
背景 · DCP 1/5：先分清 TP、DCP 和当前模型的 KV

当前 GLM-5.2 DSA：TP 切权重和 Q 头；656B KV 没有头维度，DCP 切序列

TP（始终生效）完整 TP group 仍是 8 个 rank。模型权重按 TP=8 切；代码里的 num_local_heads = num_heads // attn_tp_size 也说明 Q/输出头仍按 attention TP=8 切。
当前 KV 的特殊性DSA/MLA 的 656B indexer KV 是每 token 一行的压缩 latent KV：512B + 16B scale + 128B rope，不是「每个 KV head 一行」的普通 MHA 张量，因此这里不能说 TP 再把它切成 8 个 KV 头。
DCP（新增一层）在 TP group 内建立 DCP 子组，把这条无头 KV 按 token 序列轮转分配。每个 token 在每个 DCP 子组中只存一份；不同子组之间仍可能有副本。
# 当前 tp=8：parallel_state.py 先保留完整 TP group，再在其中切 DCP 子组
TP group:   [0, 1, 2, 3, 4, 5, 6, 7]
DCP=2:      [0,1] [2,3] [4,5] [6,7]       # 4 个子组；每组内部 2-way 序列分片
DCP=4:      [0,1,2,3] [4,5,6,7]            # 2 个子组；每组内部 4-way 序列分片
DCP=8:      [0,1,2,3,4,5,6,7]              # 1 个子组；内部 8-way 序列分片
直接回答：dcp=2/4/8 都不会让 TP 对权重或 Q 头失效；当前 attention TP 仍是 8。对本文排查的 656B DSA KV，TP 不按「KV 头」切，DCP 才是序列 owner 机制。每个 DCP 子组内部覆盖一份完整序列，因此完整 TP group 中同一 latent KV token 的副本数是 tp/dcp：dcp=2/4/8 分别为 4/2/1。
背景 · DCP 2/5：怎么切

轮转切分：v % dcp 定归属，v // dcp 定本地行

不是「卡 0 存前 1/4、卡 1 存后 1/4」的连续切，而是轮转：每个 token 拿全局编号 v，按 v % dcp 归卡。

全局编号 v（dcp=4）归属 rank = v % 4本卡物理行 = v // 4
0, 4, 8, 12, …00, 1, 2, 3, …
1, 5, 9, 13, …10, 1, 2, 3, …
2, 6, 10, 14, …20, 1, 2, 3, …
3, 7, 11, 15, …30, 1, 2, 3, …

这就是写 kernel 里那两行（所有 DCP 写路径都有，除了本文的 bug kernel）：

is_valid = (loc != reserved_skip_index) & (loc % DCP_WORLD_SIZE == DCP_RANK)   # ① 归属过滤：只写归我管的 token
safe_loc = tl.where(is_valid, loc, 0) // DCP_WORLD_SIZE                        # ② 全局编号 → 本卡行
① 归属过滤（v % dcp == rank）每个 token 只被它的 owner 卡写一份——不滤的话每张卡会把所有 token 都写一遍，本地 buffer 装不下、数据也重复
② 行号换算（v // dcp）全局编号 v 在本卡落到第 v//dcp 行——因为轮转下卡 r 的第 k 个 token 的全局号是 k×dcp + r
轮转（而非连续切）的理由：token 是逐条流式到达的，轮转让每条新 token 均匀落到各卡（t → t % dcp），无需提前知道总长度也能保持每卡负载均衡。
背景 · DCP 3/5：收益与代价

对当前 656B KV：DCP 越大，序列副本越少；TP 权重切分不变

当前模型的副本账完整 TP group 有 8 个 rank，DCP 子组大小为 N。656B 压缩 KV 没有 head 轴；每个子组内部的 N 个 rank 共同覆盖一份序列，所以完整 TP group 中同一 token 的副本数是 TP/N：dcp=2/4/8 对应 4/2/1 份。
收益 · 容量与代价每个 DCP 子组内按序列分摊，降低 latent KV 的重复存储，并让组内每个 rank 只处理自己的序列 owner；代价是组内需要通信合并局部 attention 结果。
📏 DSA indexer KV = 656 字节/token（512 fp8 + 16 scale + 128 rope） 本文的 bug 就在这条 indexer KV 的 DCP 写入路径上
不要把两个 group 混在一起TP group 仍是 8 路，负责模型权重和 Q/输出头；DCP=4 group 是 TP group 内的 4-rank 子组，负责该子组内部的序列 owner。DCP 不是把 TP 改成 4，也不是额外增加 4×GPU。
DSA 的化解先用 656B 压缩 KV 让 indexer 选出 top-k，attention 再合并各序列分片的局部结果；稀疏 top-k 减少了需要实际取用的 KV 通信量。
关键澄清：当前 DSA/MLA KV 不是按 KV head 由 TP 切开的；它是一行一个 token 的 compressed latent cache。TP 仍完整作用于模型权重和 query/output head；DCP 只在 TP group 内把序列按 owner 分到子组成员。DCP 省的是跨 DCP 子组的重复存储，且不会改变 TP=8 的权重切分。
背景 · DCP 4/5：代价的展开——通信

attention 这一步通信：all-gather 汇集 KV，all-reduce 合并输出

通信发生在 attention 计算这一步、每个 decode step 都要做（不是加载权重时）。以 dcp=4 为例：每个 DCP 子组内的 4 个 rank 各持有一部分序列，必须交换/合并组内局部结果；这是 DCP group 通信，不是把 TP group 改成 4。共三处，全在 comm.py：

时机collective目的代码
汇集 KVall-gather每个 DCP 子组内，各 rank 把自己的序列分片汇集起来comm.py:181 all_gather_into_tensor
汇集 Qall-gatherquery 也是分片的，同样广播comm.py:266 all_gather
合并局部 attentionall-gather LSE + all-reduce（或 reduce-scatter）每卡只算了自己分片的「局部输出 Oᵢ + LSEᵢ」，要合并成全局 softmaxcomm.py:92 / 114 / 161
# ① 汇集 KV：all-gather（拼完整数据，不是求和）
parallel.dcp_group.all_gather_into_tensor(gathered_kv_a, kv_a)   # comm.py:181
# ② 合并局部 attention 结果（LSE 修正）
lses = cp_group.all_gather(cp_attn_lse, dim=0)                   # comm.py:92  先广播各自 LSE
out  = cp_group.all_reduce(out)                                  # comm.py:114 再求和缩放后的输出
为什么 KV 用 all-gather 不是 all-reduce语义不同：all-reduce = 求和（训练里把各卡梯度加起来）；all-gather = 拼接（把分片拼成完整数据）。KV 是要「读到完整数据」，不是求和——所以用 all-gather
合并公式（为何要 LSE）数值稳定的 softmax 用 max + sum-exp；分片后每卡只算部分 keys，得到 (Oᵢ, LSEᵢ)。合并：O = Σᵢ Oᵢ × exp(LSEᵢ − LSE_global)，LSE_global = logsumexp(所有 LSEᵢ)。所以先 all-gather LSE、再 all-reduce 输出
all-reduce 只出现在「合并局部输出」这一步（求和语义）；汇集 KV/Q 都是 all-gather（拼接语义）。MHA 后端用 all-reduce（comm.py:114）、MLA 后端用 reduce-scatter（comm.py:161）——都是 Σ 求和，只是结果落位不同。
背景 · DCP 5/5：怎么用

开 --dcp-size N，剩下的框架自动做

你不需要写任何 per-rank 逻辑，只需启动参数开 DCP：

# decode 端（本文排查的写 kernel 跑在这边）
--tp 8 --dcp-size 4        # 8 个 TP rank 组成 4 个 DCP 组
# prefill 端
--enable-prefill-cp --cp-strategy interleave
① 定身份parallel_state.py:2251-2268 保留完整 TP group，再按 dcp_size 切 DCP 子组；rank 的 DCP 身份是其在子组中的 rank，attn_dcp_size = dcp_size
② 全局访问点kernel 里用 get_parallel().attn_dcp_rank / attn_dcp_size 读；DCP 关时退化为 size=1、rank=0
③ 发 widened id调度器发「全局虚拟编号」v ∈ [0, size×dcp)，读写两侧各自做 v//dcp 换算
📜 契约原文（memory_pool.py:4240-4245）："loc is widened under DCP; the kernel divides by the world size itself."
dcp=1 时自动退化：v % 1 == 0 恒真、v // 1 == v——同一份代码自动变成非 DCP 行为。注意：DCP 子组大小不等于 TP group 大小；例如 tp=8、dcp=4 是完整 TP=8 加两个 DCP=4 子组，不是把 TP 降成 4。本文的 bug 仍然是新 fused kernel 把 DCP 的两行换算漏掉。

收敛 ② · DCP 下写入的 loc 是什么

loc 是「虚拟 id」，不是物理行号

虚拟 id = allocator 发放的全局 slot 编号；物理行号 = 本 rank KV 池内的行号。DCP 下写入前必须先换算：归属 rank = v % dcp，物理行 = v // dcp
allocator 容量 = size×dcp、虚拟页 = 64×dcp（kv_cache_configurator.py:1775-1783）；物理池每 rank 只有 size 行（memory_pool.py:4105-4113）。
现象→ ① 变量隔离→ ② 虚拟 id→ ③ 全库契约→ ④ 根因→ ⑤ 定位

allocator 从低位顺序发页：越过 size = 拐点 解释「开头正常、突然乱码」

  • 水位 = 累计分配的虚拟 slot 数（allocator 已发出的编号总数，即高水位）；越过 size 后出现 v ≥ size 的行号 → 越界写相邻内存。每 rank 池只有 size 行，虚拟空间是 size×dcp，所以池填到约 1/dcp 就开始越界——大池高负载下要跑几小时才过线

  • 不是所有请求都出问题：越界写踩的是相邻内存里恰好在那的请求数据——只有分配在高位虚拟 id（v≥size）的请求、或数据被踩掉的请求才乱码，是零星而非全体（若逻辑错则全体立刻崩）

这与「越界写」的物理行为一致：写的是「不该写的那块内存」，破坏范围由溢出量决定，天然零星。

现象核对 ④/5 · 关掉 Indexer Share 就好了

为什么关掉（或回退）就好了？

# 无论「关掉 indexer share（换 bf16）」还是「回退 commit（fp8 退回两步）」，
# 写都回到带 DCP 换算的旧 kernel set_mla_kv_buffer_triton：
is_valid = (loc != reserved_skip_index) & (loc % DCP_WORLD_SIZE == DCP_RANK)   ① 归属过滤：只写自己 rank 的 token
safe_loc = tl.where(is_valid, loc, 0)
safe_loc = safe_loc // DCP_WORLD_SIZE                                         ② 虚拟 id → 本卡物理行
tl.store(dst_ptr + safe_loc * stride + offs, src, mask=… & is_valid)

# 开着 = fused_dsa_quant_store，直接拿虚拟 id 当行号写：
cache_loc = tl.load(loc_ptr + token_id)                                       ✗ 无过滤、无换算
tl.store(nope_buf_ptr + cache_loc * stride + offs, y_q)                      ✗ 行号错 + v≥size 越界
旧 kernel（关掉/回退后）把虚拟 id 换算成本卡行号（v // dcp），且只写自己 rank 的 token → 行号永远 < size，永不越界
新 kernel（开着）cache_loc = loc 原样当行号 → 行号错，v≥size 时越界写相邻内存

现象核对 ⑤/5 · dcp=8 没炸

现象结果不能反推 TP 是否切 KV：要看具体 cache 类型

本文 656B indexer KV它没有 head 轴，TP 不在这一行上做 KV-head 分片；dcp=2/4/8 只改变 DCP 子组大小、序列 owner 和跨子组副本数（4/2/1）。
模型计算仍是 TP=8权重、Q/输出头的 attention TP 没有因 dcp 改变。fused kernel 出错的原因是漏了 DCP 的 owner mask + virtual-to-local 行号换算，而不是 TP 被关闭。
dcp=8 的乱码是否出现，只能由代码版本、修复是否部署以及是否达到对应压力共同验证，不能用「dcp=8 正常」证明它兼容，也不能用它推断 TP 对本文 656B KV 仍按头切分。
