MTP 为什么会让上下文减小?

GLM-5.2 vs Kimi K3 · KV cache 才是大头,不是权重大小

权重只多 1% KV cache 吃掉 15-25% 显存 草稿树要预占槽位

0 一句话回答

MTP 层的 KV cache 和 草稿树临时槽位 吃掉了原本属于主干的显存 pool → 能容纳的上下文 token 数减少。

权重大小不是重点:GLM-5.2 只多 1.3% 参数(1 层 MTP),Kimi K3 只多 1%(1 层 Draft)。
真正的大头:KV cache — 每层每 token 都要存 K/V,MTP 层也是 Transformer,同样要缓存。草稿树虽然"验证后释放",但验证前必须预占槽位。

核心洞察:参数增量很小(1-1.3%),但 KV cache 是按层×按token 累积的。

3 推理时的 KV 动态变化

以 GLM-5.2 为例,展开一次 decode 请求的内部时间线。

主干 forward:读取 prompt KV,生成下一个 hidden state
KV 占用:+1 位置 × N 层(主干)
MTP 草稿展开:用 MTP 层迭代 3 次,预测 t+1, t+2, t+3
KV 占用:+3 位置 × 1 层(MTP 临时,验证后释放)
主干验证:用主干并行验证 3 个草稿 token
KV 占用:+3 位置 × N 层(主干,用一次 forward 的成本)
接受判定:逐 token 判定 accept/reject
• 接受的 token KV 永久保留(主干)
• 拒绝的释放
• MTP 临时 KV 全部释放
→ 实际产出 2-3 tokens(GLM accept=2.76)
关键点:草稿 KV 虽然"临时",但验证前必须预占槽位。
• 系统按 最坏情况 分配显存(所有草稿同时存在)
• 即使 accept rate 高,pool 也要扣掉这部分
→ 这就是上下文减小的根本原因

4 深入:GLM vs K3 训练与验证差异

技术读者可展开,不影响理解"为什么上下文减小"。

🔍 GLM-5.2 权重共享机制

训练计算图(3 层展开,权重绑定)

token → [主干 N 层] → h
  └→ [MTP·W] → t+1
     └→ [MTP·W] → t+2
        └→ [MTP·W] → t+3
↑ 同一份权重 W,迭代展开 3 次

优势:省参数(只多 1 层),但接受率高(2.76 > DeepSeek-V3 的 2.55)

🔍 Kimi K3 两阶段训练

阶段 1:预训练 MTP

在全量语料上,用 shifted target 训练(标准 next-token 预测)

阶段 2:后训练蒸馏

冻结主干,只调 Draft 层。展开 7 步模拟推理:

step1: 吃主干第 1/4/末层特征(多层级融合)
step2~7: 吃 draft 自己上一步输出

损失 = −log Σ_v min(p_v, q_v)
↑ 直接对齐接收率,不用 KL 代理

优势:多层级特征 + 直接优化接收率 → 更准,但参数开销略高

🔍 线性 vs 树形投机解码

线性(DeepSeek-V3 / GLM-5.2)

每步只选 top-1,串行单链。加速比 ≈ accept length(约 2-3×)

树形(K3 EAGLE-3)

每步选 top-K=10,展开成分支树。每层 top-K 剪枝 + 全局 top-63 选优 + tree_mask 并行验证。

核心算法(来自 SafeAILab/EAGLE 仓库 cnets.py):

  1. 第一层:top-K=10 个候选
  2. 逐层展开:每节点再出 10 个,累积分数剪枝保留 top-10
  3. 全局选 top-63 节点(整棵树)
  4. 构造 tree_mask:每个节点只 attend 祖先(分支间互不可见)
  5. 主干一次 forward 并行验证整棵树

优势:树形接受率更高,加速比可 > accept length。但草稿树 KV 槽位更多 → 上下文损耗更大。

5 工程优化 — 如何缓解上下文损耗

1. Prefix caching

多请求共享相同 prompt(系统 prompt / 文档前缀)时,缓存前缀 KV,减少重复计算和显存占用。

2. Chunked prefill

把长 prompt 分块处理,降低单次 forward 峰值显存,平滑 KV pool 压力。

3. 动态调整 max_draft_len

监控 accept rate:高则保持草稿步数,低则缩短(减少无效草稿的 KV 开销)。

4. 只对长上下文请求关闭 MTP

路由策略:上下文 < 64K 时开 MTP(吞吐优先),≥ 64K 时关 MTP(上下文优先)。

5. CPU offload

把冷 KV 卸载到 host DRAM,需要时异步加载。但要平衡 PCIe 带宽开销。

6 核心结论

  1. 权重不是大头:MTP 层权重只多 1-1.3%,加载一次,静态
  2. KV cache 才是大头:每层每 token 都要存 K/V,MTP 层也是 Transformer,同样要缓存
  3. 草稿树要预占:验证前必须分配槽位,即使后续释放,系统按最坏情况分配
  4. 上下文损耗公式:主干 KV pool 从 100% 降到 70-80%,对应上下文从 128K 降到 90-110K
  5. 这是权衡:用 15-25% 上下文换 2-3× 吞吐,智能体/短对话场景(上下文 < 64K)很划算
  6. 不是强制的:可以按请求动态开关 MTP,长上下文请求关闭即可恢复到 Base 容量
一句话总结:MTP 让上下文减小,不是因为"模型变大了",而是因为 KV cache pool 被 MTP 层和草稿树瓜分了。 权重增量很小(1%),但 KV cache 是按 token 累积的,这才是真正吃显存的地方。
