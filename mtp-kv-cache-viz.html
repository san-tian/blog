3 Kimi K3 EAGLE-3 风格 · 1 层 draft

draft = 1 个主干 block 的完整拷贝(独立权重,不共享),读取主干 第 1 / 4 / 末层 的多层级隐特征,经 fusion matrix 融合后输入。预训练当 MTP,后训练蒸馏成 EAGLE-3 draft。

训练两阶段:
① 预训练:MTP 层在全量语料上
   用 shifted target 训练(预测下一个 token)

② 后训练:冻结主干,只调 Draft
   展开 7 步 模拟推理:
   step1: 吃主干特征
   step2~7: 吃 draft 自己上一步输出

损失 = −log Σ_v min(p_v, q_v)
直接对齐接收率,不用 KL 代理
与 GLM 的核心差异:
• GLM: 3 层权重共享 → 省
• K3: 1 层完整拷贝 → 重,但吃多层级特征 → 准
• K3 直接优化接收率损失 → 更贴合投机解码

6 草稿树怎么算出来的 · 引用 EAGLE-3 核心代码

K3 的 draft 是 EAGLE-3 风格。草稿树不是"全展开 K^depth 个节点",而是每层 top-K 剪枝 + 全局 top-total_tokens 选最优子树。核心代码来自 SafeAILab/EAGLE 仓库的 cnets.py(约 200 行),本地路径 /tmp/EAGLE。

7 投机解码推理时序 step-by-step

把一次 decode 请求的内部时间线展开来,你会看到 MTP 推理时显存里到底在发生什么。这是理解"上下文为什么会被吃"的关键。

7.1 单次 decode 请求的完整生命周期(以 GLM-5.2 为例 · 3 步草稿)

7.2 接受率 vs 加速比

每次 decode 请求加速比取决于平均接收长度(accept length α):

加速比 = (α + 1) / (1 + ε)
    α = 平均接收长度(每轮接受几个 token)
    ε = MTP 小步成本 / 主干成本 (≪ 1)

GLM-5.2: α = 2.76, ε ≈ 0.1
    → 加速比 ≈ 3.76/1.1 ≈ 3.4×

K3: α 未公开,但 7 步展开
    理论上界更高,但需更长 draft KV

7.3 为什么临时 KV 槽位会"挤掉"上下文

SGLang/vLLM 在分配 KV cache pool 时需要预留草稿槽位:

max_total_tokens = 可用显存预算 ÷ 每token KV
    × (1 - draft_overhead_ratio)

draft_overhead_ratio =
  MTP层KV + 草稿树KV + 验证峰值
  ────────────────────────────
    pool 总容量

→ ratio 越大,context 越小

实际框架(SGLang)会在启动时根据 MTP 配置自动算 draft_overhead。

8 显存预算公式推导

把"上下文为什么减小"这件事用公式算清楚。以 GLM-5.2 (744B) 部署在 B200 (192GB) 上为例做估算。

8.1 总显存 = 权重 + KV cache + 激活 + 系统开销

8.2 每 token KV 开销(以 GLM-5.2 MLA 为例)

GLM-5 MLA 配置:
· hidden_dim = 6144
· kv_lora_dim = 512
· 每 token KV 大小:
  k = 512 × 2B(FP16) = 1 KB
  v = 512 × 2B = 1 KB
  合计 ≈ 2 KB/token/layer

78 层主干:
  主干 KV ≈ 78 × 2 = 156 KB/token

1 层 MTP:
  MTP KV ≈ 1 × 2 = 2 KB/token

MTP KV 增量 ≈ 主干的 1.3%

8.3 草稿树临时 KV(容易被低估)

GLM-5.2 (3 步草稿):
· 树宽 = 1 + 1 = 2(线性,非树形)
· 每步临时 KV ≈ 2 KB
· 峰值同时占用 ≈ 3 × 2 = 6 KB/token
· 相对主干 156 KB 的占比 ≈ 3.8%

K3 (7 步展开 + 树形):
· 树分支可能 4~8 条同时验证
· 峰值 ≈ 7 × 8 × 2 KB ≈ 112 KB/token
· 相对 K3 主干(更大 hidden_dim 7168)
  占比可能达到 15~25%!

💡 K3 的草稿树 KV 开销远大于 GLM

8.4 上下文估算(GLM-5.2 · 单卡 TP=8 · 单 batch · FP8)

假设:
· B200 单卡 192GB, 减去权重 148GB + 激活 8GB + 系统 8GB ≈ 28GB 可用于 KV cache
· 每 token 主干 KV = 156 KB
· MTP 临时开销约占 KV pool 的 5%(草稿槽 + 验证峰值)

无 MTP:
  max_context ≈ 28GB / 156KB ≈ 184K tokens(理论)

开启 MTP:
  可分配给主干的 KV ≈ 28GB × 0.95 ≈ 26.6GB
  max_context ≈ 26.6GB / 156KB ≈ 175K tokens

↓ 缩小约 5% · 实际还受并发 batch、prefix cache 影响

实际部署中,你会在 SGLang 日志看到:
· --max-total-tokens 参数自动从 184000 降到 ~165000~175000
· 单一长请求的影响更大(因为 KV pool 是共享的)

📌 以上是简化估算。实际数字取决于:hidden_dim、num_layers、TP 度、并发 batch、prefix cache 复用率、KV 量化精度。

9 工程优化 · 如何缓解上下文损耗

虽然 MTP 一定会"吃掉"一些上下文,但工程上有 5 类常见缓解手段。

优化手段原理收益代价
MTP 层 KV 复用主干GLM-5.2 KVShareMTP 头不重新缓存 K/V,而是 share 主干某层 KVMTP KV 开销 → 几乎为 0接收率轻微下降
Draft layer 量化MTP 层权重从 FP8 → INT4,KV 同步量化MTP KV × 0.5精度损失
树形限制每轮验证只展开 2~3 个分支(而非指数)草稿树 KV -50%接收率 -10~20%
Prefix cache 复用同 prefix 的请求共享 KV有效上下文感知不到损耗需更长 prompt 拼接
MTP 步数权衡从 3 → 1减少草稿步数临时 KV 峰值 -60%加速比 -40%

实际部署中的选择

KVShare 和 IndexShare 设计就是为了把 draft 开销压到接近 0 📌 Kimi K3 通过 DSpark 单层+ 特征复用,本质也是同一思路 📌 结论:两家在"省 MTP KV"上殊途同归,但实现路径完全不同

10 核心结论

一句话: MTP 权重本身只是"多 1 层"(约 1% 参数),但 KV cache 才是大头。

MTP / draft 层每个序列位置都要缓存 K/V,加上投机树展开多步(GLM 3 层 / K3 7 步)的临时 KV 槽位,挤占了原本全给主干上下文的 KV pool。

公式: max_total_tokens = (可用显存 − 权重 − MTP层KV − 草稿树KV) / 每token KV开销
开启 MTP 后,分子变小 → max_total_tokens ↓ → 上下文减小。
